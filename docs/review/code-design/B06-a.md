# B06-a：资源句柄与 registry

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `f8a9d633`，工作区干净。读取 handles、GfxResourceAccess、FrameLabel、
GfxResourceRegistry，追踪 Runtime begin_frame 的 timeline wait，以及 texture/sky 退役调用方；
复核叶子 buffer/image/view 的显式 destroy 与 diagnostic 顺序。未扩展到 bindings 的逐项实现。

## 发现与局部方案

- **P1，重复退役按最早帧释放。** 同一 handle 先登记 frame 10，再登记 frame 12，cleanup(13)
  在 FIF=3 时会先移除资源，而最新退役要求到 frame 15。合并为每 handle 一条记录，取较晚帧。
  null/stale handle 不进入队列；使用 checked_sub 比较年龄，避免 frame+FIF 溢出后提前释放。
- **P1，诊断 panic 破坏释放集合。** registry 移出 owner 后先记录日志；destroy_all 使用 drain，
  cleanup 提前移除所有到期记录，image 释放提前取走完整反向索引。logger panic 会中断当前
  native destroy，并遗失其他成员或其待回收记录。局部方案：去掉重复 registry 诊断，保留叶子
  释放日志；完整释放本次集合后再传播首个异常，保持 view→image 顺序及索引清理。
- **P2，destroy_all 后再登记不重置诊断状态。** 当前 public destroy_all 可清空后复用，但
  destroyed 留为 true，后续遗留资源可能绕过 Drop 检查。登记新资源时重置；不改变 Drop 为 native 释放。

## 保留的边界

SlotMap generation 能拒绝本 registry 中删除后的旧 key；不同 registry 的首个 key 可相同，
它不是全局/device 身份。当前 Runtime 是调用链中的单一 registry owner；跨 registry 身份需要
另行设计，不新增 brand/UUID 设施。GfxResourceAccess 窄化查询依赖，不延长 native 生命周期。

Runtime begin_frame 先等待 current_frame_id-FIF，再调用 cleanup；两处使用相同 FrameLabel::COUNT。
texture 退役先 unregister SRV，sky 切换后退役旧 distribution；descriptor/FIF 消费闭环交 B06-b。
调用者仍须停止后续使用，并给出不早于最后使用的 frame id；registry 不自行等待 GPU，也不证明
传入的 frame id 或 device 来源正确。u64 帧号整体回绕策略交 B12，不以局部算术检查宣称已解决。

View 创建在 leaf 成功后登记 pool/lookup/反向索引；key/desc hash 没有用户回调，剩余可分配步骤
主要是容器分配。不能把 catch_unwind 当作宿主 OOM abort 的恢复方案。native view 创建失败的
leaf 回收已由 B05-b2 覆盖；不为当前路径增加事务框架。

## 架构预检

复用 GfxResourceRegistry、SlotMap/SecondaryMap、现有显式 leaf destroy；行为归 registry impl，
不增加 free helper、跨帧 context、线程或新的依赖方向。延迟回收仍以前置 timeline 完成为条件，
不改 RenderGraph/descriptor 同步。同步 foundation/runtime README 与本报告，不更新 summary。

## 延迟回收验证

`.temp/code-design/B06-a/make_probe.py/run_probe.py` 编译实际 registry 全文、handles、FrameLabel、
GfxResourceAccess，使用锁定的 slotmap 1.1.1；仅替换 native 资源与 Tracy instrumentation。
新旧版在断言开关下各执行 11 组：单次、较晚/较早/同帧重复、接近 u64::MAX、未来帧、null/stale、
立即释放/slot 复用、同 image 多 view 缓存及跨 registry key。新版全部通过；旧版较晚重复提前
释放，极值在 debug panic、无断言提前释放。跨 registry key 相同是明确保留的契约限制。

`cargo check --offline --locked -p truvis-render-runtime` 通过；该夹具不验证真实 GPU 完成。
延迟回收和 handle 契约对应 `c00695fa`；诊断失败修复与交接位于本报告所在提交。

## 诊断失败修复与验证

移除 registry 中重复的资源释放日志；叶子仍在 native release 后记录名称/raw/reason。
私有 release_buffer_now/release_image_now 返回捕获的异常，让调用方继续收尾完整集合；
destroy_all 逐项释放全部 views、images、buffers，并清空队列/索引后传播首个异常。
立即释放、到期清理复用相同单资源路径，不新增通用异常框架或隐式 Drop release。
登记 buffer/image 重置 destroyed，覆盖 public destroy_all 后复用 registry 的情况。

`.temp/code-design/B06-a/make_release.py/run_release.py` 引入实际 registry，以 `c00695fa`
为基准；同样使用真实 SlotMap，native destroy/叶子日志顺序由桩模拟，Tracy 替换为无操作。
两种断言配置下各 19 组：buffer/image 立即释放、到期集合、destroy_all × 日志关闭/仅 registry/
仅 leaf/全部日志 panic，另含 view 创建失败与 clear 后重新登记 buffer/image。
新版全部通过，确认未来条目仍保留、view 在 image 前释放、反向索引清空、首个 panic 被传播，
所有应回收 native 对象成对释放；旧版可观察 native 遗留、到期队列丢失及 destroyed 状态过期。
最终再运行 11 组延迟回收回归，包含立即释放取消已有退役记录，两种断言配置均通过。

最终 `cargo build --offline --locked -p truvis-render-runtime`、
`cargo check --offline --locked -p truvis-renderer` 与提交前空白检查通过。

这些验证不覆盖 native destroy 自身异常、宿主 OOM abort、panic payload 的自定义 Drop，
也不证明真实 GPU 时间线或驱动生命周期正确。registry 单次调用收尾后仍会传播异常；外层
Presenter/Runtime 需要自己的整体退出策略，不能据此取消 B05-d2 → B12 的交接。

## 结论与下一批

当前 handle/只读访问 trait 有明确用途：隔开 RenderGraph 与 Runtime owner；未发现需要
合并 crate 或删除该契约层的证据。registry 的 view lookup/反向索引分别服务复用和释放，
保留；重复释放日志和 buffer 两条释放实现已收敛。不同 registry 身份限制仍需调用方遵守。

B06-a 约定范围已扫描并完成上述局部修复，B06 仍部分完成。下一批 **B06-b bindings**：
