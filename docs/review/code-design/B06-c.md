# B06-c：FIF owner 与剩余 foundation 契约

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `1b10855c`，工作区干净。范围为 StageBufferManager、CmdAllocator、
PerFrameGpuData、RenderView 和 RenderSceneView，并追踪 Runtime begin_frame/prepare/destroy、
Renderer command 分配与 Camera 快照入口。

## 扫描证据与局部方案

- **P2，未使用的 staging owner。** 全仓搜索 StageBufferManager/stage_buffer_manager，除定义、
  模块导出和 Runtime README 外没有调用；实际上传由各 upload queue/scene owner 持有 staging。
  其 destroy 注释仍声称 Drop 自动释放，实际 Drop 仅写日志，drain 中途日志 panic 也会遗失
  余下 native owner。删除整套未使用接口和导出；不新增第二套回收协议。
- **P1，FIF 数组部分构造缺少回收。** CmdAllocator::new 与 PerFrameGpuData::new 都直接
  使用 FrameLabel::ALL.map 创建 native owner。后续项失败会 Drop 已创建部分，RHI Drop
  只诊断、不释放；debug 还可能二次 panic。以局部 Option 数组持有未交付资源，失败时显式回收。
  CmdAllocator 的 CPU-only Vec 初始化应先于 native 创建；其无调用点的 Default 必然 panic，删除。
- **P1，PerFrameGpuData 销毁被诊断异常截断。** destroy 顺序调用 buffer.destroy_mut，
  leaf 已释放后 logger panic 会跳过余下 FIF buffers。完成全部 buffer 回收后再传播首个诊断异常；
  构造失败回收同样逐项收尾，并保留原始构造错误。
- **P3，command 复用文档失真。** 当前 Runtime begin_frame 在 timeline 等待后 reset pool，
  持久 command clone 留到下一次录制；不是“帧结束自动 free”。free_frame_commands 无工作区
  调用点，保留显式释放能力并说明 GPU 完成与外部 clone 撤销前置。

## 契约判断与保留项

修复属于既有 resources/bindings owner，不增加线程、依赖方向、全局错误框架或 Drop native
释放。保持 FrameLabel 三槽、pool TRANSIENT 标志、UBO 类型与 shader ABI；失败回收只针对
尚未发布/提交资源，正常 destroy 仍要求 GPU 完成。同步 Runtime README 和批次清单。

PerFrameGpuData 的 new_ubo 使用 UNIFORM_BUFFER/TRANSFER_DST，Runtime 在 prepare 中先
cmd_update_buffer，再建立 TRANSFER_WRITE 到 shader/UNIFORM_READ 屏障，最后向 graphics
queue 提交。begin_frame 已等待当前 FIF 上次使用；这里只核对局部链，不替代 B07/B12 对所有
提交与跳帧路径的同步证明。共享借用 buffer/write 仍可被调用方脱离阶段使用，能力收口交 B12/B26。

RenderView 在 Camera::render_view 唯一构造路径固定逆矩阵；字段公开允许手工构造或改变后
不重算 inverse，非法/奇异矩阵也没有入口验证。这是契约缺口，尚未发现当前调用链触发，交
B14 相机/配置审阅，不在本批改变公共数据布局。RenderSceneView 对应 runtime 私有 owner，
按指定 FIF 读取 prepare 后的 TLAS/亮度/签名与 raster cache；trait 的单实现不构成冗余证据。
draw_raster 会向传入 command 录制命令，“只读”仅指场景状态，不代表无 GPU 命令副作用。

## 实施与验证

第一项已删除 StageBufferManager 的实现、导出与活跃模块说明；engine/renderer/app 搜索已无
残留引用。`cargo check --offline --locked -p truvis-renderer` 和 `git diff --check` 通过。
删除对应 `3fdf5f5d`；FIF owner 修复、模块说明与交接位于本报告所在提交。

`CmdAllocator::new` 与 `PerFrameGpuData::new` 使用局部 Option 数组逐项记录 native owner，
成功后转换为完整固定数组。构造失败显式回收；UBO 销毁逐项捕获 leaf release 后的诊断异常，
正常 destroy 完成全组后传播首个异常，构造失败则保留原始错误。移除必然 panic 的
CmdAllocator::default；workspace 无调用。没有新增通用 helper、隐藏 Drop 回收或并行状态表。

`.temp/code-design/B06-c/run.py` 编译这两个实际源文件、实际 FrameLabel、BytesConvert 与
生成的 PerFrameData；Vulkan pool/buffer/command 采用事件替身。以 `1b10855c` 为对照，
在 debug assertions 开/关两种配置下各执行 15 组：command 分配/reset/free/destroy、三个
FIF UBO 写入、每个 pool/UBO 构造失败、构造失败伴随回收日志异常、每个及全部 buffer
销毁日志异常。新版全部回收且保持原始构造错误；旧版在第 B/C 项构造失败分别遗留 1/2
个 native owner，销毁 A/B 的日志异常分别遗留 2/1 个。成功路径的 command 事件与 UBO
槽位/字节数记录前后一致（当前每槽 456 bytes）。

替身 Drop 只记录遗留，不模拟真实 debug 二次 panic/abort；没有执行 Vulkan，不能证明驱动
分配、GPU 完成或真实屏障效果。宿主分配 abort、native destroy 失败、自定义 panic payload
析构异常及外层 Runtime 退场不作恢复保证。没有新增单元测试或修改 shader ABI。

`cargo build --offline --locked -p truvis-render-runtime`、`cargo check --offline --locked
-p truvis-renderer` 与提交前 `git diff --check` 均通过。两个修改的 Rust 文件通过 stable
rustfmt 检查，但该工具忽略项目的 nightly-only 选项，不能算完整 nightly 格式验证。
修复入口为 [CmdAllocator::new](../../../engine/e40-render/truvis-render-runtime/src/resources/cmd_allocator.rs)
（当前第 29 行）与 [PerFrameGpuData::new/destroy](../../../engine/e40-render/truvis-render-runtime/src/bindings/per_frame_gpu_data.rs)
（当前第 20/44 行）；资源发布/退役规则仍见 [资源生命周期设计](../../design/resource-lifecycle-and-destruction.md)。
