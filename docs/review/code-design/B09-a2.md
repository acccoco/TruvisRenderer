> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `afba45d7`，工作区干净。范围为 AssetSystem 的 scene request、
payload 转录、完成事件消费和 SceneImportRecord 生命周期；读取 GameWorld facade、
AssetLoadService、材质/mesh 校验以及 sample/automation 的直接消费入口。

## 修复前发现

- **P1，已复现并修复正常输入失败路径：失败的 scene 留下部分资源。** `ingest_scene_loaded` 先
  register_mesh，再逐个 register_scene_texture/material。后续 mesh 校验、纹理路径
  canonicalize 或材质校验失败时，只标记 SceneImportRecord Failed，不回收已登记资源。
  应先完成整份输入的可失败预检与路径解析，再进入资源身份发布阶段。
- **P1，已复现并修复：诊断 panic 丢失完成结果。** poll 将 update 返回的 Vec
  放在局部 for 循环中；一个事件的日志 panic 会丢弃余下事件。TextureLoaded/Failed
  又先移除任务映射、写日志，后改 record，可能留下无法再次完成的 Loading。
- **P2，已复现并修复：scene 请求发布早于 task。** import_scene 先创建长期
  record，再调用 service；请求日志 panic 会遗留一个不可达的 Loading record。
  无效文件路径应仍返回可查询的 Failed handle，但不得依赖日志成功才能把 handle 交给调用方。

预定修复沿用 AssetSystem/AssetStore、现有校验函数和 loader，不引入通用事务框架。
正常输入失败在资源发布前拒绝；纹理解码/派发失败仍是独立 texture 状态，不把 scene Ready
误解为所有贴图 Ready。诊断异常的恢复要求限定为 Rust unwind，不覆盖 abort/OOM。
冗余/过度抽象：短期 load handle、长期 import handle 与 texture 去重身份不可合并。

SceneStore 的编辑与版本审阅仍由 B09-b/c 继续。

## 资源发布预检

新增私有 `PreparedSceneMaterial`，暂存已校验的材质和已解析纹理请求；尚未发布的占位
texture handle 在登记前全部替换。mesh 使用已有 SceneMeshRecord 构造校验，预检成功后
移动该 record，避免再扫描完整顶点数据。材质复用 MaterialData::validate/validate_uv_sets。
整份输入预检期间不派发 texture 请求、不写 AssetStore；失败只更新该 import 的 Failed。
不引入副本 AssetStore、通用事务或回滚日志。CPU source identity、instance 创建和 GPU
资源职责不变。embedded 复用请求时的 canonical identity，不重新要求源文件存在。

`.temp/code-design/B09-a2/run.py` 编译基准/修改版实际 world 源码，替换仅短期 service
为可控事件生产者，保留完整 payload、预检、登记与完成消费代码。各 9 例覆盖后续 mesh
越界、后续材质 NaN、后续缺失路径、共享 Failed 纹理、缺失 UV、错误 mesh 引用/材质数量、
源文件删除后的 owned embedded bytes、成功时多 mesh/material 与纹理去重。
旧版四类后续错误留下部分资源，缺失 UV 被标 Ready；新版拒绝输入时资源/任务数量均与
入口一致，原共享 Failed/error 不变；成功发布的材质 texture handle 均有效。正常 source
文件的真实解码仍使用 B09-a1 的验证；本夹具不声称验证后台执行。

## 诊断与完成事件

AssetSystem 新增 owned `pending_events`，承接 service 整批交付；每次 pop 一个事件，
texture 状态写入后才日志输出。scene 失败已有状态先写，本次保留；如果诊断 unwind，
剩余事件由下次 poll 继续处理，不重放已提交事件。没有吞掉 poll 的诊断 panic，也不
改变线程/队列背压政策；这是已有一次性交付之后的所有权修复。

scene 请求路径错误直接登记并返回 Failed record；正常路径先请求 task 再发布 Loading
record，避免日志 panic 遗留不可达请求。scene 结构发布期间的纹理派发单独捕获 unwind，
将该 texture 记为 Failed、保留可重试身份，再完成其余材质/scene 登记。Scene Ready
仍只表示结构和资源身份，不保证所有 texture Ready。这与直接 import_texture 的调用
失败不发布新身份不同：scene 的原始 load 已交付，完整结构应保留可查询的纹理失败状态。

最终新旧夹具各 **16** 例：上述 9 例加 TextureLoaded/TextureFailed 诊断、scene loader
失败/预检失败诊断、scene 请求诊断、无效 scene 路径诊断、scene 内 texture 请求诊断。
旧版诊断会留下 Loading 或丢弃第二条结果；新版当前状态已提交、第二条下次 poll 可完成。
scene 内请求 panic 不逃逸，结构 Ready 且 texture Failed；随后显式重试沿原 handle
恢复 Ready。可控 service 只用于精确排列结果与派发故障，不替代真实 loader 集成验证。

实际集成验证：`real.py/real.rs` 使用当前编译的 truvis-world、真实 glTF Reader/线程池/
PNG 解码器，导入含一个正常 embedded 纹理和一个缺失外部纹理的文件。确认错误来自
AssetSystem canonicalize，失败后只保留入口前的材质，新增 mesh/texture 均为零；补齐
PNG 后重新导入，scene Ready 且两张纹理最终 Ready，旧 import 仍可查询 Failed。
成功计数包含 Reader 自动追加的默认材质；最初夹具漏计该默认项，核对 copy_scene 后
修正断言，未为通过夹具修改产品行为。

复跑 B09-a1 的 7 个真实加载流程通过；`cargo build --offline --locked -p truvis-world`
及 `cargo test --offline --locked -p truvis-world --lib` 现有 4 个测试通过。空白检查通过。

## 生命周期与跨批次项

SceneImportRecord 没有独立释放入口，包含成功/失败记录及 SceneData，直到 AssetSystem
销毁；sample 消费后不再保留 import handle，automation 仍按 ID 查询。增加释放/保留期
需要定义查询和调用方所有权，交 B21/B27，不能在本批自动删除可重复使用的描述。
SceneData 不进入 mesh/material 的反向引用计数；Ready 是导入完成结果，不是永久有效
的资源租约。显式删除资源后旧描述可能失效，实例化由 SceneStore 校验；此边界已补入 README。
sample 按对象逐个创建 instance，失败时已有 instance 仍保留，且日志异常可能使其重复消费；
这是 App 的实例化边界，交 B21/B25，不扩展本次 AssetSystem 资源预检修复。

当前 source + color space 去重保持 Ready 不变；同路径重新导入 scene 会创建新 mesh/
material，却复用 Ready texture。需要热重载/内容版本时必须整体定义身份与依赖更新，
交 B26/B27 复核；不在局部修复中静默改变已有不可变内容契约。
