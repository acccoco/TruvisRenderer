## 已确认的局部问题

- **P1，已修复并验证**：`SceneBuffers::new` 在字段表达式中连续构造九个 GPU buffer；后续
  构造失败会 Drop 已创建 wrapper，不能替代显式 native 回收。与 MaterialBuffers 已有
  部分构造回滚模式不一致。
- **P1，已修复并验证**：`grow_pair` 先创建 device，再创建 stage；stage 失败时 device 无 owner
  回收。候选完整后又先销毁旧对象再替换，旧对象释放后的日志异常会遗漏候选、跳过旧
  stage 回收，并让原字段留在已销毁状态。
- **P2，已修复并验证**：扩容只通过本次函数返回 bool 通知上传；替换后日志或后续 pair 失败
  会丢失该返回。重入发现容量已足够时不再报告替换。本轮将“新 buffer 尚需完整上传”
  显式保留到提交确认，而不依赖调用者碰巧同时有 scene revision 差异。
- **P2，已修复并验证**：`destroy_mut` 中任一叶子释放诊断异常会跳过余下资源。

## 边界与方案

复用 GfxStructuredBuffer/GfxBuffer 的创建和 destroy_mut、MaterialBuffers 的 catch_unwind
边界。局部 new_pair/destroy_pair 属于 SceneBuffers impl，集中四组同职责 device/stage
操作，不建立跨模块 buffer 框架。构造失败只撤销尚未交付的候选；扩容仍要求当前 FIF
已由 Runtime 等待完成，不改变其它在飞副本、slot 身份、shader ABI 或 GPU queue。

叶子 destroy_mut 已核对为 native release 在前、日志在后。本轮只保证已知安全的释放
诊断异常收尾，不把 allocator/native 失败或设备丢失视为安全恢复。跨 FIF 组合构造及
RenderWorld 关闭交 B11-e；未提交 command 的重录和 Runtime 退场分别交 B11-b2/B12。

## 构造与关闭结果

构造局部持有 scene root 和四组 device/stage 候选，全部创建成功后才交付；第二个
buffer 创建失败先回收本组 device，外层再撤销其余已完成组。回滚忽略释放后的诊断
异常，保留原始构造错误。正常关闭完成九个叶子回收后才传播首个诊断异常；重复关闭安全。
没有把成功对象字段改成 Option，Option 只存在于构造准备阶段。

`.temp/code-design/B11-b1/{run.py,mocks.rs,probe.rs}` 编译实际完整 SceneBuffers，保留
真实 FrameLabel 和生成 GPU 类型，RHI 用受控分配/回收替身。初始容量、九个创建点、
九个关闭释放点及后八个构造点伴随清理诊断异常，共 27 类 × 前后两版 × 两种断言，
108 次运行通过预期；修复版模拟 native 计数归零、原始创建错误保持、正常重复关闭不重复释放。
旧版 wrapper Drop 在夹具中不触发真实 debug assert，才能观察未回收计数；真实 debug
构建在 unwind 中可能二次 panic 终止。夹具不证明 allocator/native 失败或 GPU 安全性。
Runtime 离线锁定依赖编译检查和 diff 空白检查通过；没有新增源码单元测试。

## 扩容与上传交接结果

`grow_pair` 复用成对创建，日志与 checked_next_power_of_two 在分配前完成。候选完整
后先通过 mem::replace 交给字段，登记 needs_full_upload，再回收两个旧对象；旧释放
诊断失败时新 pair 仍由 SceneBuffers 持有，旧 pair 均已收尾。容量不变时不分配。

`ensure_capacity` 返回本次或此前中断留下的完整上传需求；RenderWorld 将它与 scene
revision 差异合并决定结构上传。标记只在 commit_uploaded_frame 确认本 FIF 存在已提交
的 pending_scene_revision 时清除，无结构上传确认或确认中断时保持。提交确认不等于
GPU 执行结束；后续替换仍须等待当前 FIF。初始容量与首次空场景行为保持。

正常新 active 实例通常也会推进 scene revision，但这不能代替 buffer owner 自身的
重建状态。本轮证明扩容通知可跨局部异常保留，没有宣称已复现完整应用中的错误画面。
每 FIF 独立分配、按稳定 slot 求 instance 容量、按 active submesh 求 indirect 容量的
分工保持；未引入通用 buffer-pair 类，也未把其它 light/material owner 一并重构。

`.temp/code-design/B11-b1/{run-resize.py,resize-probe.rs}` 编译实际完整 SceneBuffers 和
实际 RenderWorld::commit_uploaded_frame，后者的其它 owner 使用受控替身。25 类 ×
修复前后 × 两种断言，共 100 次运行符合预期：

- 四组 pair 的八个分配点、八个旧释放点，四个 stage 分配失败伴随清理诊断异常；
  原始分配错误保持，修复后完整新 pair 可继续持有并最终回收，模拟 native 计数归零。
  旧版 stage 失败遗漏一个新 device，释放诊断失败遗漏两个候选并留下已销毁字段。
- 增长日志、部分 pair 成功后下一个失败、usize 容量上界；新日志前置、容量溢出显式
  拒绝，不修改旧 pair。上界注入不声称实际场景会自然达到该规模。
- 所需容量分别为 geometry 9000、最高 instance slot 2048、indirect 9000 时，扩至
  16384/4096/16384；无新增容量需求但尚未提交时仍返回完整上传需求。
- 实际 commit 方法在无 pending revision 或其它 owner 确认中断时保留标记，成功确认
  A 后只清除 A，B 仍需上传；成功确认后再次 ensure 不重复要求上传。

夹具中的 GPU buffer 仅为类型化 CPU 存储和 native 计数替身；没有执行实际 copy、TLAS
或 shader，不据此证明同步正确或画面一致。构造阶段记录保留在 `.temp/code-design/B11-b1/construct/`。
最终 `cargo check --offline --locked -p truvis-render-runtime`、`-p truvis-app` 及
`git diff --check` 通过，无新增项目编译警告；未运行完整构建或 GPU 回归。
