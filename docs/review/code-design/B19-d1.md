## P1：后续图像组构造失败遗失已完成的前缀

RestirDiTargets::new 连续构造 initial/temporal/final/surface 各四组 PerFrameImageSet。
任一后续组创建失败，前面已经注册 image/view 的组仅经过 Drop；Drop 只有 debug 断言，
不执行 Vulkan 回收。release 构建遗留 registry 对象，debug unwind 还可能触发二次 panic。
B15-a5 的单组 image/view 回收不能覆盖这个组合 owner。

每次 PerFrameImageSet::new 正常返回都已等待该组 initial transition 完成；后续组的
transition 只引用自己的新图像。因此已完成前缀可独立回收，不能由“当前失败组的 submit
状态未知”推导前缀也在使用中，更不能反过来据此前缀的安全点释放失败组内部图像。

架构预检：改动归 RestirDiTargets::new，复用 Option 保存半成品和 catch/resume 的既有
模式，复用 PerFrameImageSet::destroy。组内 view-before-image 由 registry 保证；
原始构造异常优先于回收诊断。不新增长期 owner、通用事务、依赖方向、线程、shader ABI、
资源或 pass；同步 renderer-rendering README。现已修复并验证，与本报告所在提交一致。
以固定长度的描述数组和 Option 数组保留已完成组；失败时逐组显式回收，全部成功后才
组装完整 owner。构造顺序、名称、格式和 usage 不变；不新增空 target 或默认 fallback。

## 已核对的直接生命周期

- RestirDiTargets 无私有 history signature，只持有三种 reservoir 与 surface 的 FIF 图像；
  temporal accessor 是下一帧历史来源，final 只服务当前帧。这是 owner/接线核对，FIF 同步
  正确性仍交下一批，不在此宣称完成。
- rebuild 先按 Resize 清空旧组，再创建替代；失败不恢复旧画面。已完成的旧组释放后，
  self 保持空 handles，不能当作可继续渲染的 fallback。TruvisRenderer resize 请求 reset。
  外部 resize 的 Presenter、内部 extent 同步及正常 shutdown 均先等待 GPU idle；这只说明
  本批 target 的已提交引用完成，不消除 B05/B16 记录的 WSI presentation/异常退出缺口。
- destroy_all 逐组清空 handles，捕获释放诊断后继续释放其余项，最后传播首错；Drop 只检查
  显式释放是否完成。RealtimeRenderResources shutdown 在 RT pass 释放后释放 targets。

## 验证与交接

`.temp/code-design/B19-d1/check-construction.py` 编译实际 RestirDiTargets、共享 target 和
FrameLabel 源码；只将 Vulkan/registry/ctx 换成 CPU recorder。新建与 rebuild 各覆盖
48 个 image、48 个 view 失败位置，包含清理同时失败；16 个 transition 失败位置也按
两种清理状态检查，另含正常新建/rebuild、48 个释放失败位置和全部释放报错。

- 每轮 499 例；修复前关闭 debug assertions 的一轮确认最多遗留 45 张已注册前缀图像，
  修复后 debug assertions 开/关的两轮均通过，已知安全失败全部清空 registry。
- 原始构造错误身份保留，每张图像最多显式释放一次；一个清理诊断不会跳过其它组。
  rebuild 失败后旧 owner handles 已清空，再 destroy 不会重复释放。
- transition 异常只回收已经返回的前缀；正在失败的三张 raw image 没有新增回收。
  mock 没有真实 raw GfxImage 的 debug Drop，不能据此证明实际未知提交路径可正常 unwind。
- 正常新建/rebuild 校验全部 16×3 个 accessor 的 image/view、format 与 extent；前后
  资源事件（含名称、usage、transition 与等待）逐字节一致。旧版开启 debug 的失败用例
  会遇到前缀 Drop 的二次 panic，未将它们纳入通过数；旧版 debug 仅运行两项正常流程。
- `cargo check -p renderer-rendering -p truvis-renderer` 与 `git diff --check` 通过。
  无 shader/ABI 改动，未重复 shader 构建，也未执行 GPU 故障注入或图像验证。
