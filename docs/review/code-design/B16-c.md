不改变上传次数、图像格式/layout、GPU idle 前置、线程与依赖方向。

## 关闭链审阅：保留明确的全局缺口

| 阶段 | 当前事实 | 结论/交接 |
|---|---|---|
| 正常 Renderer→Runtime→Gfx | 正常 run 退出执行 shutdown；Renderer 先释放 DLSS feature 再关闭 target；Runtime 回收 child，Gfx 关闭 SDK 后销毁 device/instance | 静态顺序与既有契约一致，不代表实际 GPU/SDK 关闭已验收 |
| RenderLoop 内异常 | run 没有围绕 init/frame 的 cleanup guard，异常跳过尾部正常 shutdown；RenderThread 外层只捕获并通知/交回错误 | P1：join/完成通知不是 GPU owner 已回收的证据；debug Drop 诊断也可能造成 unwind 再次失败。B27 整体设计，不把每个 hook 包 catch 当作完整修复 |
| feature free 失败 | B16-a 保留失败归属并停止继续配置/销毁，B16-b 失败 evaluate 不再提交部分 graph | 只保证局部停止，不提供进程恢复；SDK 是否部分执行未知，不能自动重试 |
| SDK shutdown 失败 | native 停止服务、保留 DLL、清空 callback；Rust StreamlineRuntime::drop 只记错误。Gfx::destroy 在 Drop 正常返回后仍继续 gfx_core.destroy | P1：DLL 保留不等于 SDK 资源已回收；失败后继续 root 销毁的政策与 SDK 状态没有闭合。B27 需确定终止/保留策略和可验证的完成信号 |
| 更早的 Client/资源 hook 抛错 | 仍可阻断 Renderer 或 Runtime 后续关闭链 | 不把允许继续的释放后诊断与未知资源状态的 SDK/submit 错误混为一类；随 B21–B25 补足 owner 证据，B27 统一方案 |

以上均为本次静态读取到的路径，不是新的运行崩溃复现。SDK 依据仍是配置 v2.14.1 及
B16-b 核对的固定官方文档；本批没有升级、重启或故意破坏 SDK。

## 构造与能力边界

- SR exposure 的本次修复只覆盖上传成功返回之后；one_time_exec 未向 Renderer 暴露
  “尚未提交”和“submit/wait 状态未知”的区分，不能套一个 catch 后释放全部 image/staging。
- RR input target 的多个 PerFrameImageSet 构造各自可能执行 transition，之后还有 hit-distance
  clear 提交；SDR/Realtime/Offline 组合 owner 同样嵌套同步提交。叶子已完成资源与失败中的
  在飞资源须分别追踪。当前没有结构化失败信息，整体回滚方案交 B27，不新增隐式 Drop Vulkan release。
- **交 B20 的明确局部项**：SharcTargets::new 在首次 clear_all 提交之前顺序创建三个 buffer，
  后一个分配失败会跳过已完成前缀的显式回收。这一阶段可独立修复，不应藏入最终全局改造；
  SHARC 自己的 clear_all submit/wait 失败仍属于未知状态，不能与前缀分配失败一起回收。
  后续 [B20-a](B20-a.md) 已修复该分配前缀回收，未知提交边界保持不变。
- manual hook 的唯一保留理由是未来 ABI 兼容，已移除。RR packed/unpacked 则保留 SDK options
  的表达与现有 unsafe 前置：独立 optimal query 不消费 guide，生产 set/evaluate 固定 packed，
  当前 evaluate descriptor 没有独立 roughness。未将该字段可表达的值误报为完整 unpacked 能力，
  本批不实现新的 guide 模式，也不通过新增泛型 feature abstraction 隐藏差异。
- 高层调用目前收敛在 RenderThread 的 phase Ctx：init/support/options、update/resize idle、
  当前 command 录制与显式 feature free。binding 自由入口仍为 unsafe，不因 owner !Send/!Sync
  就宣称所有 raw handle 与调用阶段在类型层已经完备；是否进一步收窄属于 B27 方案。
