## 容量替换（P1，已确认并修复）

`engine/e40-render/truvis-render-runtime/src/ray_cast/mod.rs` 的 `ensure_capacity` 原来
先删除全部旧 buffer，再依次写入三个新 owner，最后才更新 capacity。已有容量 4、请求
7 条 ray 时，新建第一个或第二个 buffer 失败会留下旧 capacity=4 和缺失字段；随后请求
少量 ray 将跳过扩容并访问缺失字段。旧 buffer 释放诊断也可形成同样的不完整组合。
当前 RenderLoop 没有恢复这类 panic 的保证，但这不能使部分构造资源的遗漏变得合法。

本报告所在提交先验证 u32 count 与 checked capacity，完整创建候选后同时登记 owner/
capacity，再逐项释放旧资源。失败只回收候选并保留原错误。`release_buffers` 是此 owner
内部同一资源组合的释放入口，被构造候选回滚、替换和关闭复用；未引入泛型资源框架。

`run-grow.py` 基于 `38193865` 前后对照，实际提取对应方法；13 类 × 2 版本 × 2 配置，
**52 次通过**。覆盖首次/再次扩容的三个创建失败点、三个旧释放诊断、两种回滚报错、
复用/缩小、失败后小请求与重试，以及超 u32 请求在修改前拒绝。大计数使用模拟分配
上限验证拒绝位置，不实际申请数十 GB。提取后的生命周期夹具再次全部通过（56 次），
确认复用释放入口后关闭和重复关闭契约保持。App 编译、空白检查通过；未新增源码测试。

## 冗余、抽象与未决项

service 与 pass 分离查询生命周期和 pipeline/descriptor 录制，当前有保留依据。
释放分支在本 owner 内收敛，未把资源清理推广到其它模块。没有改动 shader ABI、CPU
identity 映射或同步查询返回语义；GPU 命令读写和输入数值检查尚未完整审阅。
