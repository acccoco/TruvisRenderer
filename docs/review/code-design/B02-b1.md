## 边界与判断

`ShaderBuildRunner` 拥有任务发现、并行编译、依赖校验和成功状态；三个 compiler 负责参数与进程调用，`ShaderDependencyValidator` 检查 depfile 的 package 边界。`just shader` 只有 shader-build 成功后才运行 binding 构建。

冗余与抽象：三类 compiler 参数不同，共用任务模型和诊断有实际用途；本链未发现需要合并或删除 trait 的证据。不增加新状态框架。严密性：当前仅凭输出与 depfile 存在认定任务可复用，没有区分编译器临时产物和已验证产物。

## 已确认问题

### 失败产物可被下一次增量构建接受（P1）

- 修复前 `runner/mod.rs:compile_task` 删除旧 depfile 后直接调用 compiler，非零退出通过 `?` 返回；编译器已经写出的 output/depfile 留在原位。`run` 在旧 manifest 与输入一致且两个文件存在时跳过任务。
- 触发：成功构建 → 输入不变的 `--force` 编译写出两个文件后退出 7 → 普通构建。临时夹具在 Slang/GLSL/HLSL 三条调用路径均确认：失败返回 1，下一次返回 0 且没有调用编译器。
- 反证：输入改变时旧 manifest 通常会强制重编，不能消除 force、工具故障或中途终止时的缺口。当前依赖越界分支会删除输出，正常可重试，但删除失败时 depfile 仍可能存在。
- 最小修复：复用现有 depfile 缺失即重编的判定；编译器只写临时 depfile，通过退出状态、输出存在和依赖验证后才发布正式 depfile。开始执行前使旧完成标记失效。失败清理错误继续报告，不依赖清理成功保证重试。
- 处置：已修复并验证，见下方验证记录。

### 编译器成功退出但没有生成输出仍可报告成功（P1）

- `compile_task` 不检查本次 output；旧 output 未移除时，新的合法 depfile 可让旧字节被当成本次成功结果。
- 临时夹具：先成功，再 force 返回 0、只写 depfile；三条路径均返回成功，随后普通运行跳过。
- 最小修复：执行前移除旧输出，成功后检查新输出是文件。这里只检查产物存在，不宣称完成 SPIR-V 语义验证。
- 处置：已修复并验证，与任务完成标记一同闭合。

### 编译器启动错误绕过 Result 汇总（P2）

- `slang.rs`、`glsl.rs`、`hlsl.rs` 使用 `Command::output().expect(...)`；bare executable 不存在时进入 Rayon panic，不能按任务返回诊断。
- 三种临时场景均确认退出 101；已有缺失 depfile 通常仍保证下次重编，因此不将此问题夸大为必然污染缓存。
- 最小修复：沿既有 `Result<(), String>` 返回包含编译器与源路径的启动错误，与非零退出走相同失败链。
- 处置：已修复并验证，三条路径均返回错误码 1，不再 panic。

## 修复与验证

本报告所在提交统一修改任务的成功判定：执行前删除旧正式 depfile、临时 depfile 和 output；编译器写 `.d.pending`，只有本次输出存在、依赖验证通过后才 rename 为正式 `.d`。失败时清理临时产物并汇总清理错误。正式标记缺失保证清理失败仍不会跳过任务。三个 compiler 的启动错误沿既有 Result 返回。

`COMPILER_ARGS_VERSION` 提升为 `shader-compiler-args-v5-validated-depfile`，使旧判定留下的缓存首次运行时重新验证；没有改变 state schema 或引入旧格式读取。没有改变 Shader 源码、ABI、编译参数、public API 或 Rayon 并行模型。utils README 同步说明任务成功边界。

已执行：

- `cargo build -p truvis-shader-build` 成功；修复后的实际 `just shader` 也重新编译并执行当前工具。
- 15 个修复前/后对照场景全部满足修复后断言：失败返回 1、正式 depfile 缺失、旧成功 manifest 不变；恢复后的普通构建确实重新调用 compiler，再次运行可增量跳过。使用含空格的夹具路径，覆盖三种 compiler。
