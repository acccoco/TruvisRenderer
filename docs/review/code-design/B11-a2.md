  mesh sync；mesh 同步失败时已消费的 material 通知丢失。
- **P2，已修复并验证**：Runtime 在 sync_assets 前 take_instance_changes，资源结果也仅

- **P2，已修复并验证**：instance table 成功交付后，RenderWorld 先进行 analytic 同步/上传，

  sky binding 的 changed 和 history_invalidated 返回前也有后续失败窗口。

这些路径沿实际调用顺序可确认。完整 Runtime 当前不保证 panic 后继续执行，因此本批
验证局部状态交接，不将它描述为已实现整帧恢复或已复现用户可见的错误画面。

## 局部方案与边界

由既有 RenderWorld 保存去重的待处理资源通知，asset sync 每完成一个 owner 即移交
结果；CPU 变更保持在 World，直到 bindless prepare 成功，再立即交给 instance table。
下游 dirty/revision 与历史失效先于可能失败的上传登记；历史失效保留到 prepare submit
确认。沿用 B10-e 的 queue-owned timeline 完成值，每次 sync 返回当前 wait，持久通知
不保存裸 semaphore。GPU queue、pass 顺序、shader ABI 与资源销毁责任不变。

未提交 command 的重录、instance pending uploads/history、设备错误退场分别交 B11-b/B12。
不清空这些状态来绕过断言，不引入全量扫描兜底；最终全局错误模型只在 B26/B27 提方案。

## 实施结果

- `RenderResourceSyncResult` 仍是私有变化载体，改由 RenderWorld 长期持有；三个身份集合
  使用已有 IndexSet 去重。RenderAssetSystem 在每个资源 owner 成功返回后立即写入该集合，
  不再把 material/mesh 通知只放在跨多个 owner 的局部结果中。
- `sync_assets` 返回本次 prepare 所需的 queue-owned wait；B10-e 的完成值推进、wait
  stage 和 semaphore 关闭前提保持。持久集合不保存 native handle，也不成为资源 owner。
- Runtime 在 cmd.begin/bindless 成功后才 take CPU 变更；RenderWorld 入口合并资源反向
  引用并调用 table.queue_changes，先于 sky binding/material 上传。初始 membership 和
  后续最终状态对账规则保持，RenderData 不反向成为 CPU 权威。
- instance result 先转成 scene/appearance revision、TLAS/emissive dirty，再执行 analytic
  同步/上传。只有通知已落实为这些持久状态后才清空资源变化集合；未使用材质不触发
  appearance/emissive 失效。
- sky binding changed 立即并入 pending history，资源/scene/light 变化也先保存历史
  失效；prepare 返回只是读取该提示，commit_uploaded_frame 全部成功后才清除。正常
  无变化帧不重复失效。sky state 自身已有 pending binding 标记，本轮不把它误报为
  独立必现故障；修复的是 binding 成功返回后到外层提交确认间的丢失窗口。

这几类状态表达不同交接边界：待处理身份、各 GPU 派生 owner 的失效状态和待交付历史
提示，不应压成同一个 dirty 值。没有新增通用事务/调度类、兼容入口或跨层依赖。
scene buffer/TLAS 内容与容量、提交失败后的资源处置仍按后续批次验证。

## 验证与限制

`.temp/code-design/B11-a2/{run.py,mocks.rs,probe.rs}` 编译实际 asset sync、RenderWorld
sync/prepare/commit 方法，以及 Runtime 从 poll_asset_loads 到 RenderWorld result 交付的
实际调用片段。底层资源、command、binding、instance table 和上传实现使用受控替身，
保持一次性通知消费；不将它描述为完整 Runtime 或真实 GPU 执行。

基准与修复后在 debug assertions 开/关下，20 类前后对照共 80 次，加上仅修复后才有的
持久通知去重检查 2 次，**共 82 次进程运行通过预期**：

- CPU 候选在 asset sync、cmd.begin、bindless、sky binding、material upload 异常后，
  修复版仍由 World/table 持有；旧版丢失。在重试中不重新注入输入也能交付同一身份。
- material 结果之后 mesh sync/取 wait 注入异常、mesh 发布之后取 wait 注入异常，以及资源同步后
  begin/bindless/material 失败：旧版通知丢失，修复版交付完整变化，重复身份只保留一次。
- instance 结果之后 analytic sync/upload 失败：修复版的 scene revision、TLAS revision
  和 emissive dirty 已登记，旧版尚未登记且无法由 no-op 自动重建。
- sky binding 返回后 material 失败、emissive/scene 上传失败、prepare 成功后尚未确认
  或 commit 中断：修复版保留历史失效；成功确认后下帧无重复提示。
- 正常通知、未使用材质、当前 wait 值与确认后无变化帧保持原语义。

graphics_wait 实际仅检查 queue 状态并读取缓存 signal，没有新的 driver 查询；上述
wait 注入验证交接边界，不表示正常 poll 成功后该 guard 实际会失败。

另在 `.temp/code-design/B11-a2/instance/` 适配新的候选接管接口，复跑 B11-a1 的真实
完整 table/RenderData 夹具：14 类 × 两版 × 两种断言，共 56 次通过。其旧基准仍为
`a75c7db5`，验证 B11-a1 修复及正常 generation、FIF/历史语义在当前实现继续成立；
这与上面的模拟 table 通知链验证分别记录，不混作完整应用恢复测试。

`cargo check --offline --locked -p truvis-render-runtime`、`-p truvis-app` 与
`git diff --check` 通过，无新增项目编译警告。未运行完整构建或 GPU/图像回归；B10-e
原真实 GPU 探针记录保留，本轮没有重跑，也不扩展它的证明范围。
