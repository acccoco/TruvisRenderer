## P1：零容量 hash map 会取模零（已修复）

`HashMapInsert` 和 `HashMapFind` 在计算 base slot 前直接使用 `hashMapData.capacity`。
虽然当前 `SharcTargets` 固定分配 `2^22` 个 entry，入口没有保证非零；capacity=0 会在
shader 中触发 `% 0`，不是可接受的失败返回。

两个入口现在先返回 `HASH_GRID_INVALID_CACHE_INDEX`；Find 同时把 bucket offset 置零。
正常容量、hash key、探测窗口和插入失败语义没有改变，Update/Resolve 的 invalid index
传播仍由 B20-b1 保持。没有新增 fallback buffer、动态容量或 CPU 兼容分支。

## 固定表示的支持域

- hash position 使用 17 个 payload bit 并按 17-bit sign extension 解码，单轴可表示
  `[-65536, 65535]` 的 grid coordinate；超出范围会截断高位并可能产生空间碰撞。
  level 使用 10 bit，编码范围由当前 clamp 为 `[1, 1023]`。这是缓存 key 的固定 ABI，
  不是可以在单点扩大位宽的局部修复。
- accumulation 每个颜色分量是 `uint32` 原子加，当前 `radianceScale=1000`；足够大的
  radiance 或大量并发样本会回绕。改成饱和 CAS、扩展 64-bit ABI 或动态缩放会改变保存量
  和性能契约，留给后续独立设计与 GPU 数值验收。
- resolved 的 radiance 和 sample count 都写入 fp16，打包上限 `65504`。sample count
  的逻辑位宽为 18，但 fp16 载体会在高计数时饱和；Resolve 的 frame window 限制不改变
  该表示上限。
- `SharcPackVoxelData`、`uint3` 转换和 hash 坐标计算没有完成非有限输入证明；主路径
  期望物理 radiance、正 scene scale 与有限 position。CPU 签名只断言 scale 有限且为正，
  不能声称 shader 对 NaN/Inf、负 radiance 或极端单位完全稳健。
- anti-firefly 仍沿用固定版本的 luminance heuristic，不能覆盖整数回绕、fp16 舍入或
  视角相关 cache bias；本批没有以参考实现替代数值验证。
