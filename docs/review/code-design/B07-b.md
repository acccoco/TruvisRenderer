## 问题与局部方案

- **P1，连续读取缺少新增访问范围的可见性。** 写 W → compute 读 R1 → fragment 读 R2，
  layout 相同时，needs_barrier 对 R1→R2 无条件返回 false。W→R1 的目标范围不含 R2，
  后续合并 read state 仅影响下一次写入，不能补上 R2 的依赖。读到读仅在目标 stage/access
  均已被来源范围包含时跳过；新增范围建立 dependency chain。位集比较保守，不展开
  ALL_COMMANDS 等复合语义，可能多插 barrier，不引入额外 writer/visibility registry。
- **P1，等状态写 export 被过滤。** epilogue 以 current_state != final_state 为前置，
  相同 storage read/write 状态不会生成 barrier。移除该过滤，复用 needs_barrier 判定。
  export 是对后续消费者声明访问状态，状态相等不能取代写后依赖。
- **P1，缺失 image 被静默跳过。** record_barriers 的 filter_map 会丢弃失效 registry 引用；
  execute 仍可运行后续 pass。录制前完整核验所有 imported image、可选 view 的存在/存活、
  image format 和 view 来源；不同 registry handle 指向同一 native image 也拒绝。
  录制 barrier 时使用明确 expect，不能把失效资源解释成“无需屏障”。
- **P1，image 同步模型和范围不一致。** graph 按整个 image 跟踪，但 GfxImageBarrier 默认
  仅 mip 0/layer 0。现有 allocated image 和 swapchain 均为单 mip/layer，未发现当前画面
  故障；外部 image/view 接口允许更宽范围时不成立。graph 转换显式使用全部 mip/layer，
  RHI 默认行为保留；不新增 subresource 调度。
- **P2，可选 view 被编码成 null。** import(None) 后 get_image_view_handle 返回 Some(null)，
  get_image_view/get_image_and_view 则内部 unwrap panic，与 Option 接口不符。内部查询表保留
  Option view，缺少 view 的查询返回 None；image-only pass 仍可正常工作。

## 设计与证据边界

依赖语义依据 [Vulkan Synchronization and Cache Control](https://docs.vulkan.org/spec/latest/chapters/synchronization.html)：
availability 与指定访问的 visibility 不同；执行依赖链需要相邻作用域相交。新增 read 范围的
屏障连接已完成的可见性操作，并为后续访问建立新的目标范围。该静态论证不替代 GPU validation。

修复位于既有 graph owner、RHI image barrier builder 和 image view metadata；view 保存的
source image handle 只标识借用关系，不转移销毁责任。graph 在录制前只读核验资源，不创建
或释放 native 对象。同步更新 graph README/design；不改变 shader ABI、queue ownership
或应用渲染模式。不同 graph/registry 同 key 的身份问题仍遵循 B06/B07-a 调用方契约。

GfxResourceAccess 在一次 execute 中必须稳定返回同一活资源；标准 registry 的共享借用
满足 CPU 集合稳定性，但不能替代 GPU 完成和 native owner 生命周期前置。view 重解释格式
可以不同于 image format，不据此拒绝合法 mutable-format view；native 创建合法性由 RHI
和驱动负责。graph 仍不自动核验 shader 实际访问、usage 全组合或扩展格式能力。

## 实施与验证

屏障修复已完成。`.temp/code-design/B07-b/run.py` 编译真实 graph 模块、SlotMap、foundation
handle 与 RHI barrier，命令/资源端采用替身；仅追加只读方法提取编译计划。
以 `8c637b21` 对照，在断言开/关下各执行 15 组：新增 stage/access/两者的连续读链、
相同/子集读取、只读 import 后新增范围、layout 变化、相同 write/read-write/空图写 export、
相同/新增范围 read export、layout export、WAW/WAR。新版通过；旧版能复现新增范围和
相同写 export 的屏障缺失。范围已经覆盖的重复读取仍不生成额外屏障。

屏障修复对应 `603145ea`；物理解析修复与交接位于本报告所在提交。

execute 先 resolve_images 完成全部核验，再录制 pass；record_barriers 不再静默过滤缺失
image。view 配对通过 RHI 保存的原始 source image 比较，内部查询表保留 Option view。
graph 转换调用 whole_image，以 REMAINING_MIP_LEVELS/REMAINING_ARRAY_LAYERS 表达完整
范围；默认 RHI barrier 的行为未改变。所有子资源的初始 layout 一致是导入前置。

`run.py resolve` 在断言开/关下各执行新旧 graph 的 18 组：有效配对、缺失 image/view、
已释放 image/view、错误来源、错误 image format、native alias、未使用但失效的导入、
image-only、四种无 view 查询、非零 view mip/layer 范围、depth、depth-stencil 与格式重解释。
新版八类非法导入均在命令计数为零时拒绝；四种 view 查询返回 None；其它合法路径通过。
捕获的真实 RHI barrier 描述覆盖全部 mip/layer，COLOR/DEPTH/DEPTH|STENCIL 均符合预期。
旧版允许非法导入继续录制，四种缺省 view 查询暴露 null 或 panic，范围固定为 1/1。

该夹具使用当前真实 GfxImageView 的创建/释放与来源 getter、实际 GfxImageBarrier；native
device/image 与 registry 内容为替身。新旧对照仅切换 graph 源码，RHI 元数据使用当前版；
验证了 source 记录与显式 view 释放，没有执行真实驱动。15 组屏障夹具在最终版复跑通过。
`cargo build --offline --locked -p truvis-render-graph` 与
`cargo check --offline --locked -p truvis-renderer` 通过；不新增仓库单元测试。
提交前空白检查通过；修改文件使用 stable rustfmt，nightly-only 配置被工具忽略。
