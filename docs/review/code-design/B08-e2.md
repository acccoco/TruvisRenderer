## 审阅证据（修复前）

- **P1，已复现：源 UV 被烘焙目标覆盖。** `bake_procedural_materials` 删除全部
  UV，再做 smart_project。Blender 5.2.1 的平面夹具以原 UV `(0.2, 0.7)` 驱动颜色：
  显式 UVMap 变黑，隐式 Texture Coordinate 改用新 UV；原 UV 数组均丢失。
  这也会影响未烘焙的贴图通道。应保留源 UV，给输出贴图显式绑定独立烘焙 UV。
- **P2，已复现：材质枚举与实际使用图脱节。** 遍历全部 data.materials，且选择第一个
  Principled。一个未使用、没有 Principled 的材质就会终止导出；未连到输出的节点可能
  被误改。应只处理 scene mesh 使用的材质，以实际输出连接定位 shader。
- **P2，已复现：隐式继承 bake 设置。** 源 scene 开启 Selected to Active 时，夹具
  报 `No valid selected objects`。应显式设置目标 UV、选择传递、cage 和法线空间。
- **P1，已复现：金属颜色被烘成黑色。** 常量 RGB `(0.2, 0.7, 0)` 经节点连接到
  Metallic=1 的 Base Color，旧 DIFFUSE pass 输出黑色。现在用临时 EMIT 输出求颜色
  表达式，finally 恢复原 Surface，再烘焙 Normal；两张图完成后才替换原输入。
- **P1，已复现：静态几何与节点变换使用不同帧。** prepare_meshes 使用当前帧，但
  Blender exporter `export.save` 默认 `frame_set(0)`；第 10 帧 shape key/armature
  已烘入 mesh 时，动画位置被重置为第 0 帧。本次显式 `export_current_frame=True`，
  与前序转换/烘焙的求值时刻一致，不新增动画能力。
- **P2，已复现并修复：validator 对结构类型缺少保护。** null collection、非 object
  的 PBR/attributes 会抛原生异常；bool 可作为 index；URI 解码宽松且无 scheme/query
  检查。它是外部资源与部分引用预检，不应被当作完整 glTF 或运行时能力验收。

冗余/过度抽象：host/worker 分工有进程与文件所有权依据，保留；无需新框架或统一 runtime
与 Python validator。严密性问题集中在 bake 输入/输出隔离与 validator 失败边界。

## 烘焙修复与验证

上述烘焙问题已修复。`SceneExporter.material_bsdf/bake_material` 承接局部职责；仅处理
使用中的材质，要求 Cycles/Eevee 同输出且直接连接 Principled。每对象独立图与 material，
共享 mesh 必要时复制。原版多对象 atlas 尚无充分证据判为重叠错误；单对象处理是隔离源
UV 与目标 UV 的实现选择，代价是更多材质/图像，不把此选择提升为跨系统不变量。

保留 source render UV 和数据，另建 bake UV，通过 bake 的 `uv_layer` 指定写入位置；
输出纹理和 NormalMap 显式指定 bake UV。选择传递、cage、清空、normal swizzle/space
均显式传入，不继承源文件设置。节点图的其它通道保留；不是任意材质图全通道烘焙。

Blender 5.2.1 / `9e2066aef7ef` 的 glTF exporter `primitive_extract.prepare_data`
调用 `mesh.calc_tangents()`，没有按 normalTexture UV 指定切线。因此存在烘焙材质时
整个输出省略可选 TANGENT，避免把源 UV 的基标作新 UV 的基；当前 Rust Reader 缺失时
发布零 tangent，shader 已有重建路径（B08-c2b）。未改 runtime、ABI、线程或 GPU 契约。

## 导出能力边界

prepare 保留 scene 的 mesh/camera/light；选择变化不限定导出范围。实际复合夹具包含
BLEND、COLOR_0 和必需 KHR_lights_punctual，均超出当前 Rust Reader 接受能力；灯光/
相机完整接入属于后续 scene/material 路径。这里不删除源属性来伪装运行时可用。其它程序
材质通道、组节点/混合 shader、不同 engine 的独立输出不属于本烘焙器的完整转换能力；
已有单材质槽限制保留。跨层材质支持和切线重建的画面验证仍交 B11/B15/B17，离线脚本
成功与 Rust/GPU 验收必须区分，模块 README 已明确说明。

## Validator 修复与验证

`validate` / `require_object` / `require_array` 在遍历前检查实际容器形状，入口要求
asset.version=2.0；JSON/UTF-8/NaN 错误转为 GltfValidationError。每次调用清空状态，
避免修复文件后复用实例仍携带上次错误。`check_index/check_uint` 排除 Python bool；
`validate_external_resources` 检查文件长度，`validate_references` 检查 view 声明边界，
并补齐 sparse/morph、skin/camera、animation 的核心引用。

`resolve_uri` 严格校验百分号，UTF-8 解码一次；只接受包内相对文件路径，拒绝 scheme/
authority、query/fragment、控制字符、Windows drive/反斜杠，以及经 resolve 后越界的
路径。encoded `%23` 是文件名字符；`%2520` 只得到字面的 `%20`，不会二次解码。文件
系统读取错误有明确诊断，仍不承诺与并发改名竞争下的文件沙箱。

新增确认问题：旧 validator 会接受过短 buffer / 越界 bufferView、漏检 sparse/morph/
skin/animation 引用，以及复用实例时保留旧 errors；均由新旧夹具复现，本次在原 owner
修复，没有另建 schema 框架。保留独立离线预检的理由：发布需要核对所有外部文件；runtime
则按自身支持能力加载并解释数据，二者目的不同。成功措辞改为 preflight，范围写入 README。

`.temp/code-design/B08-e2/validator_probe.py`：基准/修改版各 **119** 例。旧版 18 例泄漏
原生异常；新版为 9 个接受、110 个明确拒绝，没有原生异常，包含失败后复用成功的案例。
覆盖顶层/嵌套容器、bool/负数/越界引用、错误 UTF-8/JSON、坏百分号、中文/空格/encoded
文件名、query/scheme/绝对路径、实际目录 symlink 越界、buffer/view 范围和新增核心引用。
4 个实际 CLI 调用确认退出码 0/1、无 traceback；5 份真实 Blender 输出通过预检，包含
带未引用 skin、BLEND/COLOR_0/light 的复合场景，印证“预检通过不等于 runtime 支持”。
合成核心引用夹具只证明索引关系，不将其当作完整合法 glTF。Python 语法和空白检查通过。
最终整合后复跑 e1 宿主新旧共 30 例、实际 Blender host/worker 3 例，均通过；旧文件、
源文件和临时目录生命周期保证未回归。日志副本在本批 `host-regression.log`，实际运行
日志沿用 e1 的 real 目录。

预检有意不覆盖全部 JSON schema、accessor payload/stride、图片解码、node 无环性、
扩展内部引用或渲染能力；相关安全加载仍由 B08-c 的 Rust Reader 校验承担。没有新增
仓库单元测试，未运行 Rust 全构建或 Truvis GPU；只改离线 Python，不虚报运行时验收。
