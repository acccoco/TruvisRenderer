# B05-d2：Presenter 组合构造与 WSI 退场审阅

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `827171b0`，工作区干净。承接 [B05-d](B05-d.md)。
核对 SwapchainPresenter 全部方法、Runtime init/resize/present/destroy、registry image/view 释放，
以及 GfxDevice 扩展列表；沿直接调用检查 RenderLoop 最小化/恢复与帧安全点。

## 已确认问题与修复范围

- **P1，初始化组合资源缺少失败回收。** surface、swapchain、registry wrappers、逐个创建的
  acquire/render-complete semaphore 在最终 Self 构造前分散于局部变量；后续创建 panic 时，
  wrapper Drop 只诊断，不能代替显式释放。局部方案：先建立部分 Presenter owner，逐项填充；
  尚未提交 GPU 工作时失败，按依赖顺序显式释放，然后传播原错误。
- **P1，view 创建失败遗失已登记 image。** image handle 在 view 成功后才加入返回数组；
  任一 view 失败还会遗失之前成功的 image/view。局部方案：先记录登记 handle，并在 helper
  失败时回收本次登记集合；new/rebuild 共用此路径。registry 的内部异常安全留给 B06 专项审阅。
- **P1，重复窗口初始化会覆盖旧 owner。** Runtime 的一次性入口未验证 Presenter 为空；
  第二次成功创建会直接覆盖旧值。增加创建前断言，保留已有 owner；正常唯一调用链不变。
- **P1，重建失败保留无效 view 列表与未交付新链。** 旧 image 被取走释放后，旧 view handle
  仍留在字段；新链已创建而 helper 失败时，image/view 列表与新链不一致。局部方案：开始替换前
  验证没有在手 image，wait_idle 成功后清空旧 view 状态；记录剩余旧 image owner；新链未交付
  的失败路径回收新链并置 None，继续 fail-fast，不恢复已退役旧链，也不伪装成可渲染状态。
- **P1，跨代 present semaphore 复用与退场缺少完成证明。** rebuild 没有重建
  render_complete_semaphores，image 数增长会越界；数量不变也不能证明旧代 present 等待已结束。
  device.wait_idle 仅覆盖提交工作，不能独自保证 presentation 资源可销毁。当前 GfxDevice
  未启用 present_wait/present_id/swapchain_maintenance1，也未向 present 传递 completion fence。

第三项不适合只增减 vector：需确定设备能力基线、present 完成凭据和失败退场策略，交 B12/B27
集中复核，不在本轮隐式增加硬件要求、fallback 或无限保留旧资源。
依据：[Swapchain semaphore reuse](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html)、
[VkSwapchainPresentFenceInfoKHR](https://docs.vulkan.org/refpages/latest/refpages/source/VkSwapchainPresentFenceInfoKHR.html)。

## 架构预检

行为归现有 SwapchainPresenter/impl；复用 GfxResourceRegistry 显式释放和叶子 wrapper destroy。
owner 仍在 RenderThread，由 Runtime 持有；不增加跨帧 context 引用、Drop release、线程或依赖。
构造回收只处理未发布、未提交的新资源；旧代 WSI 完成条件不能由此推导。
同步模块 README；设计文档只记录真实偏差，不降低“完成使用后才能销毁”的约束。

## 初始化验证

`.temp/code-design/B05-d2/make_probe.py/run_probe.py` 抽取实际 Presenter struct、new、image/view
helper、destroy/release 方法及 FrameLabel；leaf/native/registry 用事件桩替代。新旧版在断言开关
下各执行 21 组，新版全部通过：3/4 张 image 成功、surface/swapchain 失败、逐张 image/view
失败、逐个 FIF/image semaphore 失败，以及 helper 单独失败回收。校验 registry 为空、创建释放
配对、view/image 先于 swapchain、surface 最后释放。旧版记录未回收对象；桩 Drop 记录遗留而不
abort，不能据此推导真实 debug unwind 可恢复。Runtime 一次性入口新增断言经编译与调用点复核。

该夹具不执行真实 registry 内部、驱动或 RenderLoop。registry 释放日志仍可能 panic，其内部
从 map 移出对象后再诊断的异常边界交 B06；本轮不宣称所有 panic、OOM abort 都能回收。
初始化修复通过 `cargo check --offline --locked -p truvis-render-runtime` 及 Renderer 编译检查，
对应 `96477bcc`；重建失败修复与交接位于本报告所在提交。

## 重建验证与剩余风险

`.temp/code-design/B05-d2/make_rebuild.py/run_rebuild.py` 抽取实际 rebuild 和上述构造/释放方法，
以 `96477bcc` 为基准。新旧版在断言开关下各执行 11 组：正常重建、image 数量变化、在手 image、
wait_idle 失败、native 新链失败、逐张 image/view 失败。新版验证在手状态在 wait 前拒绝，
wait 失败不修改旧字段；构造新链或 view 失败后没有旧 view 引用/新链，保持 resize 标记并传播错误。
mock 下后续显式销毁配对；旧版 view 失败仍留有新链和旧 view 列表。

最终 `cargo build --offline --locked -p truvis-gfx -p truvis-render-runtime` 与提交前空白检查通过。

此夹具替换 native/registry，旧链由 mock 模拟消费；不证明旧代 presentation 已完成。
数量变化用例明确记录新链 4 张 image、旧 semaphore 仍为 3 个，作为尚未修复的回归风险，
不是“重建整体通过”的证据。没有真实窗口/GPU、validation layer 或驱动错误注入验收。

RenderLoop::run 已在外层对零宽/高 park，恢复后经过 debounce/resize 再开始帧；该路径不会把
零尺寸传给 Presenter，也不执行 begin_frame。非零但 acquire 无 image 时才走空 timeline signal。
surface 在尺寸快照之后变化仍可能使新建失败；本轮不引入通用重试或设备失败恢复。
