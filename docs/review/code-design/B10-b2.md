## 发现与修复

| 优先级 / 状态 | 触发与影响 | 本轮处理 |
|---|---|---|
| P1，已修复 | 创建 timeline 失败时，局部 pool 没有显式回收。 | new 捕获 semaphore 构造失败，回收 pool 后传播原错误。 |
| P1，已修复 | index/staging/BLAS/scratch/command 创建、映射、录制或 metadata 准备中途失败，早先创建的 GPU 对象尚未进入 pending；普通 Rust Drop 不代替 native destroy。 | 局部 MeshUploadPreparation 逐项记录部分 owner；未提交异常先撤销 command，再分别释放 BLAS、scratch、stage、vertex/index。stage helper 返回前自行回收分配；叶子释放日志不能阻断余下回收。 |
| P1，已修复 | 原先 native submit 和 trace 后才 push pending；提交 panic 或提交后的诊断异常可使在飞对象失去 owner。 | 提交信息、Vec 与准备日志先完成；进入 submit 前完整移交 pending，设置 submission_uncertain，只有正常返回才清除。未确认结果时禁止后续 submit/update，关闭仍必须经过成功等待。 |
| P2，已修复 | 队列关闭检查在资源分配后，timeline 自增在录制后；debug 溢出会丢失局部 owner，关闭 overflow checks 时可能回绕。 | 存活、不确定提交、checked timeline 和 pending.try_reserve 均前置到 native 分配前；staging 数量 checked_mul。失败准备不消耗 timeline 值。 |

关键位置：MeshUploadPreparation::discard、MeshUploadQueue::new/submit_mesh_upload/update、
create_vertex_stage_buffer/create_index_stage_buffer。输入仍由 CPU registry 校验；不为错误
输入新增兼容转换。无 public API、shader ABI、线程、队列或 barrier 变化。

准备结构只服务 mesh 部分构造，不引入通用事务框架；复用共享上传队列在 B10-a2 的
“未提交撤销 / 进入提交后保留”边界。geometry 的两个叶子分别销毁，避免第一个叶子的
释放日志异常丢失第二个 owner。提交前 trace 明确改称 prepared，不能再作为已提交证据。

## 已核对的保留项

- **BLAS flags 没有本轮疑似的不一致。** 调用传入 empty，但 RHI `acceleration.rs` 的
  new_blas_for_build 在尺寸查询前 OR `PREFER_FAST_TRACE`，与 mesh build 录制相同。
  scratch 创建失败时 RHI 已回收 BLAS/backing，不需要调用方重复回收未返回对象。
- vertex/index wrapper 返回成功后只包装 GfxBuffer；底层 destroy 先释放 native owner 后
  trace。加速结构销毁先释放 AS handle，再释放 backing buffer。准备清理捕获的是这些
  已完成 native 释放后的诊断异常，不承诺 native release 自身失败仍可安全继续。
- 当前 mesh 使用 graphics queue 上的 copy + BLAS build，texture/sky 使用另一个上传
  owner。没有仅因相似字段就强行合并；是否需要统一机制留给完整 B10 与 B26 评估。
- 进入 GfxCommandQueue::submit 后，内部仍有提交描述 Vec 转换及 native unwrap。调用方
  保守保留资源，不推断该次提交一定发生或一定未发生。未 signal 的提交可能永远无法等到，
  由 B12/B27 处理外层退出策略；不实现 device-lost 恢复。

## 验证与边界

`.temp/code-design/B10-b2/{run.py,mocks.rs,main.rs}` 编译基准/当前实际 mesh 队列源码、
stage helper 和 metadata 方法，保留真实 ash/glam/log 依赖及 SoA 布局方法，移除 Tracy。
RHI、CPU 数据载体和 geometry 描述投影使用受控替身；logger 可注入 panic。

43 类场景分别在旧/新版本、debug assertions 与 overflow checks 同开/同关运行，
共 172 次进程运行全部满足各自预期：

- pool/timeline 构造，两个 submesh 的 vertex/index 与四个 staging 分配，mapped pointer、
  flush/map、geometry 描述、BLAS/scratch、command/begin/copy/barrier/build/end、提交信息、
  signal、trace 失败；metadata 越界仅作为回滚故障注入，不放宽 CPU 校验契约。
- 部分准备及 stage helper 失败叠加释放日志异常，检查原始错误保留、native 计数回到基线。
  已有 pending 不受第二次准备失败影响；新版清除注入后可再提交，timeline 连续。
- 提交入口与提交返回边界异常：新版保留 13 个模拟 native 对象（含 pool/semaphore），
  阻止后续上传/发布；等待超时不移出资源，模拟完成后关闭全部回收。旧版遗失任务 owner。
- 关闭后调用、u64::MAX 与 MAX-1：新版分配前拒绝非法状态，保留最后有效递增行为；旧版
  debug 自增 panic 丢资源，关闭溢出检查时回绕。未强制注入真实 allocator OOM。
- 正常、无 UV 和多 UV 场景：四次 copy 的 staging 字节逐项比较，handle/name、三角形
  面积/索引顺序与完成后资源回收通过；正常路径的 BLAS flags/geometry 数量亦检查。

旧版替身不启用 native wrapper 的 Drop 断言，以记录泄漏而非二次 panic 终止；因此测试
证明的是实际上层代码的 owner 转移，不是实际驱动行为。未执行 GPU/图像回归，不证明
同步可见性、真实设备恢复、OOM abort 或 native destroy 失败安全。完成后的释放日志及
consumer 异常仍在 B10-b3 范围，本轮准备回滚不能替代完成移交审阅。

`cargo check --offline --locked -p truvis-render-runtime`、
`cargo check --offline --locked -p truvis-app` 和 `git diff --check` 通过。
