## 已确认问题与局部方案

- **P1，重复物理资源被拆成独立状态。** RgResourceManager::register_image 无条件插入；
  同一 GfxImageHandle 导入两次后，compute_barriers 分别跟踪两个 RgImageHandle，无法
  连接它们的写读关系。当前模型没有 subresource 跟踪，不能把不同 view 当作独立 image。
  import 时拒绝同一物理 handle 的重复登记，调用方复用已有 graph handle；不静默复用
  并丢失第二次初始状态/semaphore。Realtime/Offline debug 路径已经显式复用主图 handle。
- **P1，未登记句柄静默穿过 compile。** compute_barriers 的 image_states.get 失败会跳过
  pass 声明；compute_epilogue_barriers 同样跳过不存在的 export，但仍收集 signal。
  add_pass 在 setup 完成后、发布 node 前校验所有句柄，export_image 在修改前校验。
  import 同时拒绝 null image 和 Some(null view)；None view 仍合法。
- **P1，同一 pass 的声明丢失访问范围。** 读取只保留第一次，写入以最后一次覆盖所有读取；
  例如同图 compute/fragment 读取，只会为 compute 建立依赖。合并同 layout 的 stage/access，
  冲突 layout 在 compile 拒绝；graph 不推断 pass 内部状态转换或命令顺序。
- **P1，通用 shader/host 写被当作只读。** RgImageState::WRITE_ACCESS 未包含 SHADER_WRITE
  与 HOST_WRITE；它们和 SHADER_STORAGE_WRITE 是不同位。自定义 initial/pass state 使用
  这些 mask 且 layout 不变时可漏 barrier。补齐核心 image 写类别；不添加新设备能力。
  依据：[Vulkan VkAccessFlagBits2](https://docs.vulkan.org/refpages/latest/refpages/source/VkAccessFlagBits2.html)。

## 边界与保留项

职责留在 RgResourceManager/RenderGraphBuilder/RgImageState；维持外部 native owner、线性
pass 顺序、当前 graph handle 类型和 shader ABI。没有新调度器、注册表或通用校验框架。
同一 pass 的合并只是外部依赖范围；内部写读依赖仍由 pass 正确录制，不证明 shader 访问
与声明一致。使用 Vulkan 扩展的新访问类别时仍须显式扩展状态分类并验证。

SlotMap 仅验证本表 generation，两个 graph 的首个 key 可能相同；membership 断言不能证明
graph 身份。handle 必须留在创建它的 graph，跨 graph branding 交 B26，不新增全局 ID。
null 检查也不能证明 native owner 存活或 view 属于 image；这些由 B07-b 核验。

尚需 B07-b 复核：连续读取对前序写可见性、同状态写 export 的 epilogue、barrier 默认仅
覆盖 mip 0/layer 0、record_barriers 缺失资源时 filter_map 静默跳过。B07-c 核对 semaphore
重复/冲突、重复执行的 initial state 前置与失败录制。RgImageSource 当前只有 Imported 分支，
没有直接行为故障；不在修复中夹带 enum/API 重构。Ctx 可访问未声明资源的问题交后续调用链。

## 实施与验证

登记校验已完成。`.temp/code-design/B07-a/run.py` 编译全部实际 graph 模块、真实 SlotMap、
foundation handle 与 RHI barrier；命令/资源查询端用替身，夹具仅调用构建和 compile。
追加只读观察方法读取内部 barrier 计划，不替换构建或状态推导。以 `449ed314` 对照，
断言开/关下各执行 10 组：null image/view、重复 image/不同 view、未登记 read/write/export、
null pass handle、合法 graph 和跨 graph 同 key。新版前八组均拒绝且没有半登记资源/节点；
旧版全部接受。合法路径可编译；跨 graph 同 key 在两版均不能识别，保留调用方契约。

登记修复对应 `deb0675a`；状态合并、写访问分类与交接在本报告所在提交。

状态修复复用既有 merge helper，将其命名扩展为 merge_states；移除写声明覆盖读取的
分支与重复 is_write 标记，直接依据合并后的 access 判断写入。同一 pass 读/写/混合声明
均保留全部访问；layout 冲突报出 pass 名称和 graph handle。RgImageState 补充 SHADER_WRITE
与 HOST_WRITE 分类，debug dump 同步显示这两类 mask。

`run.py state` 在同一真实 graph 编译夹具中、新旧版本及断言开关下各执行 17 组：多阶段
读取及反序、不同 read access、写入及反序、读写混合、read_write、同状态重复、三类 layout
冲突、generic shader/host 初始写、generic shader pass 写，以及基础 RAW/WAR/WAW。
新版全部满足期望：合并目标范围也成为后续写入的来源范围，冲突被拒绝，核心通用写不再
漏 barrier；旧版可复现声明丢失及对应 barrier 缺失。该夹具不覆盖跨 pass 连续读取的完整
可见性、epilogue 或真实 GPU 执行，不把基础用例通过写成全图同步正确。

`cargo build --offline --locked -p truvis-render-graph`、
`cargo check --offline --locked -p truvis-renderer` 通过。未运行 GPU/validation layer，
未新增仓库单元测试。未更改 pass 录制、资源创建、shader 或 queue submit。
最终重新通过 10 组登记夹具与 `git diff --check`；四个修改的 Rust 文件通过 stable rustfmt
检查，该工具忽略项目 nightly-only 配置，不宣称完整 nightly 格式验收。
