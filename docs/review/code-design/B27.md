# B27：全局严密性与验收计划

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准 `7f7dfc3d`，分支 `refactor`，本批开始时工作区干净。B27 是本清单的最终全局复核，
只输出风险合并、整改顺序和验收方案，不实施全局修改，也不把本报告建议当作已修复结论。

本批的“走通”首先是静态调用链；只有明确列出的夹具、构建或实机结果才算对应运行证据。
局部批次的 mock、CPU 数值检查和 `cargo check` 不能替代真实 Vulkan、窗口、SDK、WebView、
GPU 图像或性能验收。

冗余与过度抽象的结论沿用 [B26](B26.md)：保留有实际 owner/阶段语义的分层，仅收敛
已确认的兼容 API、闲置能力和重复协议形状。严密性方面，下面的 P1/P2 缺口仍然存在。

## 复核边界与长期不变量

复核入口是主清单第 4 节的八条链，以及 B00–B26 的交接。当前源码回查了：
`RenderLoop`/`RenderThread`/standalone/embedded host、`RenderRuntime`/Gfx/Presenter、
`AssetSystem`/`SceneStore`/RenderWorld、`RayCastService`、TruvisRenderer、Editor/MCP
controller 与 endpoint、`MaterialData`/RT shader 入口和 Streamline wrapper。没有重新运行
全部历史夹具，也没有覆盖第三方实现、所有 C++ include 或动态加载路径。

必须保持的边界：`app -> renderer -> engine`；CPU `GameWorld` 是唯一 scene 权威，GPU
`RenderWorld` 是派生状态；Vulkan 对象只在 RenderThread 创建/使用/销毁；Renderer 显式决定
pass 顺序；资源在正确的 GPU/WSI/SDK 完成凭据后释放；配置、frame input、提交确认和
temporal history 不互相冒充。任何整改都不能用全局单例、兼容层、自动 Drop 或中央注册表
替代这些 owner。

## 八条端到端链

### 1. 启动和中途失败：P1，静态确认，未闭合

`RenderThread::spawn` 在 OS 线程外层捕获 `RenderLoop::run` 的 panic，然后发布 finished、
调用 `on_finished` 并交给 `join`；正常情况下 `RenderLoop::shutdown` 才会 wait idle、调用
Renderer shutdown、销毁 Runtime。`init_after_window`、`run_frame` 和 Renderer hook 内部
没有一个统一的异常退场 guard。于是 init/frame/shutdown 中途 panic 时，join 证明线程结束，
不证明 Renderer、Runtime、Gfx 或 Streamline 已按顺序回收。embedded/standalone 随后 drop
child window，仍不能补回已跳过的 GPU/SDK cleanup。

最小整改方案是先定义失败状态机，而不是给每个 hook 套 `catch_unwind`：区分“尚未创建”、
“已知 GPU idle/完成”、“submit/wait 未知”、“SDK release 失败”和“诊断失败但资源状态已知”。
每个 owner 只实现自己能证明的退场动作；未知提交禁止按未提交对象释放，也禁止继续创建新工作。
外层最终交付结构化退出结果，保留首个业务错误和后续 cleanup 诊断。`panic=abort` 构建不
提供恢复证据，不能以 debug Drop 通过推断 release 安全。

验收需注入每个 init、resize、render、shutdown hook 的 panic/错误，分别覆盖未提交创建、
已提交但未完成、等待失败、SDK shutdown 返回错误和二次诊断异常；在真实 Vulkan debug
运行中检查 validation、资源计数、线程 join、child HWND 顺序。静态和 mock 只能作为前置证据。

### 2. 导入后删除或替换：P1/P2，部分闭合

`AssetSystem` 用 `SceneLoadHandle -> SceneImportHandle` 保存异步结果；`SceneImportRecord`
保留 status/error/data，纹理用 `AssetSource + color_space` 去重。RenderWorld 的 texture
completion 再检查 CPU scene membership，删除后的已提交上传只销毁 image，不重新 publish；
generational handle 和反向引用保护旧 GPU slot。该链能阻止典型晚到纹理复活。

未闭合的是记录保留期和内容身份：SceneImportRecord 当前直到 AssetSystem 销毁，没有明确
sample 消费、Automation 查询和删除后的租约；同路径新内容仍可能复用既有 Ready 纹理语义，
没有 source/content version 方案。SceneData、mesh/material、GPU slot 和 FIF history 不能
合并为一个 handle。

后续应由 AssetSystem owner 定义 import record 的查询租期、显式过期结果和 content generation；
热替换必须同时规定 texture、mesh/material、GPU upload、descriptor 和 temporal invalidation。
验收要覆盖晚到 texture/scene completion、删除后 query、同路径内容替换、重复导入、旧 handle
复用和 GPU 仍在读旧 image 的窗口；需真实异步/GPU completion 证据，不能只跑 CPU membership。

### 3. 编辑材质、灯光、环境：P1/P2，正常链闭合，超时语义未闭合

Editor/MCP request 经有界 endpoint 到 RenderThread Client；World 负责 mutation、版本和领域
校验，RenderWorld prepare 读取 CPU scene，Renderer 在实际 queue submit 返回后确认各自
material/light/sky/history 状态。`MaterialData::validate` 是 World 防线，App adapter 的
字段级 wire 校验是输入诊断；两层不能删除其一。环境导入的 CPU 接受只表示 identity 注册，
不表示 decode、upload 或画面完成。

HTTP/MCP 和 Editor 的 timeout/断连只放弃 reply，不能取消已经进入 RenderThread 的 CPU mutation；
notification 丢失依靠 query/version polling 恢复。Automation 现有通知通道没有生产/消费，
属于 B26 的删除候选，不应被当作一致性凭据。

整改应明确 response 的语义：accepted、committed-to-CPU、uploaded、submitted、visible
分别由谁报告；expected scene version 只保护 CPU mutation，不冒充 GPU 完成。对超时/断连场景
记录 mutation 是否执行、重查是否幂等。验收覆盖队列满、reply receiver drop、版本冲突、部分
实例化、晚到 import、材质非法 HDR/alpha、灯光 revision 饱和，并分别检查 CPU、GPU、history
确认点。

### 4. 相机和渲染模式变化：P1，正常确认点清楚，失败恢复未闭合

`RenderLoop::run_frame` 的顺序是 begin/input/update_phase（内部 acquire）/Renderer update/
sync extent/prepare/after_prepare/render/finish/present/end；无 acquired image 时跳过 prepare/render。
TruvisRenderer 的 DLSS、Realtime/Offline、ReSTIR、SHARC 和
Offline accumulation 各自保留 requested/effective、提交确认和 history；`render` 返回
false 时不应确认主视图提交。已有报告证明多套计数并非重复状态。

风险在于 render graph、SDK evaluate、submit 或 present 失败时，哪些 state 已被写入、哪些
候选可以重试、哪些资源处于 unknown。不能把所有 reset 合成一个 bool，也不能无条件清除旧
history 后继续渲染。应为每个消费者列出 prepare、record、submit returned、GPU complete 四个
边界，规定失败后保留/丢弃的 snapshot 和下一帧允许的动作。

验收需用相机跳变、模式切换、无 acquired image、DLSS/SHARC/ReSTIR 失败和 submit/wait 未知
组合，核对 jitter、view、reservoir、cache、sample count 及 CPU commit；GPU 时间线和固定
场景图像必须分别记录，不能只用状态夹具。

### 5. Resize、最小化和恢复：P1，WSI 代际退役仍未闭合

RenderThread 对尺寸使用 latest value、generation 和 debounce；零宽高暂缓新帧，恢复后再
重建。`rebuild_after_resized` 在 device idle 后释放旧 swapchain image/view 并创建新链，
但当前 `render_complete_semaphores` 不随 image 数量和 swapchain generation 一起重建。
普通 graphics idle 也不独立证明 presentation 已完成，旧代 semaphore/image 的复用和释放
凭据仍不足。

方案必须先选择能力基线和实际 completion 机制；同代 acquire 的 semaphore 复用条件与
旧代销毁凭据分别证明，不能把 present ID 本身或普通 device idle 当完成凭据。
优先评估支持 present fence 的明确设备基线，按 [B12-d](B12-d.md) 的固定证据重新核对实现时的规范。
Presenter 按代持有 swapchain、image/view 和 render-complete semaphore；acquire semaphore
继续按 FIF 管理，但须证明重建/退出时没有遗留已 signal 未 wait 的槽。零尺寸期间不创建新资源，
连续 resize 只保留最新请求，但不能丢失旧代退役状态。

验收要改变 image count、连续 resize、minimize/restore、suboptimal/out-of-date、transfer/
compute 写入和窗口跨屏 DPI；跑 validation、present 结果、semaphore 数量与 generation 对账。
当前 B25 的 DPI CPU/编译证据不替代实机多显示器和字体/child HWND 验收。

### 6. 拾取后场景变化：P2，CPU stale 防线存在，GPU/窗口验收缺失

`RayCastService` 在当前 RenderInstanceTable 快照上录制 query，submit/wait 成功后按 instance
slot、submesh index 转回 CPU handle；未知 slot、越界 submesh 会报错。此函数不再次查询
CPU World；删除与 slot 对账依赖 prepare 的同线程快照及随后 selection 校验。selection、
outline、gizmo 在 Renderer 中按当前 scene/view 更新，B24 已修复 GUI 裁剪边界。

仍需证明的是 readback slot、FIF、对象删除/复用与窗口坐标/DPI 的联合时序；静态转换成功不
证明 GPU hit 对应本帧展示的 scene。真实点击、resize、scene mutation、slot reuse 和无 hit
必须在同一窗口中检查，包含 Raster/RT 两种路径及高 DPI 坐标。

### 7. 队列满、超时和关闭：P1/P2，边界分散但可追踪

Editor/Automation request queue 有界并使用 `try_send`；RenderThread 每 tick 按预算消费，
shutdown 关闭 receiver 使 pending reply 失败。MCP HTTP 关闭有两秒 graceful drain，超时后
返回并销毁剩余连接任务。Desktop 特权命令容量为 1，失败和关闭会恢复 busy 状态。

RenderThread 输入队列仍是 crossbeam `unbounded`：窗口线程不等待，持续输入或最小化期间可
无限积累；退出请求只阻止后续发送，不能收回已有事件。该设计避免平台线程阻塞，但缺少预算、
丢弃策略和可观测计数。必须先决定输入事件的合并/有界容量/关键事件保留规则，再改控制层，
不能用通用队列替换不同业务的 request 语义。

验收覆盖输入洪峰、resize/DPI 洪峰、MCP incomplete body、HTTP 断连、队列满、RenderThread
提前 panic 和重复 shutdown；检查内存上限、最终事件顺序、mutation 是否执行及所有 join/HTTP
任务是否结束。两秒是实现配置，不是协议不变量。

### 8. 完整 shutdown：P1，顺序有文档，失败策略未闭合

正常路径是停止接收、RenderThread wait idle、Renderer shutdown、Runtime shutdown/destroy、
thread join，最后由 host 销毁 child Window；`Gfx::destroy` 先释放 command pool/allocator，
再 drop Streamline runtime，最后销毁 Vulkan core。这个顺序在成功路径成立。

`StreamlineRuntime::Drop` 对 `slShutdown` 失败只记录错误；`Gfx::destroy` 随后仍销毁 device/
instance。RenderLoop 异常时可能跳过其 shutdown；join/finished/on_finished 只描述线程
状态。未知 submit/wait、SDK release 失败、日志/Drop 二次 panic 和 device lost 不能共用“继续
销毁”策略。

最终方案要定义 shutdown result 的优先级和可验证门槛：已知完成才释放依赖资源；未知状态则
停止新工作、保留必要 native root 或终止进程并报告原因；SDK shutdown 错误不能静默变成成功。
每个层级返回首个错误和 cleanup 诊断，窗口 owner 只在 join/资源结果满足契约后销毁窗口。
验收需真实设备/validation、SDK 故障注入、device lost、线程 panic、重复 close、窗口事件
循环退出和进程结束，不能由 Rust mock 或静态析构顺序替代。

### 独立整改批次与回滚边界（仅提案）

建议先后关系为：失败状态分类 → 已知阶段的组合退场 → SDK/root 退场 → host 结果交接；
WSI 能力/代际回收在相应失败结果可表达后接入。数值/材质方案先决定语义，再并行组织
资产表达和 shader 消费，最后做全链图像验收；不能让 Runtime 依赖具体 Renderer 模型。

| 可独立评审的行为批次 | 同一提交必须包含的范围与回滚要求 |
|---|---|
| 提交/等待结果分类 | immediate、upload、raycast 与 Runtime 的实际调用方同时迁移，禁止旧 catch 继续把 unknown 当未提交；可先保持正常路径行为，独立编译和故障验证 |
| 组合 init/shutdown 退场 | Loop/Renderer/Runtime 的已创建 owner 前缀及退出结果一起迁移；回滚时保留上批底层结果分类，不留下只迁一侧的接口 |
| SDK 关闭结果与 root 门槛 | C API/Rust runtime/Gfx 一起传递 shutdown 成败；不能先删 Drop 再等待后续补释放，unknown 不自动重试 |
| WSI 代际完成 | 设备能力、Presenter/Swapchain、image/semaphore retire 和关闭分支同批；不单独提交 vector 扩容作为完整修复 |
| 平台退出/失败通知 | RenderThread/host/App 的结果消费同批；保留 parent/child owner 和锁外 join，实际窗口验收后接受 |
| 输入预算与 loader 预算 | 两个独立行为批次，各定义自己的顺序/容量/关闭语义；不共用一个全局 scheduler。每批可单独撤回，不改变另一链的预算 |
| CPU 版本耗尽 / import record 生命周期 / content version | 三个独立行为批次；content version 若涉及 ABI，所有 GPU 消费者和 history 同批；保留可重复导入和 stale ID 的明确响应 |
| 层能量与复合 lobe / 法线与资产表达 / 数值支持域 | 先设计再按完整契约分批，每批包含相关 eval/sample/PDF、消费者与验收资产；不能只改 shader 某一公式。无法拆成完整契约时继续拆设计和证据，不为了两次 commit 硬塞全部模型 |
| B26 清理候选 | 路径、native 工具、schema、通知、submit 投影分别独立；每个执行批最多两次提交，不要求整个整改方案两次完成 |

这里列的是下一阶段的审批/实施单元，不创建新兼容分支、永久测试框架或未调用的能力。
当前任务按用户要求到方案为止。
