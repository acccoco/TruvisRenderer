完整阅读四个 crate 的源码和 manifest：`truvis-path`（含 build.rs）、`truvis-utils`、`truvis-logs`、`truvis-fetch-res`（含 CLI）；核对 `paths.toml`、`resources.toml`、`.cargo/config.toml`、`just fetch-res`、工具/日志/External README。按 B00、架构入口及分层约束检查直接消费点；未展开渲染算法、native 部署或 shader 构建器实现。

| owner | 当前责任与保留理由 |
|---|---|
| `TruvisPath` | build.rs 嵌入工作区根，首次读取 `paths.toml` 后 OnceLock 缓存。它是本地开发工作区定位器，不承诺复制 exe 后独立运行；路径映射是受信配置，不能当作不可信路径沙箱。 |
| `PathUtils` | OS executable/UTF-16/词法路径操作；不决定业务目录和导入失败策略。 |
| `ConfigUtils` | 只解析字符串 bool，默认值和日志由 Renderer DLSS、Streamline config 两个调用者决定；小型无状态类型不构成已确认的过度抽象。 |
| `TruvisLogger` | 安装一次全局 logger；路径由调用方传入，线程上下文按线程缓存；命名、保留策略、formatter、tee writer 分别承担局部契约，没有 Renderer 依赖。 |
| `GitHubResourceFetcher` | 持有 HTTP client 和独占缓存目录；选择、下载、checkout、解压与发布在同步工具进程内完成，不管理应用 DLL 部署或 GPU 生命周期。名称虽带 GitHub，当前已支持其它 HTTP 来源；命名本身不是故障。 |

日志保留优先保留当前打开文件，只按符合命名协议的同 exe 分组清理；失败写 stderr，文件打开失败退回 console。此降级是可观测性策略，不是协议兼容设施。未进行多进程日志竞争或磁盘故障验收。

## 确认问题与处置

### P1：ZIP 未限制条目路径，且失败后可能发布半成品

- 证据：`resource_fetcher.rs:200–218` 在解压前删除旧目标；`:583–622` 将 ZIP `file.name()` 直接 join 并写到正式目录。已有 7z 的 `archive_relative_path` 与 staging 没被 ZIP 复用。
- 触发与复现：本地 ZIP 的 `../escape.txt` 写到资源目标之外；第二条记录 CRC 损坏时返回错误，但旧资源已删除、第一条文件已落盘；关闭 force 后再次执行因目录存在返回成功。所有夹具与越界写入均限制在 `.temp/code-design/B01/before/` 内，没有接触真实资源或联网。
- 反证与限制：不是说当前仓库配置的远端 ZIP 已损坏或包含越界条目；已证明的是合法下载/失败恢复路径缺少保证。
- 本批修复：在现有 fetcher 中让 ZIP/7z 共用路径预检和 staging 发布，完整解压后才替换目标；不增加 archive trait 或通用事务框架。发布阶段失败仍报错，不宣称跨卷 rename、进程崩溃或磁盘故障下原子回滚。
- 状态：已修复并验证（本地 archive 夹具）。当前 `process_archive`/`extract_zip` 共用发布与路径规则，ZIP 直接从文件读取，不再复制整个 archive 到内存。有效 ZIP、9 类非法路径拒绝、CRC 失败保留旧目标、首次失败后再次执行仍失败、staging 清理均通过；7z 正常与截断包回归通过。未验证发布阶段的 OS 故障回滚。

### P2：Git branch 更新没有消费本次 fetch 的提交

- 证据：`resource_fetcher.rs:334–339` fetch origin 后执行 `checkout --force <git_ref>`；已有本地同名 branch 不会因 fetch 自动前移。`resources.toml` 的 pbrt-v4 使用 `master`，是实际配置允许的场景。
- 本地 Git 夹具复现：远端 source 前进一个提交后，再执行 fetch 返回成功，checkout HEAD 仍是旧提交；tag 与完整 commit 的原路径正常。仅通过该子进程的 Git URL 映射访问 `.temp` 中的本地仓库，没有修改真实 external checkout 或全局 Git 配置。
- 本批修复：fetch 指定 ref，detach checkout `FETCH_HEAD`，保留 `.git` 与现有 submodule 同步责任。不改变上游版本配置；固定 commit/tag 不随 branch 更新。
- 状态：已修复并验证（本地 Git 夹具）。`checkout_git_ref` 对移动 branch、固定 tag、固定 commit 均得到预期 HEAD。未对公网认证、代理、submodule 下载执行运行验证，未刷新真实 external 资源。

### P2：词法归一化错误抵消连续父路径

- 证据：`truvis-path/src/path_utils.rs:44–63` 对每个 `ParentDir` 都尝试 pop，没有区分已有普通段与已有 `..`。
- 调用实际公共方法复现：`../../asset`、`../a/../../asset` 均变为 `asset`；Windows 根路径还残留根之上的 `..`。
- 反证：全仓搜索未发现该方法的当前业务调用者，因此不能声称已经造成运行中资产加载错误。它是已存在 public helper 的契约错误。
- 本批修复：只有普通段可被抵消；相对路径保留未解析父段，绝对根不向上越过。不访问文件系统、不引入 canonicalize 或存在性要求。
- 状态：已修复并验证（调用实际公共 API）。7 个输入覆盖连续父路径、普通段抵消、盘符绝对/相对路径和 UNC 根；相对 `../../asset` 保持两个父段，`C:/a/../../asset` 停在 `C:/asset`。没有新增业务调用者。

### P2：CLI 在缺失资源配置时返回成功

- 证据：`truvis-fetch-res/src/bin/fetch_res.rs:30–38` 缺失 `resources.toml` 时只打印提示后 `Ok(())`；调用脚本无法通过退出码判断资源准备失败。
- 本批修复：直接调用已有 `ResourceConfig::from_file` 链，让读取错误传播到 CLI；成功提示只在整个批次成功后打印。
- 状态：已修复并验证（静态错误传播与 CLI 编译）。`main` 直接以 `?` 传播读取/批次错误；help 正常，`--all unexpected` 返回失败。未移动真实根配置复现缺失配置分支，不将参数检查结果当成该分支运行验证。

### P2：四项直接依赖已无用途

- 证据：fetch-res 源码不再使用 manifest 中的 `env_logger`、`anstyle`、`chrono`；日志由 `truvis-logs` 拥有。path 源码不使用 manifest 中的 `anyhow`。逐项检查源码、build.rs 和 targets 后未找到用途。
- 本批修复：仅移除四项直接依赖，更新 lock 中对应 package dependency 列表；日志 crate 继续持有需要的第三方依赖。不能据此声称会减少四个实际编译的第三方 crate。
- 状态：已修复并验证。四 crate 编译通过，lock 仅移除对应四项 dependency 记录，`cargo metadata --offline --locked --no-deps` 通过；没有升级第三方版本或移除日志 crate 自身需要的依赖。

## 未决项与保留判断

- **资源缓存身份，交 B02 定向补查**：`fetch_resource` 以 URL 最后路径段作为缓存名，不记录 URL、内容 hash 或完成标记；两个来源的相同 basename 会共用缓存，缓存写入中断也可能被下次复用。当前 `resources.toml` 未发现同名下载项冲突，External README 明确 NR hash 仅人工核验。需要单独走通缓存身份、刷新、磁盘写失败和构建消费方的失效契约，再决定配置与缓存格式，不在本批临时补一套兼容读取器。
- **Git/普通文件发布**：现有 Git clone/force refresh 与普通 file copy 仍不具备完整 staging/rollback 契约；本批只修复已复现的 branch 版本错误和 archive 失败发布。B02 继续检查断网、磁盘错误、clone/submodule 部分失败，不把本批 ZIP/7z 保证推广到所有资源类型。
- **兼容别名与 API 面，交 B26**：`TruvisPath` 的 `*_path`/`*_path_str` 明确是历史兼容入口，部分仍被 Engine/Renderer/App/CXX 使用，另有无调用的 `save_to_file` 和路径便利方法。存在收敛空间；清理 public API 需同步各消费点并验证相关 crate，不以本批的局部编译宣称完成全仓移除。
- **分层路径事实，交 B02**：`paths.toml` 的 `target` 与 `.cargo/config.toml` 的 `target-dir` 当前都为 `build`，CMake/Nushell 也消费构建目录。Rust 路径配置不能自动改变 Cargo/CMake 输出；修改映射时必须核对整条构建链。
- 未发现把 Renderer 业务状态下沉到基础工具的证据；日志的局部类型各有责任，不仅凭类型多就合并；配置字符串解析由两处真实调用复用。下载器重复的 archive 发布规则需要收敛，尚无依据建立插件式下载框架。
