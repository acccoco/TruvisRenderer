## 发现与本批处置

### HTTP 缓存身份和完成性不足（P1，已修复并验证）

`fetch_resource` 以 URL 最后一段命名缓存，只凭 exists 复用。两个来源的 `tool.bin` 会共用字节；缓存被截断/改写后仍可发布。查询字符串也被当成 Windows 文件名，而非来源标识。下载读取整个响应到 Vec，内存随包大小增长。

本批修复：以完整 URL 的 SHA-256 区分缓存目录，完整流式写入 payload 并生成内容摘要后才发布；复用前校验摘要。旧 basename 缓存无法证明来源，不兼容读取、不自动删除，首次使用新布局需要重新下载。摘要只检查本地缓存一致性，不提供上游签名或预期版本认证。

目标也不能只凭存在跳过：同一目标切换到另一份已经缓存的 URL 时，原实现不更新。为已成功发布的 HTTP 目标记录来源/内容身份；仅当目标存在且该记录匹配才跳过。手工改写已发布目录的内容不纳入资源工具的持续完整性监控，需 force_overwrite。

### 文件、archive 和 Git 发布失败会损失旧目标（P1，已修复并验证）

file 刷新先删除旧目标再 copy；archive 完成解压后先删除旧目录再 rename，跨卷或 rename 失败时旧版本丢失。Git force/非 checkout 转换先删除旧目标；clone 或指定 ref/submodule 后续失败会留下半成品。普通 Git 更新在原目录 checkout 后再更新 submodule，同样可暴露混合状态。

本批修复：复用下载器内一个完整发布流程，staging/previous 与目标位于同一父目录；新内容准备完后才移走旧目标，发布失败恢复 previous，下次运行恢复中断的发布。仅在所有 Git ref/submodule 就绪后发布 checkout；普通更新拒绝主仓库和已初始化 submodule 的本地改动、未跟踪/ignored 文件与 stash，force 明确允许替换。使用现有 checkout 的独立对象副本准备更新，保留 `.git`，不引入运行时 Git 兼容层。Git clone 在已确定的父目录使用相对名称，避免 Windows verbatim 路径参数不被 Git 接受。

这仍是受工具管理的参考 checkout：本地 Git config/额外 refs 不承诺继承，不应作为开发工作区。整体准备增加磁盘空间需求，submodule 可能重新下载。整个资源批次不是事务；新目标发布后清理 previous 失败会返回错误，完整新目标与 previous 保留供重试，不宣称失败必然回到旧版本。第二次 rename 失败会尝试回滚；若回滚也被 OS 阻止则保留 previous 并报告路径。恢复要求下载器独占缓存和发布目录，断电持久性不保证。

路径名规则复用已有 Windows archive 校验并应用于所有资源类型；保留 `.truvis-` 内部 staging/previous 命名空间。删除/移动前验证实际目标仍在配置父目录下；不以真实 external 资源作为临时链接实验目标。

## 路径与职责结论

- `paths.toml` 是 Rust 路径查询配置，不是 Cargo/CMake/Nushell 的自动配置生成器。当前 `dirs.target`、`.cargo/config.toml:target-dir`、CMake presets/generated include 路径都指向 `build`，当前值一致。
- `run-cargo-bin.nu` 明确使用 `config/vulkan`；CMake 还使用 `external` 的固定 SDK 路径。修改 paths.toml 不会同步这些入口。全局统一属于 B26/B27，只记录联动点，不实施最终全局修改。
- ResourceConfig 的 target_dir 以 workspace 根解析，CLI 使用 workspace 的 resources.toml；调用公共 fetch_resource 的绝对目录由调用方负责。资源部署与 Shader/native 构建分别拥有状态，fetcher 不复制 DLL 到应用输出。
- HTTP 缓存与目标发布需要共享身份/失败语义；Git 有 ref/submodule 和本地编辑约束，不应伪装成普通下载流。保留现有 fetcher 与具体格式方法，不建立下载插件框架。
