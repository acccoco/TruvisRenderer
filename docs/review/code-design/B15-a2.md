基准 `57f4444f`，`refactor`，初始工作区干净。承接 B15-a1，读取 OfflineAccumState、
Realtime 历史判定与 compute/present 返回、Truvis render 提交出口、FrameLabel/FrameTiming，

## 已确认问题与方案

- **P2，状态先于提交**：Offline take_next_sample_batch 在 graph 构造阶段增加计数；
  Realtime restir_last_* 同样在录制/提交前推进。后续 compile/record/submit 失败时，
  CPU 状态声称的样本/历史并未获得提交证据。当前失败终止整个 RenderThread，未发现
  正常重试路径，不能声称已复现下一帧 GPU 画面污染。
  两个子系统返回各自不可复制、字段私有的提交候选，Truvis 局部枚举保存对应模式；
  仅在 queue submit 正常返回后交回 owner。失败或放弃建图丢弃候选，不新增持久 pending。
- **P2，极值行为不成立**：Offline saturating_add 会反复使用最大 sample index；
  shader 的 uint accum_frames+1 可回绕为零。应在创建整个 batch 前检查总数可表示，
  耗尽明确停止，不重置历史或重复随机种子。Realtime previous_frame_label 取模前对
  完整 frame_id 加 COUNT-1，同样可先溢出，应从现有有界 frame_label 求前一个 slot。

架构预检：提交候选分别归 Offline/Realtime，不含 GPU handle，不改变 RenderGraph，
不增加异步或通用事务设施。子系统状态改为普通可变字段；Truvis 在既有提交出口确认。
CPU 签名变化的失效仍可立即 reset；“提交正常返回”不等同于 GPU 执行完成或 present
成功。未知 submit 结果继续沿现有终止策略，不能通过丢弃候选宣称 GPU 已回滚。
两组分别处理提交边界和计数极值，文档随组同步。

## 计数边界验证

第二组为本报告所在提交。Offline 在 batch 总数 checked_add 成功后才生成样本，
因此最后的 sample index 至多为 MAX-1，shader 的整数分母加一可表示；正好达到
MAX 的 batch 可完成，下一个 batch 明确停止。剩余额度不足整个 batch 时不截短或
自动 reset。Realtime 直接在 FrameLabel 的三个 slot 内计算前一槽，不对完整 frame_id
做加法。不改变随机序列、running average 或 ReSTIR 条件。

`run-limits.py` 编译实际计数方法、FrameLabel 和 previous_frame_label 表达式，以
`3bf92d98` 对照；正常/最后一个/最后一批/耗尽/跨界/dispatch clamp，以及 0、1、2、
完整轮转、MAX-2、MAX-1、MAX 帧号，共 13 类 × 前后版本 × 两配置，**52 次通过**。
旧版饱和 batch 可产生 shader 分母零；旧完整帧号加法在 debug 溢出，在 release 边界
会选错槽。新版异常 batch 不修改计数，合法样本分母非零，前一槽与模运算参考一致。
这是当前 Windows 64 位 CPU 极值实验，不是长时间 GPU 渲染实验。

两组共 132 次状态/顺序/边界检查通过；第二组 App 编译、空白检查和 `just shader`
通过（编译 1、复用 30，并完成两个 shader binding build）。shader 只纠正历史 owner
和计数前置注释，无算法或 ABI 变化。未新增源码单元测试，未做实际窗口/GPU 验收。
