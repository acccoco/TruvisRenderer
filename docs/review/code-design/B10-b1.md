## 发现与局部修复

- **P2，已确认：查询错误被当作未完成。** update 的 `unwrap_or(0)` 吞掉设备查询错误，
  mesh 保持 pending 且调用方无法观察失败。改为带 mesh 上下文的 expect，遵循现有 RHI
  fail-fast 契约；查询失败前不弹出任务、不释放资源、不发布 mesh。
- **P1，已确认：关闭等待失败丢失同步 owner。** 原实现先 take semaphore/pool 再等待，
  timeout 或设备错误触发 unwind 后字段为空，pending 仍保留，再次 shutdown 会错误标记
  destroyed。现在先借用 semaphore 等待，成功后才取走 owner；失败保留任务及同步资源。

实现仍位于现有 MeshUploadQueue，无新增公共 API、抽象层、线程或依赖。保持显式销毁、
FIFO、graphics queue 上的 copy/BLAS build、现有 barrier 和完成后发布契约；同步模块
README。本轮没有修改 shader ABI、BLAS 构建参数或跨 queue 同步。

资源保留使局部状态不因失败等待而失真，不表示 device-lost 可恢复。若上层继续 unwind，
既有 Drop 断言仍可能终止进程；外层失败退出策略继续由 B12/B27 核对。

## 验证

临时夹具位于 `.temp/code-design/B10-b1/{run.py,mocks.rs,main.rs}`。从基准和工作区抽取
实际 Submitted/Finished 类型、队列字段、update、shutdown 与 Drop，移除未覆盖的构造、
上传准备、metadata 方法及 Tracy/doc 注释后独立编译；RHI 替身记录资源释放并注入失败。

新旧版本分别在 debug assertions/overflow checks 同开、同关时运行 10 类场景：零/部分/
全部完成、查询错误、单/多 mesh 等待超时、超时后直接再次关闭、等待设备错误、空队列关闭、
重复关闭。每个 mesh 包含两个 geometry、两个 staging、scratch、BLAS 和 CPU metadata。

旧版复现吞查询错误、等待失败丢失 semaphore/pool、再次关闭误标销毁并残留 pending；新版
失败不移出 owner、不提前释放，模拟完成后可继续 update 或再次 shutdown。正常路径保留
FIFO、handle/name/triangle metadata，command、staging、scratch、geometry、BLAS 与同步
owner 各释放一次。40 次进程运行全部满足各自基准/修复预期。

叶子 Drop 替身记录丢失而不触发二次 panic，以便观察旧状态；这不模拟实际驱动或 GPU。
`cargo check --offline --locked -p truvis-app`（覆盖 Runtime/Renderer 调用链）及
`git diff --check` 通过。未运行实际 GPU、完整构建或图像回归；夹具不覆盖释放日志异常、
准备/提交失败、GPU 内存可见性或真实设备恢复。
