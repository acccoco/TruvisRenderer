## FIF 回收与确认

- **P1，已修复：满容量时可回收 slot 仍被视作耗尽。** 回收原来在 upload，而分配位于
  更早的 sync_scene。1024 个 slot 用满后，旧 slot 已退役满三帧，新注册仍会在回收前
  panic。现在 begin_frame 先回收到期空 slot，保留 saturating_sub 与 COUNT 门槛。
  Runtime 在调用此入口之前已经成功等待当前 FIF timeline；没有提前释放仍在飞的 slot。
- **P2，已修复：确认记录没有完整绑定当前 payload。** update/unregister 撤销对应 slot
  的旧 pending_commits；每次 upload 先清空当前 FIF 的旧记录，flush/copy/barrier 全部
  完成后才交付本次 written_slots。失败保留 dirty，commit 仍只在 submit 成功后推进。
  这避免放弃命令后重录时混入旧记录，也避免旧确认清除新 dirty 或删除后的退役计时。

当前 Runtime 的正常顺序是 sync→upload→cmd.end→queue.submit→commit，不会在一次
正常录制/确认之间编辑材质。本批故障夹具显式覆盖“放弃记录后重新进入”和晚到旧确认，
后者是局部状态约束检查，不伪装成当前正常帧已观察到的故障。Runtime 遇到原生提交错误
仍 fail-fast；没有实现设备恢复或允许重用失败 command，外层恢复契约继续 B12。

扩展夹具在两种断言配置下比较基准和最终实现，共 **24 类 / 96 次进程运行**通过。
除前述 13 类，还覆盖满容量回收、放弃记录后删除/修改/slot 复用、失败重录、flush/copy/
barrier 故障、非连续 copy 区间、三 FIF 独立确认与回收日志异常。关键断言包括：

- frame 10 删除的 slot 在 9/10/12 不回收、13 回收；1024 容量下新身份重新取得 slot 0，
  旧版仍错误耗尽。回收日志异常后重试不会把同一 slot 重复加入 free list。
- 旧版放弃上传后删除，后续空上传的 commit 会移除退役计时，slot 永久不回 free list；
  新版保留计时并正常回收。修改/复用后的过期确认不能清除当前 payload 的 dirty。
- 失败重录的新 pending 集合为空；dirty 保持。重新录制并确认 A 后为 `[false,true,true]`，
  B/C 分别确认后移出 dirty；录制成功但尚未 submit/commit 时不提前清除。
- dirty slots 0/1/3 合并为两个复制区间，offset/size 与实际 PbrMaterial 大小一致；stage
  中的 roughness 是当前 prepared 值，未改 slot 不进入 copy 区间。

## 保留项与下一步

名称变化只更新 CPU snapshot，不制造 appearance/dirty。未 ready BaseColor 使用诊断
fallback，其余槽使用 null 中性输入；texture 0/1 revision 推进使实际依赖重新准备。
当前 emissive table 的权重只使用 emissive_factor + class.emissive_radiance，未依赖
纹理采样统计，因此不因 texture ready 自动新增 emissive-table 重建；appearance 通知
仍推进画面历史失效。此结论是当前实现边界，不代表纹理发光采样权重最优。

SlotDirtyInfo 同时保存 active dirty 和已注销计时，slot_to_handle 的 Some/None 区分两种
状态；现有边界足以表达契约，本轮没有为它新增版本注册表或通用状态机。检查当前
MaterialData 字段后，same_render_projection 覆盖除 name 外全部渲染字段；GPU 投影保留
class/coverage、alpha、IOR、emission、纹理 sampler/UV transform，不改变渲染算法。

通知只保留到 material sync 成功返回；RenderAssetSystem 后续 mesh 同步或 Runtime 后续
prepare 若失败，返回结果可能仍随外层栈丢失。按 B10-b3 交接继续 B11/B12，不以本轮
证明端到端事务。真实 GPU 同步继续 B10-e。
