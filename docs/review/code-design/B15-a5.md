## 修复前发现

- PerFrameImageSet 用 array.map 连续创建 raw image；后续 image 创建失败时，已经
  创建的 wrapper 只会 Drop，不能显式回收。初始 transition 完成后，任一 view 创建
  失败也没有回收已注册的一组 image/view。SingleImageTarget 存在同类 view 失败缺口。
  这两种阶段分别满足“从未提交”与“已等待完成”，本批局部修复，保留原始异常。
- Realtime debug_image_source 只检查非空 handle。无 TLAS 时 compute 只清理 source、
  main color 与 RR hit-distance，其他 GBuffer/guides 未写；DLSS Off 时 output 未写。
  这些 handle 仍能被 Resolve debug preview 采样，不能把资源存在等同于本帧内容有效。
  本批在现有 source 选择入口限制可借出的图像，不引入内容版本注册表。

## 边界

构造 rollback 复用 GfxImage::destroy 与 target.destroy，view-before-image 保持由
registry 负责。错误只在原有 owner 内处理，不在 Drop 调 Vulkan；image/transition/view
顺序、queue 数量、线程与依赖方向不变。原始创建错误优先于 rollback 的日志诊断。
transition 内的 submit/wait 失败仍不能推断可释放，保持单独的未闭合范围。

首组 `d8f5f271`：PerFrameImageSet 在分配阶段逐项保存 raw image，失败显式销毁
已成功项；两类 target 在 transition 返回后保存注册 handle，view 创建失败时回收本组。
rollback 诊断被捕获，继续传播原始创建错误。没有改变 transition 异常的处理方式。

`.temp/code-design/B15-a5/run-create.py` 编译实际 shared target 源码，替换底层 Vulkan/
registry 为 CPU 记录器：逐个 image/view 失败、清理也失败、正常与 transition 异常，
15 类 × 前后版本 × debug 开关，**60 次通过**。已知安全阶段回收数量匹配且 registry
不残留本次资源，原错身份保留；模拟 transition 异常没有触发新增回收。替身不模拟
真实 raw GfxImage::Drop 的 debug 二次 panic，不能用此证明未知提交路径可正常 unwind。

复用 B15-a3 的 GBuffer 正常生命周期记录器，4 次执行的前后事件序列仍一致；
App 编译和空白检查通过。未做 GPU 验收，未新增源码单元测试。

第二组为本报告所在提交：无 TLAS 仅允许 source、main color 与已清理的 RR hit-distance
用于 preview；DLSS output 还须 feature active 且本次 evaluate 返回 Succeeded。
TruvisRenderer 在 compute graph 录制后把已有 DlssEvaluation 传给 present 编排，
不新增跨帧状态。无效 source 返回 None，Resolve 仍显示主画面，不采样该 debug 图。
成功返回不是 GPU 完成凭据；两个 graph 仍按原顺序一起提交。

`run-debug.py` 编译实际 debug_image_source，替换资源 accessor：12 个 ID（含未知 ID）、
有/无 TLAS、Off/SR/RR、NotRun/Succeeded/Failed 和两个 FIF slot 的组合，另检查所有
有效 ID 的空 image/空 view；每次 **454 项**，前后版本、debug 开关四次执行通过。
确认旧版仅检查 handle，新版按生产路径筛选，并保留剩余 source 的 image/view/状态映射。
这里验证 CPU 选择策略，不验证实际 shader 写满、SDK 输出内容或图像质量。App 编译和
空白检查通过；未改 shader/ABI，未做 GPU 验收。
