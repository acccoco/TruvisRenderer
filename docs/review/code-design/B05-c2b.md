# B05-c2b：compute/RT pass 组合 owner

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `5f6758a2`，工作区干净。读取 ComputePass、RealtimeRtPass、OfflineRtPass、
RayCastPass 的构造/销毁、两个已有 RT pipeline owner、shader cache 与 SBT 构造。复核实际 compute
参数来自生成的 Renderer ABI；本轮不改 shader 结构、group 表、set 顺序、递归深度或 GPU 提交时序。

## 局部发现与处置

- **P1，ComputePass 组合创建失败。** shader、local descriptor layout、pipeline layout 未及时归属
  可回收 owner，后续失败导致遗漏释放或 debug 二次 panic。现在空 pass 记录每个成功步骤，临时 shader
  在 catch 外持有，始终显式释放；失败沿 pass.destroy 回收其余资源，再传播错误。
- **P1，compute 参数字节不受约束。** `P: Sized` 配合 BytesConvert 允许读取含未初始化 padding 的
  类型。改用已有 bytemuck::NoUninit/bytes_of，不改变生成 ABI。构造前检查 push constant 大小可用 u32
  表示、非零且四字节对齐，并先检查 local set 紧接全局 set；设备 limits 仍是 device/pass 契约。
- **P1，RT pass 与 SBT 的交付缺口。** 三个 RT 构造都先创建多个资源再组装 owner；naming、后续 shader、
  SBT 或 SHARC 分配失败会遗漏前置资源。SBT 在 buffer 创建后查询 handle/flush 失败也可能二次 panic，
  现在已创建资源在 catch 外分阶段持有，native pipeline 失败输出先过滤 null 回收；临时 shader cache
  始终释放，失败时显式销毁 pipeline/layout、descriptor pool/layout 与 SBT，再传播错误。
  SBT 自身失败复用 GfxBuffer 的 crate 内无日志 release，避免内部 Drop 阻断外层回收。
- **P2，销毁日志可阻断剩余资源释放。** 正常 RT destroy 将 SBT buffer 放在其他 native 对象之后释放；
  buffer 的日志发生在 native release 之后。构造回滚时同样最后释放 SBT，并捕获该诊断 panic，保留
  原构造错误。没有改变提交后必须等待 GPU 完成的前置条件。

## 边界与设计判断

保持 Runtime 私有 raycast 与 Renderer realtime/offline 的 owner 分离，复用现有销毁路径，不新建跨层
pipeline 工厂、通用回滚注册表或隐式 Drop release。已有阶段枚举/group 映射有明确索引用途；算法与
递归深度是否合适交对应 RT pass 批次，本轮不凭创建成功推断渲染正确。

Graphics/compute/RT 的 native 创建存在重复投影，但各 owner 的 descriptor、SBT 和资源交付责任不同。
是否统一 RHI pipeline 类型只列 B26/B27 设计建议，不在这里实施最终全局改造。
