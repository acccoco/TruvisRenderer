> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准 `44b11dc4`，`refactor`，初始工作区干净。扫描 WinitInputAdapter、两种 host 事件
转发、RenderThreadControl、Loop drain/暂停、Truvis 与两个 sample 的 on_input、
InputManager 和 ImGui 输入消费；沿 camera/GUI 的焦点与尺寸消费定位剩余职责。

## 确认的问题与修复分组

1. **P1，退出期间输入接收/排空缺少边界**：control 同时持有 Sender/Receiver，
   RenderThread 退出后只要窗口仍持有 control，channel 不会自然断开；send_input
   的“断开后忽略”注释与真实存活关系不符。Loop 的 while-let drain 不再读退出标记，
   大积压/持续输入可推迟退出。send_input 在已观察到 exit 后不入队，Loop 在排空
   期间和进入 resize/frame 前重查 exit；不改变正常 FIFO，不加固定队列容量或丢事件策略。
2. **P1，sample 被 UI 捕获的松键丢失**：Triangle/ShaderToy 把所有 captured 输入
   拦在 InputManager 外；相机先收到按下、UI 随后捕获松开时，按下状态会保留。对齐
   已有 Truvis 策略，坐标与按键释放仍更新状态，按下/滚轮意图保持由 UI 消费。

架构预检：退出输入边界归现有 RenderThreadControl/RenderLoop；sample 消费策略归
各自 Renderer::on_input，复用现有 InputManager 与 ImGui capture，不增加新线程、
输入协议、通用调度器或 public API。资源、GPU/WSI 与窗口销毁前置不变。

## 退出边界验证

首组修复在 `4c63f69b`；sample 修复在本报告所在提交。`.temp/code-design/B13-c/run-exit.py`
提取实际 Control/Loop，Control 使用真实 crossbeam_channel，并以实际 OS producer
在已收到退出后投递 1000 次；Loop 使用可注入退出的控制桩和模拟 Renderer/Runtime。
FIFO、退出后投递、resize/恢复、退出后 resize、尺寸打包边界、线程生产六类，以及
正常帧、drain 末尾退出、持续到达期间退出、初始退出四类，前后两版本/两配置共
**40 次通过**。原无限 drain 用桩在第 100 次读取主动停止，确认尚未进入 shutdown；
新版在第 3 次读取发布退出后关闭。它不证明现实输入速率能无限占满队列。

退出前已越过检查的并发 send 仍可能被接收；退出后不保证队列绝对为空，也不增加
同步锁。最小化期间无界积累仍未修复，不能将退出检查宣称为完整背压。

首组 `cargo check --offline --locked -p truvis-app` 与空白检查通过。

## 平台范围与保留项

- WinitInputAdapter 使用物理键位、物理像素，滚轮取竖直分量；Focused/Resized 进入
  输入模型。host 对 resize 只经 publish_resize 投递一次，避免适配器再重复发送。
  这些是当前 demo 输入范围，不是完整键盘文本/IME/水平滚动后端。
- 当前 Truvis 在 Focused(false)/Resized 时取消 gizmo/输入/待选中请求，ImGui 失焦
  释放鼠标状态；两个 sample 的 InputManager 也重置持续输入。CameraController
  内部手势/待查询状态与 ImGui 键盘输入的完整契约留给 B14/B24，不能仅凭 InputManager
  reset 推导所有 Renderer 子状态已清空。
  后续 [B14-a](B14-a.md) 已补齐 Truvis 的 Controller 取消传播并验证旧查询不会回放；
  相机其余契约及 ImGui 键盘范围仍分别留给 B14/B24。
- 零尺寸时 Loop 外层 park，不 begin_frame；恢复时经过 generation/debounce/resize。
  尺寸回到原值仍增加 generation，并发送 Resized 取消旧交互。窗口的尺寸、generation
  和事件队列不是一个原子快照，不能把 debounce 时间当作事件已消费的同步证明；
  当前正常路径顺序已读，极端线程调度下的发布一致性仍需 B14/B27 联合验证。
- **P2，已确认结构风险**：运行/最小化期间 channel 与 Loop Vec 仍无界；持续输入或
  resize 会积累，恢复时批量消费。不能任意 drop release/focus/resize，否则可能产生
  stuck key 或旧交互。是否合并 MouseMoved、是否给每帧消费预算、暂停时如何取消手势，
  应结合 B14/B24/B25 消费者在 B27 提方案；本次仅停止退出后的生产与长 drain。
- **P2，范围缺口**：ScaleFactorChanged 在 standalone 忽略、embedded 仅日志，输入
  模型没有 DPI 事件；GUI hidpi_factor/ui_scale 只在初始化设置，跨屏时不能由 Resized
  自动证明字体/布局缩放已更新。交 B24/B25 结合字体 atlas/资源重建验证，不临时增加
  未贯通消费者的新事件。Win32 child style 设置的返回值检查也尚不完整，需 native
  失败场景验收，不能用 Rust Result<Ok> 代替 Win32 API 成功。
- 两种 host 都忽略 device_event，窗口事件承担现有交互。B13-a 的 finished/payload、
  B13-b 的窗口错误返回仍成立；B12 的 Vulkan/WSI 完成分类和 parent 消息泵等待缺口
  未因本批输入修复消失。真实窗口最小化/恢复、跨屏、native 错误及 GPU 退场未验收。
