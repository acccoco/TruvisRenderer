## 边界与契约

`RayCastService` 由 Runtime 持有，只在 `after_prepare` 的窄 Ctx 中同步提交 RT、等待 fence、读回并通过 `RenderInstanceTable` 转成 CPU identity。Renderer 在 `update` 产生点击 ray，在 `after_prepare` 消费当前 prepare 快照；`TruvisRenderer::commit_selection` 是网格/灯光选择的共同入口，Gizmo 和 LightOverlay 只持有 Renderer 侧交互快照。Selection outline 由 render-passes 消费当前选择和 runtime 的 raster view，Viewport overlay 负责图标、Gizmo 和坐标几何，ImGui 最后叠加。

输入捕获由 Renderer 组合：ImGui 可消费按下意图，但松键、移动和活动 Gizmo 仍进入 `InputManager`，以闭合拖动状态。灯光在网格 raycast 前命中；Gizmo 在点击选择和灯光 hover 前消费。Raycast shader 的 instance slot/submesh/primitive 结果由 CPU 表映射，不能直接把 GPU slot 当作持久选择身份。

## 发现

### UI scissor 裁剪没有做交集（P2；已确认）

- 证据：`renderer/renderer-imgui/src/backend/gui_pass.rs:241-256` 先把 `clip_x/clip_y` 截到 0，却用未截断前的 `clip_w/clip_h` 生成 `vk::Rect2D`；`canvas_extent` 只用于 render area（174-177），没有参与 scissor 上界裁剪。
- 触发与影响：当 ImGui draw command 的 clip rect 部分或全部位于 viewport 左/上边界外时，起点被改为 0 而宽高仍按原区间计算，实际 scissor 会向右/下扩大；反向或空的 clip rect 还可能留下零宽/零高的无意义 draw。自定义绘制、窗口拖出边界或高 DPI 缩放下会出现错误覆盖，边界值可能触发 Vulkan validation。
- 保留现状的理由/反证：普通 ImGui 窗口通常已经在 `DrawData` 中裁剪到 display rect，因此主界面未必稳定重现；这只能降低触发频率，不能证明 backend 对合法 draw data 的裁剪契约完整。
- 最小建议：在 `GuiPass::draw` 内将缩放后的 clip rect 与 `[0, canvas_extent]` 求交，空交集跳过 command；保留现有 display-space 投影、纹理缓存和 pass owner，不引入公共裁剪 helper。
- 验证：已运行 `.temp/code-design/B24-a/probe.ps1`：12 组正常、部分越界、空交集、反向矩形和零尺寸 canvas 用例通过；探针同时确认修复前部分越界矩形为 `30x20`、修复后为 `20x15`。执行 `cargo check --offline --locked -p renderer-imgui` 与 `git diff --check`，均通过。仍需真实 Vulkan validation 和窗口拖拽/DPI 运行验收。
- 处置：本批修复。

### 拾取与选择链路未发现充分证据的问题（保留现状；静态已确认）

- `RayCastService::validate_rays`、TLAS 缺失 Miss、容量增长、HOST/RT/TRANSFER/HOST 屏障和 fence 等失败出口闭合；`convert_raw_hits` 对 slot、submesh 和无效 hit 做边界检查。
- `TruvisRenderer::after_prepare` 只消费 prepare 后快照；选择变化会清除旧 click probe 和 Gizmo，World 删除后下一次 update 会清理 stale selection。selection outline 在 raster view 不可用时跳过绘制，不伪造 CPU identity。
- LightOverlay 使用投影快照并按近处优先命中；Gizmo 拖动拥有活动 target，窗口失焦、resize 或 apply 失败会统一取消。当前没有足够证据证明需要改变优先级或拆分 owner。

### 冗余与过度抽象结论

本批未确认同一拾取规则在 Runtime、Renderer 和 pass 中重复维护：Runtime 负责 GPU hit→CPU identity，Renderer 负责交互选择，pass 只消费快照；这些转换的变化原因不同。`ImGuiSubsystem`/`GuiPass`/`GuiMesh` 的分层分别承担 context、GPU pipeline 和 per-FIF buffer 生命周期，当前调用链中有明确 owner，未因薄包装而建议合并。UI 配置归一化、输入/DPI 与渲染控件仍交 B24-b，避免跨子批作全局判断。
