# B12-b2：Runtime 正常关闭与失败边界

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准 `dd9f60a4`，分支 `refactor`，工作区干净。核对 Runtime destroy、Presenter release、
RayCastService、GameWorld/AssetSystem、RenderWorld/RenderAssetSystem/GpuMeshStore、FIF
buffer、CmdAllocator、registry、binding/sampler/descriptor 和 Gfx root 的直接关闭路径。

确认两个局部问题：raycast/FIF/registry 已释放后传播的诊断异常，会跳过 Runtime 后续
清理；Gfx 在 allocator 回收后、SDK/root 关闭前记录日志，日志 panic 会阻断后续显式
销毁。已分两次提交分别处理，保持正常 owner 顺序、公共 API 与 GPU 安全点不变。

不能统一 catch 后继续：device idle 失败尚未证明 GPU 完成；Presenter 可能部分释放
且缺 WSI 完成凭据；RenderWorld/asset 的消费式 destroy 可能混合等待失败与释放诊断，
外层无法可靠区分。CmdAllocator 的 free 仍有释放前校验；SDK Drop 失败也没有可用的
完成证明。上述路径保持直接传播，不拿“日志应可继续”替代完成状态。


## Runtime 的已完成释放诊断（P1，已确认并局部修复）

`23048498` 只捕获 `RayCastService::destroy_mut`、`PerFrameGpuData::destroy`
和 `GfxResourceRegistry::destroy` 的异常；当前实现均先尝试各自完整集合，再传播释放
诊断。继续原顺序清理之后，才报告首个已保存诊断。其它关闭调用保持直接传播，后续
未分类/安全点错误优先于先前诊断，不能因早期日志失败掩盖后续等待失败。

没有引入通用 shutdown trait、错误分类框架或生命周期注册表。构造 rollback 与正常
关闭仍分开：前者只适用于启动已知安全段，后者必须先 wait_idle，还涉及 Presenter、
CPU producer 和运行后的上传队列。保持 Gfx 最后销毁的设计要求，未降低 WSI 完成前置。

`.temp/code-design/B12-b2/run-runtime.py` 提取实际 Runtime struct/new/destroy 及启动
候选，子 owner 采用受控账本。23 类 × 前后两版本 × debug/overflow 两配置，**92 次
通过**：正常有/无 Presenter，逐项关闭故障，三种诊断组合，早期诊断与后续等待/校验/
root 错误组合。逐条比对释放顺序、停止位置、剩余资源及异常优先级；只在允许继续的
诊断路径确认 root 最后回收。mock 不实现 WSI、真实 GPU 等待或 native Drop/abort。

`cargo check --offline --locked -p truvis-app` 通过。Presenter 部分关闭、RenderWorld
消费式 destroy 的异常分类、Runtime 外层 panic 退场仍有缺口，不因为这 92 次夹具通过
而宣称整个 shutdown 安全。Gfx 日志断点见下。


## Gfx 关闭前日志（P1，已确认并修复）

`Gfx::destroy` 原来释放内部 pool/allocator 后先执行一条 info 日志，再 drop Streamline
和销毁 core。日志后端 panic 会跳过显式 core.destroy；SDK 可能随 unwind Drop，但不能
据此推导 device/instance 已释放。该日志没有资源职责，保留它不值得引入额外异常边界。

本报告所在提交直接移除这条日志，保留已有中文顺序约束。正常关闭顺序不变，没有
新增 catch/恢复层；Streamline 自身 Drop/关闭失败仍直接传播，不强行销毁其依赖 root。
这是 B05-a2 待办中 Gfx 外层日志断点的局部闭合，不涵盖 SDK 内部日志或关闭行为。

`run-root.py` 提取实际 Gfx::destroy，以模拟 pool/allocator/core/Streamline Drop 和可失败
日志后端记录顺序。无 SDK、正常 SDK、外层日志失败、SDK 关闭失败四类 × 前后两版本 ×
两配置，**16 次通过**。旧日志失败未调用 core.destroy；新版不调用该日志并正常到达
core。模拟 SDK 失败时仍停在 core 之前。夹具不加载真实 Streamline/Vulkan，不证明 SDK
内部 CPU/GPU 工作已经结束；也未测试同时二次 panic 的 native 退场。

两次提交各通过 App 编译，最终空白检查通过。未新增源码单元测试或运行 GPU/窗口验收。

## 保留、偏差与交接

B12-b 已完成约定范围扫描与两批可证明前置的局部修复，仍保留以下明确偏差：

- **B12-c/B27**：RenderWorld 构造/消费式 destroy 同时覆盖普通诊断与未知 submit/等待
  失败，没有足够完成信息供 Runtime 决定是否释放共享依赖与 root；b1 不在该边界回滚，
  b2 不捕获后继续。统一 owner/错误契约的最终调整只提方案，不能补一个泛化 catch。
- **B12-d/B27**：Presenter 仍缺 presentation 完成凭据，跨代 semaphore 数量/回收问题
  按 B05-d2 继续复核；device idle 不单独证明 WSI 完成。其 release 中任一 image 诊断
  也可能留下后续对象，Runtime 不能假设 Presenter 已完全释放。
- **B16/B27**：SDK 内部关闭失败、日志/Drop 与 native root 顺序需结合 Streamline 实际
  版本和线程/GPU 行为审阅；本次只移除 Gfx 外层一个诊断调用。
- **B12-c/B13**：RenderThread catch 位于整个 Loop 之外，init/frame/shutdown 任一 panic
  都可能绕过后续显式关闭；finished 标志不等同于 Vulkan/window 所有权已完成回收。

没有发现需要合并 Runtime/RenderWorld/Presenter owner 的证据；它们的同步前置不同，
释放顺序可相似但不可互换。下一批 **B12-c：固定帧阶段、提交确认与失败出口**，从
RenderLoop::run_frame、Runtime::prepare/finish_rendered_frame/present/end_frame 入手。
