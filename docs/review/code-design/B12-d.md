## 状态与尺寸交接

- FrameTiming 是时间与 frame id 的唯一 owner；begin_frame 一次采样 delta/total，
  软件限帧基于同一 last_frame_started_at。暂停后 delta 包含暂停时间，超间隔不补帧；
  消费者是否需限制大 delta 属于其策略，不能在 Runtime 擅自截断时间。
- `render_runtime.rs:504` sync_render_extent 仅在尺寸改变时 wait idle，再发布 state
  和 ResizeCtx；等待失败不发布新尺寸。`handle_resize:574` 则先重建 Presenter，再
  同步输出尺寸；Truvis on_resize 先重新派生 DLSS 尺寸，再重建各 target。
- UpdateCtx setter 只写 requested；init/resize setter 同时写 requested 和 render_extent，
  保证随后创建的资源读取新尺寸。该差异对应合法阶段，不合并为一个通用 resize helper。
  Offline 复制 FrameRenderState 后设 native 只影响自己的 target，不另立 Runtime 权威。
- history_invalidated 在 begin_frame 清零。外层 resize 的提示不跨帧保存，当前
  Truvis on_resize 直接重置 DLSS/view_accum/ReSTIR；update 后内部尺寸变化则可被同帧
  after_prepare 观察。没有发现需要另增持久 pending reset 的证据；新 Renderer 必须
  遵守 resize 回调契约，具体 temporal 消费仍交 B14–B16。

## Ctx：真实限制与未封闭能力

| Ctx | 当前限制 | 仍靠契约的部分 |
|---|---|---|
| Update | 可变 CPU World、只读 frame/timing；GPU 能力字段私有，只公开 wait_idle | set_render_extent 没有完整尺寸校验 |
| RayCast | 字段 crate-private，只公开 history 提示与同步查询 | 同步查询的成本/时机由 Renderer 选择 |
| Render/Record | 无可变 CPU World、无 concrete RenderWorld/asset owner；record 是借用视图 | device/resource/queue 仍可分配或提交；“只读”不是权限沙箱 |
| Init/Resize | 生命周期短借用，持有创建/重建所需 owner | 公开可变 FrameRenderState 可绕过 setter，输出尺寸/格式约束不是类型强制 |
| Shutdown | root 存活期间借用 owner；Loop 调用前 idle | 部分 owner 的失败完成状态不明确，不能任意 catch 后继续 |

**P2，API 约束缺口，待跨层复核**：未来调用者可以提交零尺寸或直接改写 init/resize
state；当前唯一生产 setter 调用者 TruvisDlssState 会过滤零 optimal extent，底层
GfxImage 也检查非零，因此未证明现有正常配置会触发此问题。只给 setter 加 assert
无法封闭 public 可变字段；应在 B14–B16 复核消费者后，于 B27 提出权限与验证方案。
不创建新 extent 类型、通用 phase trait 或兼容入口。

ImGui::prepare_render_data 确实经 SubsystemRenderCtx 的 resource_ctx 扩容、写入当前
FIF mesh，queue_ctx 也用于标记。因此不能机械删除这些字段。SubsystemRenderCtx 不含
selection raster 能力，有明确裁剪作用；其 timeline 等字段有进一步收窄空间，须结合
B14 的子系统消费图判断。没有仅凭薄包装/单实现 trait 就合并现有 owner。
后续 [B14-c](B14-c.md) 已核对全部消费者并移除未用的 device/device-info/timeline
转发；保留 ImGui 实际使用的 resource/queue，不改变上述 Vulkan 能力边界结论。

## WSI：已复核但仍未闭合（P1）

`swapchain_presenter.rs:355` 重建 images/views，却不重建 render_complete_semaphores；
新链 image 数增加会在对应 image index 越界，数量相同仍沿用旧代 semaphore。当前
Presenter 与 `f8a9d633` 的文件内容完全相同；B05-d2 的 count-change 证据仍适用，
本批未将旧夹具当作新运行结果，也未重复构造/重建实验。

当前 GfxDevice::basic_device_exts、feature chain 没有 maintenance1/present_wait/
present_id；GfxSwapchain::present_image 没有 completion fence，new 消费并销毁旧链。
因此 B05-d2 的缺口仍在：image 数量、旧代 semaphore 和旧 swapchain 的退役要一起
处理，不能只 resize vector 或用 device idle 宣称 presentation 已完成。

2026-10-29 核对 [Khronos semaphore reuse 指南](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html)：
同代按 image 分配并等待再次 acquire 的同步，可建立该 image 的 present semaphore
复用条件；普通 submit 完成与 WaitIdle 不独立证明 presentation 资源可关闭，maintenance1
的 present fence 提供相应凭据。当前 acquire wait 固定 COLOR_ATTACHMENT_OUTPUT；
已检查 resolve/triangle/shader-toy 当前首个 present 写入均为 color attachment，未证实
这些消费者 stage 不匹配。未来改为 transfer/compute 写入时须重审该固定入口。

**交 B27，仅方案**：统一决定扩展能力基线与设备选择、present fence 交付/等待和错误
是否入队的分类、按代持有 image/semaphore、旧代与 shutdown 回收门槛；结合 B13 的
窗口退场确认。不能在未定能力基线时加 fallback、无限保留旧链或只做数组补丁。
