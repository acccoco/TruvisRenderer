## 发现与修复

- **P2，已修复**：六个叶子与三 FIF 的组合构造无回滚；关闭首个释放诊断异常阻断后续
  清理。现保留已完成候选，失败撤销本 pair、其余 pair 和先前 FIF；关闭逐项回收后
  再传播首个异常。回滚日志异常不覆盖原始分配失败。
- **P2，已修复**：扩容原先先销毁旧 frame 再创建新 frame。分配失败会留下旧容量与
  已销毁字段；下一次数据量缩回旧容量时，容量判断通过，但映射访问失败。现先创建
  完整候选，再替换字段和回收旧资源；分配失败保留旧 frame，旧资源回收诊断异常
  保留已接管的新 frame。其它 FIF 不受替换影响。
- **P2，随扩容修复**：next_power_of_two 的溢出在 Release 可回绕为 0，随后 max(1)
  产生过小容量。现由 frame owner 的 checked 计算在创建/释放前拒绝不可表示请求，
  移除原独立 free function。

新 frame 持有 needs_full_upload，直到当前 FIF 的 pending version 提交确认才清除。
它独立于内容 version，不能把“容量已足够/内容 version 相同”视为新地址已有内容。
完整 upload 录制后才登记 pending；map/flush/copy/barrier 中断不提前确认。

复用既有候选/显式回收模式，保留 frame 六个叶子的共同生命周期，不新增跨 owner
框架。扩容要求当前 FIF 无在飞使用，关闭要求所有 FIF idle。不改变公共 API、Shader
ABI、估计器算法、GPU 提交顺序、屏障或等待策略；扩容仍整体替换三组 buffer。
版本确认仍要求 Runtime 同帧 upload→submit→commit，不支持旧 pending 跨重新 prepare
后再确认。外层组合收尾、部分 command 处置和未知提交退场分别交 B11-e/B12。

## 验证

临时夹具位于 `.temp/code-design/B11-d2a/`，编译实际 emissive 模块、RenderData、resolver
接口、FrameLabel 与生成 GPU 类型；替换 buffer/command 和材质叶子。不新增源码单元测试。

- `run-life.py`：正常、18 个分配失败点、18 个关闭异常点、17 个构造回滚伴随释放异常，
  共 54 类；基准与生命周期修复分别启用/关闭 debug assertions 和 overflow checks，
  **216 次通过**。核对遗漏数量、原始分配错误与重复关闭。mock 不实现 native Drop
  abort，不能据此推断旧实现支持真实异常恢复。
- `run-grow.py`：以生命周期提交为基准，32 类前后共同场景、修复后额外一类独立上传
  标记检查，两种 assertions/overflow 配置，共 **130 次通过**。覆盖正常/空/增长、
  六次分配、六个旧叶子释放、三次 stage 回滚、容量溢出、失败后缩小请求，以及三组
  buffer 的 map/flush/copy/barrier 故障。核对存活 owner、容量、地址、实际复制字节、
  pending/uploaded version、其它 FIF 不变及确认前后标记；无 pending 的其它 FIF 确认
  不清除当前 frame 标记。
- 资源夹具直接设置三种 CPU 表的长度和 version，以隔离容量/录制路径；使用零化 GPU
  record，不验证 emissive 几何或 alias 算法。独立上传标记场景通过私有 frame 替换
  保持相同内容 version，确认新地址仍会完整上传，不当作正常 Scene 输入复现。
- 两个提交均通过 `cargo check --offline --locked -p truvis-app`（包含 Runtime）；
  `git diff --check` 通过。未运行 GPU/RT/raster 回归。受控局部重试只证明 owner/CPU
  状态，不代表失败 command 可以直接重新提交。
