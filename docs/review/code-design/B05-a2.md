# B05-a2：Gfx root 构造失败与显式回收

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `12c4d6f4`，工作区干净。接续 B05-a 的 root 分阶段创建、VMA Drop 和 Entry/Rc/Pin 注释偏差。范围仅包括 root 构造与直接子构造，不改变渲染策略、GPU 队列数量或整个 RHI 的所有权模型。

## 局部修复与约束

1. **VMA 隐式 Drop 已修复。** vk-mem 0.4.0 的 Allocator::drop 会释放 native allocator；外层 Drop 仅写断言不能阻止字段继续析构。inner 改为 Option<ManuallyDrop<Allocator>>，仅显式 destroy 取出并执行唯一释放。误用时保留 Debug 诊断，无断言构建泄漏；不以 native 自动回收掩盖 owner 遗漏。Pin 注释改为真实的 native root/loader 存活前置。
2. **分阶段构造回收已完成局部修复。** GfxCoreInit 保存未交付的 instance/device/messenger，Gfx 保存已交付的 core/pool/allocator。catch_unwind 后显式逆序回收并 resume 原始 panic；不吞错误，不在正常 wrapper Drop 中调用 Vulkan。Gfx 在回收内部 child 后、device/instance 前结束其 Streamline runtime，正常与失败路径遵循同一根对象顺序。

3. **子构造失败也纳入交付边界。** Device 分成 native 创建与 dispatch 初始化，生产 root 在 dispatch 失败时仍持有 native device，先关闭 SDK 再销毁它；独立 Device 构造仍对自己的失败回收负责。command pool 在 debug naming 失败时先释放未交付的 pool，再传播错误。Instance/Device/DebugMsger 销毁与 pool Drop 不再调用 logger，防止构造已因 logger panic 失败后，回收路径又进入同一失败 logger。

Entry 改为 GfxCore 最后声明的字段，并更正 Rc 仅共享 Rust wrapper、不能阻止 native 显式销毁的说明。没有改成由 Rc 自动释放 native，也没有新增通用 transaction/guard 框架；临时状态只归属 root 构造。显式 loader 注入入口不拥有外部 SDK，已删除“外层持有 Streamline 就能自动满足所有失败顺序”的含混承诺；仓库生产路径仍使用 Gfx::new。

该设计只处理可捕获的构造 unwind 与 Vulkan 错误转成的 panic；OOM/panic=abort、native 访问违例以及 SDK 关闭失败无法由该机制恢复。Streamline 自身失败后的 GPU 退场政策仍交 B16。外部 child/Rc 与 safe API 的完整销毁前置仍属于 B05 后续子批，不因本次修复宣称整个 RHI sound。

## 验证与提交

第一提交 `15e2defb`：VMA 显式销毁边界。

- `.temp/code-design/B05-a2/vma.rs` 包含实际 VMemAllocator 源码，仅以计数 allocator 替代 vk_mem native 实现；不把模拟 ash handle 交给 driver。修复前在 debug assertions 开/关两种编译中，遗漏 destroy 都触发 inner 释放一次；修复后两者均为零。显式 destroy 始终恰好释放一次，Debug 的遗漏诊断保留。
- `cargo check --offline --locked -p truvis-gfx` 通过。夹具证明 wrapper 的 Drop 行为，真实 VMA 分配和 GPU 资源未执行。

第二提交为本报告所在提交：root 分阶段交付与失败回收。

- `.temp/code-design/B05-a2/root-before.rs/root-after.rs` 引入实际 Gfx/Core/foundation/command pool 等源码。可控 `fake-vulkan.dll` 经真实 ash loader 和真实 native Vulkan binding 返回错误/记录事件；只替换 Streamline runtime 与 VMA 的具体实现，不创建真实 GPU 对象。`make-root-probe.py` 从第一提交提取修复前源码，不改工作区历史。
- 修复前对照：物理设备枚举失败记录 `sl+,instance+,sl-`，Instance 遗漏；dispatch 缺失记录 `sl+,instance+,device+,device-,sl-`，Device 早于 SDK 关闭且 Instance 遗漏；pool naming 失败子进程以 -1073740791 退出，发生二次 panic。
- 修复后 14 个 Gfx 场景覆盖成功、Instance 创建、物理设备枚举、队列不足、Device 创建、dispatch 缺失、messenger 创建、root naming、pool 创建/naming、VMA 创建、logger panic、loader 缺失、CString NUL；10 个独立 GfxCore 场景覆盖其适用阶段。均校验每个已创建对象恰好回收一次，child 早于 device，生产路径 SDK shutdown 早于 device/instance。开启/关闭 debug assertions 两种探针编译均通过；额外核对独立 Device 成功/dispatch 失败的回收。
- VMA 失败顺序为 `sl+,instance+,device+,debug+,pool+,pool-,sl-,debug-,device-,instance-`；dispatch 失败为 `sl+,instance+,device+,sl-,device-,instance-`。构造过程没有提交宿主 GPU work；这些事件证明 wrapper 的调用顺序，不证明 SDK 内部线程/GPU 已停止。
- 最终 `cargo check --offline --locked -p truvis-gfx -p truvis-renderer`、`cargo build --offline --locked -p truvis-gfx` 通过；修改文件 rustfmt 和 git diff 空白检查通过。无 GPU/真实 SDK/VMA 故障注入；关闭断言的探针不是正式 Release 全量构建。
