## 跨 queue 依赖

**P1，已修复：CPU 查询完成后发布资源，但 graphics submit 没有等待上传 signal。**
`GfxCore` 当前选择同一 graphics family 的 queue 0/1 分别作为 graphics/transfer。
`GpuAssetUploadQueue::poll_completed` 查询 timeline 后，texture/sky 即可进入发布流程；
原 `RenderRuntime::prepare` 的 submit 没有对应 wait。同 family 只免去 ownership transfer，
不同 queue 之间仍需显式执行及内存依赖；CPU 查询成功不能代替 device semaphore wait。
依据 [Vulkan 同步规范](https://docs.vulkan.org/spec/latest/chapters/synchronization.html)
与 [counter 查询契约](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetSemaphoreCounterValue.html)。

queue 记录实际移入完成集合的最大 signal 值，经 sync_assets 返回给 prepare，以
`ALL_COMMANDS` wait 提交。B11-a2 将持久资源通知与这个临时 wait 分离，原同步范围保持。
不等待尚未完成的上传，也不直接采用可能大于
已提交值的查询结果。完成值保留到关闭，重复帧、发布中断或 prepare 中断不丢依赖；
提交状态不确定或已关闭时拒绝提供 wait。没有增加确认/重试框架或第二个资源 owner。

wait 作用于该 batch 及同一 queue 后续 submission order 内的工作，因此覆盖后续
raycast/RenderGraph；见 [提交顺序规范](https://docs.vulkan.org/spec/latest/chapters/cmdbuffers.html)。
它不覆盖未来改到其他 queue 的消费者。semaphore 仍由 upload queue 拥有；销毁前必须
结束引用它的所有 wait batches，当前 Runtime destroy 的 device idle 满足此正常退场前提。
设备丢失与等待失败后的全局退场仍交 B12/B27。

## 消费屏障

**P1，已修复：上传 helper 的目标范围小于实际消费者。** `GfxImage::transfer_data`
原目标阶段仅 `FRAGMENT_SHADER`，但 fallback/texture 还可供 compute/RT shader 使用；
`MeshUploadQueue::submit_mesh_upload` 中 copy 后的 barrier 仅覆盖 AS build，实际
`RasterDrawCache` 还绑定 vertex/index buffer，shader 也通过 device address 读取几何。
timeline 查询完成不会补全同 queue 后续命令的读取可见性。

image 结束屏障保留布局及 SHADER_READ，目标阶段改为 ALL_COMMANDS；mesh copy 屏障
保留 AS_READ/SHADER_READ，补充 VERTEX_ATTRIBUTE_READ/INDEX_READ，阶段同样覆盖
ALL_COMMANDS。mesh 仍在 graphics queue 上传，后续 BLAS 屏障保持，不额外增加 queue wait。
此处选择保守范围以覆盖当前多个消费者；未测量性能收益，后续缩窄须列全实际阶段和访问。
不改变 mip/layer 支持范围、内存布局、公共 API、queue ownership 或 RenderGraph 职责。

`.temp/code-design/B10-e/run-barriers.py` 编译实际 barrier 封装、image 上传方法及 mesh
mask 表达式，command/buffer 使用替身。修复前/后、debug assertions 开/关四组运行
共 8 项 image/mesh 检查通过：确认数据复制、布局、源访问、queue-family ignored 保持，
目标 stage/access 按预期扩大。它验证录制契约，不是完整 mesh/BLAS GPU 执行。
最终 `git diff --check` 通过；未运行完整构建或完整渲染回归。
