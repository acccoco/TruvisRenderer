# B04-c3：Streamline feature ABI 与调用契约

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `b5c0b6b9`，工作区干净。范围为 native feature 查询/options/tag/evaluate/free、Rust dlss.rs 和直接调用点；GPU 跨帧与恢复策略仍交 B16。

## 发现与局部修复

- **P2，SR 忽略显式深度类型，已复现并修复。** `use_linear_depth=1` 修复前仍 tag 为 `kBufferTypeDepth`，与 header/Rust 契约及 RR 行为不一致。复用 RR 的条件选择；生产 Renderer 仍传 false，不改变当前管线的深度约定。
- **P1，Rust safe feature 入口无法保证调用前置，已修复 binding 边界。** 整数 handle 无法证明对象存活；无 runtime 借用的 free function 也不受 `StreamlineRuntime: !Send + !Sync` 保护，可与初始化、关闭或函数表懒解析竞争。11 个入口改为 unsafe，调用方保留串行、对象存活、command buffer 状态和 GPU 完成责任，并补齐现有 Renderer 调用点说明；这不等于已证明上层全部 safe API 的阶段安全。
- **P1，feature SDK 异常越过 C ABI，已通过注入复现并修复。** 修复前 11 个 feature 导出没有异常边界。固定版本源码中的异常宏受编译选项控制，不能作为 Rust ABI 的 C++ 异常保证。导出边界现在转换为 `eErrorExceptionHandler`，不在 catch 内分配文本；错误不代表 SDK/GPU 状态已回滚，也不承诺处理访问违例。

## 证据与保留

SDK 仍为 2.14.1；沿用 B04-c2 核对的源码 commit `2122257e0fce486f91b385aa63b9a09b0a34b363`，本地副本在 `.temp/code-design/B04-c2/sdk/`。`sl.cpp::slGetFeatureFunction` 仅在非空地址时返回成功；`slGetNewFrameToken` 成功时返回内部环形槽地址。按这个契约使用，不为成功结果再加空指针 fallback。frame token 只在一次 native 调用中借用，未跨 ABI 返回或保存，不由宿主 delete。

ABI 由 module.h/runtime.h 定义，Rust plain structs 逐字段转到 bindgen 类型；不把 Rust bool、enum 或默认 struct 布局直接跨 FFI。SDK 类型逐字段构造，保留其版本链和初始化；不把自定义 POD reinterpret_cast 成 SDK struct。当前 Vulkan handle 投影仅适用于 Windows x64。

RR options 可表达 unpacked，但现有 evaluate descriptor 只有 packed normal/roughness tag，不能凭此认为支持独立 roughness guide；当前 Renderer 固定 packed。模式与 guide 的完整适配、release 失败后 owner 状态以及高层 safe API 的阶段约束交 B16/B05，不在 ABI 修复中建立新 runtime/session 抽象。

冗余与抽象评估：SR/RR 的 options/settings 与 evaluate 有重复，但 SDK 类型、guide 集合和错误上下文不同，当前显式适配比新增通用 feature 模板更容易核对。真正多余的能力候选是没有生产调用者的手动 `set_vulkan_info` 和未配套 guide 的 unpacked 选项；B16 在确认支持范围后收敛，当前不为未来模式扩展实现。现有 free function 缺少 owner 借用是安全边界问题，本批显式标为 unsafe；是否整体改成 owner 方法需结合 Gfx/Renderer 的阶段能力复核，不能仅把函数搬进空 struct 就宣称生命周期安全。

## 验证

第一提交 `7f41c5a3`：SR 深度类型转发。

- `.temp/code-design/B04-c3/feature.cpp` 包含实际 module.cpp，以可控 SDK 入口检查调用顺序、同一 token/viewport/command buffer、矩阵字段、SR/RR tag 数量、extent 和生命周期。修复前 SR linear 请求 actual=0 / expected=49；修复后 SR/RR 的 device/linear 四种组合全部匹配。夹具不提交真实 GPU 命令。
- `just cxx-debug` 成功编译并部署 Debug DLL。ABI 字段与 Rust 签名未改；不重复完整 GPU 构建或画面验收。

第二提交为本报告所在提交：跨语言 feature 调用契约。C ABI 字段、依赖方向、owner 和 pass 顺序不变；Rust 函数签名有意收紧，不增加兼容入口、锁或新的 session owner。

- 同一 `feature.cpp` 在 11 个导出的 23 个 SDK 调用点注入 C++ 异常：修复前均逃逸，修复后均返回 `eErrorExceptionHandler`。正常 evaluate 的预算警告仍归为成功，真实错误保留原值。注入使用实际 wrapper 源码与 SDK 类型，未加载真实 SDK。
- `layout.cpp/layout.rs` 对照 native header 与当前生成 binding：Windows x64 的 10 个 struct、93 个字段 offset，以及全部 size/alignment 一致；C++ 探针由 clang 的 MSVC target 编译，Rust 由 rustc 编译。含 InitDesc 的 callback/指针，所有 feature POD 与 evaluate 嵌套结构。两种 evaluate descriptor 分别为 664/832 字节、alignment 8；没有调整字段或 padding。
- `safe-calls.rs` 编译负例：11 个未包 unsafe 的 feature 调用分别报 E0133；正式 `cargo check --offline --locked -p truvis-streamline-binding -p truvis-renderer` 通过，覆盖两个 pass 和状态调用者。`cargo build --offline --locked -p truvis-streamline-binding`、`just cxx-debug` 和修改文件 rustfmt 检查通过。
- 输出行为按现状明确：optimal settings 只在成功时写入；support query 可能先写 requirements 再失败。Rust 只在返回成功后构造结果，native caller 也不得消费失败输出。support=false 的降级语义保留，完整 capability/fallback 策略交 B16。
- 固定版本 [ResourceTaggingForFrame::setTag](https://github.com/NVIDIA-RTX/Streamline/blob/2122257e0fce486f91b385aa63b9a09b0a34b363/source/plugins/sl.common/resourceTaggingForFrame.cpp) 复制 Resource/Extent；commonEntry.cpp 的 constants.set 经 commonInterface.h::ViewportIdFrameData 复制到 owned blob。native 栈上的 tag/constants 描述可在调用后结束，但底层 Vulkan 对象仍须活到 GPU 使用完成。预算警告处理另对照同版本 [slEvaluateFeatureInternal](https://github.com/NVIDIA-RTX/Streamline/blob/2122257e0fce486f91b385aa63b9a09b0a34b363/source/plugins/sl.common/commonInterface.cpp)。源码副本仅放 `.temp/code-design/B04-c3/`。
