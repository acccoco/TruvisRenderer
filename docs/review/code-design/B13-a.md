# B13-a：线程完成通知与异常保留

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准 `a5cbfcae`，分支 `refactor`，初始工作区干净；局部修复在本报告所在提交。扫描 RenderThread 全部方法及两种
窗口宿主的 spawn 回调、about_to_wait、destroy/join；平台窗口细节留给 B13-b/c。

## 已确认问题与局部方案

- **P1：异常日志可阻断完成发布。** RenderThread::spawn 在捕获主执行错误后先调用
  error 日志；日志后端 panic 会跳过 request_exit/finished/on_finished。窗口等待完成
  通知且 about_to_wait 只能看到 false，可能一直不能退出，join 还会得到日志异常。
  移除该诊断调用，原始异常继续通过 join 交给窗口 owner。
- **P1：通知异常覆盖原始错误。** finished 已发布，但 on_finished 位于主 catch 外；
  callback panic 成为 JoinHandle 的外层错误，保存的 init/factory/Loop 原异常被丢弃。
  单独捕获通知；主执行失败时保留其 payload，主执行成功时返回通知失败。
- **P1：Drop 诊断可能二次展开。** Drop fallback 在 join 得到错误后调用 logger，
  如果窗口宿主已经在 unwind，logger 再 panic 可导致 abort。Drop 只请求退出/join，
  不执行该日志；正常路径必须显式 join 才能传播原 payload。

修复只影响线程完成/诊断交接，不添加 shutdown guard、GPU 回收、重试通知或平台依赖。
finished 定义为主执行已结束、窗口可以进入 join，绝不表示 callback 已返回或 native
资源已销毁。已有宿主回调仅 best-effort 发送事件，about_to_wait 可读取 finished。

## 验证

`.temp/code-design/B13-a/run.py` 编译实际 RenderThread 全文件，替换 RenderLoop/控制
对象和 logger，保留真实 OS thread、catch_unwind、原子标记、channel 和 JoinHandle。
正常、build_init/factory/Loop 失败、notify 失败及与主执行失败组合、日志失败、Drop
正常/异常等 13 类 × 前后版本 × debug/overflow 两配置，**52 次通过**。

逐项检查执行入口顺序、工作线程身份、通知次数、exit 发布与 join 的 payload 优先级。
通知 callback 通过 channel 等待主线程确认，验证此时 finished 已为 true，而 callback
尚未返回；旧版日志失败可丢通知并改变 payload，新版不调用日志。旧 Drop 的日志失败
会向外 panic，新版 Drop 不因该日志失败；没有在旧版主动触发二次 unwind/abort。

夹具没有 Renderer/Vulkan、真实 EventLoop/窗口、OS spawn 失败或自定义 panic payload
析构器的二次异常。不证明 finished 之后 GPU 已完成，也不证明所有 Drop 均不会 panic。
移除日志调用后，本 crate 的 log 依赖和 lockfile 对应依赖边同时清理，没有升级包。

`cargo check --offline --locked -p truvis-app` 与 `git diff --check` 通过。未新增源码
单元测试，未运行 GPU/窗口验收。

## 交接

RenderLoop 中途 panic 仍可能跳过显式 shutdown，join 返回错误不能证明 HWND 可安全
销毁，沿用 B12-c/B12-d 的 B27 待办。嵌入窗口的启动失败传播与事件循环退出错误另见
B13-b，输入队列增长另见 B13-c；本子批不勾选整个 B13。

保留判断：RenderThread 不依赖 winit，factory 在目标线程执行，raw handle 由宿主
重建；此处没有需合并线程宿主与窗口宿主的冗余。finished 是事件投递之外的查询状态，
JoinHandle 负责真正线程回收，二者不互相替代。没有引入额外状态枚举或后台 watchdog。
