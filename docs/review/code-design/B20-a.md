## P1：首次 clear 前分配前缀未回收

SharcTargets::new 顺序创建三个 GfxBuffer，后续分配失败时，已完成 buffer 进入只诊断
不释放的 Drop。debug 下还可能在原始 panic 中再次 panic。B16-c 已明确此阶段可局部修复。

架构预检：owner 仍为 SharcTargets，复用同文件 RestirDiTargets 的固定 Option 数组与
catch_unwind 显式回收方式。各 buffer 只有分配，没有 GPU 提交；叶子构造失败已由
GfxBuffer::new 处理自身半成品，组合层只回收已返回前缀。释放后的日志异常不停止剩余
回收，继续传播原始构造错误。没有新增长期状态、通用 guard、ABI 或资源。
修复提交为 `bfdd3db4`。

clear_all 留在分配回收范围外：公共 one_time_exec 不区分未提交和 submit/wait 未知状态，
不能遇到任意 panic 就释放三个 buffer。真正未知阶段与外层 RealtimeRenderResources
组合构造仍交全局失败退场方案；本修复不承诺整体无泄漏或真实 clear 失败可安全 unwind。

验证在 `.temp/code-design/B20-a/`：

- `check-allocation.py` 抽取实际 SharcTargets struct/impl/Drop，mock GfxBuffer 与 immediate
  command。三个失败位置 × allocation/叶子初始化两类失败 × 八种释放诊断 mask，共 48
  组，原始错误身份保留，clear 均未开始，修复后前缀全部显式释放且无重复释放。
- 正常创建与八种 shutdown 诊断组合全部通过；释放错误不跳过后续 buffer，重复 destroy
  无作用。debug 开启 56 例、关闭 57 例通过；关闭时额外记录未知 clear 提交保留三个
  buffer、未新增回收。旧版 debug 仅运行八项正常构造/关闭，避免故意触发双重 panic；
  旧版无 debug 的分配矩阵共遗留 48 个前缀 buffer，新版为零。
- 正常分配名称、尺寸、usage、clear/fill/submit/wait 和释放事件前后逐字节一致；容量
  2^22，大小 32/64/64 MiB，三个 accessor 不变。这里只是 CPU recorder，不分配真实 160 MiB。
- `cargo check -p renderer-rendering -p truvis-renderer` 通过；未修改 shader/ABI，不重复
  shader 或完整 App 构建。无永久测试。

## P1：首个 cache 访问缺少跨帧依赖

原有 barrier 只在 Update 和 Resolve 后执行；上一帧 Query 位于最后一个 barrier 之后，
下一帧 Update 却在首个 barrier 之前写相同的持久 buffer。FIF 只等待复用槽，cache 不分
FIF；SHARC 原子操作和 queue 提交顺序不能保证所有读写访问已正确串联。

现复用 barrier_sharc_buffers，在首个 SHARC dispatch 前执行一次，并将 source 扩展为
CLEAR/TRANSFER_WRITE 与 RT shader 读写，destination 保持 RT shader 读写。
原 Update/Resolve 后的两个调用保留；Off 下也执行入口依赖，因为 debug_cache_radiance
没有 mode guard，仍可能读取 buffer。不新增 host wait、资源、ABI、跨队列同步或 graph 框架。
此项对应本报告所在提交；副作用是沿用现有 global barrier 的保守范围，未宣称性能提升。

依据 [Vulkan Synchronization and Cache Control](https://docs.vulkan.org/spec/latest/chapters/synchronization.html)，
同 queue 的 barrier 按 submission order 约束前后访问；submission order 本身不是完整
执行/内存依赖。初始化 clear 来自同一 graphics queue 的 immediate context；本改动显式
承接该 producer，但不把下述无 host wait 的 probe 当作项目首次初始化故障实测。

`check-sync.py` 从实际 Rust closure 提取四个 scope mask，并断言入口调用位于 mode
分支之前、原两个阶段调用仍在。探针用 COMPUTE 替代 RT stage，保留 CLEAR、读写访问
和入口屏障位置，在 SDK 1.4.335.0 / NVIDIA GeForce RTX 4060（API 1.4.351）验证：

- fill→首个 update：旧版一次 WRITE_AFTER_WRITE；新版零诊断，submit/wait 完成。
- update→已有 barrier→query→下一 update：旧版一次 WRITE_AFTER_READ；新版零诊断，
  submit/wait 完成。旧版缺陷 command 只录制后丢弃，不执行。
- SDK 的 `syncval_shader_accesses_heuristic` 默认 false，初次 probe 未报告 shader
  访问冲突，不能算通过。临时配置显式启用后得到上述诊断；设置只传给探针子进程。
  该选项基于 SPIR-V 静态访问分析，probe 使用单一 buffer 地址和独立读/写 pipeline；
  不含实际 TraceRays、FIF submit、完整 SHARC 或图像/性能测量。
- 两相关 Rust crate 的 cargo check 和空白检查通过。生产 shader/ABI 未变，不重复
  shader 构建；临时 compute shader 仅用于上述探针。

这些是源码与 mock 验证，不等同于 GPU 故障注入；外层 hook 异常退场仍属已有 B27 缺口。
