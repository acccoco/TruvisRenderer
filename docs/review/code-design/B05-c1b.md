## 已确认与局部修复

- **P1，pool 销毁状态与 handle 分离。** destroy 只修改 valid，重复调用再次释放同一个 native pool，
  handle/reset/free 也不拒绝销毁后的对象。改为以 null handle 表示销毁，两条释放入口共用 release；
  重复 destroy 无操作，访问已销毁 pool 在 native 调用前拒绝。Drop 按项目规则仅在 debug 诊断。
- **P1，free 不验证来源或同批重复。** 保存的 command pool 来源此前未使用；现在先验证整个批次的
  pool handle、device wrapper 身份和 handle 唯一性，通过后一次性调用 native。空批次不调用 native。
  这不验证传入 pool 的创建 device，也不防止跨批重复 free、raw handle 复用或外部 alias 继续录制。
- **P1，command 未交付失败遗漏回收。** 分配后 naming panic 没有 free；begin 在 native begin 之后
  才转换 label CString，NUL 使 command 已进入录制状态。现在先拥有名称再分配，naming 失败只 free
  本次 command；begin 与 begin_label 共用 CStr 标签入口，begin 在进入 native 前完成 CString 校验。
- **P1，immediate 提交前失败漏 free。** begin/闭包/end 可捕获失败时回收未提交 command，再传播原错误。
  返回值放在 catch 外，避免 end 失败先展开返回 owner 而来不及 free command；正常路径仍是
  record→submit→wait→free→返回，借用 slice 构造 submit info，不再为临时提交 clone command。

## 所有权与失败边界

CmdAllocator 保存 clone 负责集中释放，Renderer/sample 保存另一个 wrapper 跨帧复用；当前分配发生在
初始化路径。RenderRuntime::begin_frame 先等待当前 FIF timeline，再 reset 对应 pool。不能把 reset
直接改为 free，也不能移除 Clone 破坏实际复用契约。wrapper 不是完整状态机，safe 录制 API 尚不能
证明 command/pool/device 存活或 recording/executable/pending 状态；这些跨层类型改造交 B26/B27。

one_time_exec 的闭包可能返回 staging GPU owner，也可能捕获外层资源。必须区分提交前错误与
submit/wait 错误：后者不能作为 GPU 完成证据。通用 helper 无法凭 R 的 Rust 类型推导显式 destroy
所需的 allocator/context；也不能无条件 free command、销毁 staging 或通过 Drop 掩盖失效设备策略。
buffer/image/AS 组合构造中的资源收尾接后续 B05-c，运行时设备失败策略交 B12/B16/B26/B27。
本次明确闭包仅录制、不自行提交/free、不让 command alias 逃逸的契约；代码尚未通过类型强制它。
返回 R 或闭包局部资源的 Drop assertion 仍可能在 unwind 时造成 abort，不能宣称整体错误路径已恢复。
命令回收要求非 pending，依据 [Vulkan free 约束](https://docs.vulkan.org/refpages/latest/refpages/source/vkFreeCommandBuffers.html)；
submit/wait 错误路径不新增 free，mock 中的最终 pool teardown 也不是失效设备退场证据。

submit info 的 inner 重复保存数组裸指针，但 submit_info 每次均从仍存活的 Vec 重建投影；本轮未发现
该冗余本身导致悬垂读取。不单独为删除此冗余拆提交；native semaphore/command 的存活仍归调用 owner。
