# B15-a3：主视图 target 的共享实现与释放边界

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


起始基准 `f0d6d6c0`，`refactor`，工作区干净。覆盖 shared/targets、GBuffer、
OfflineTargets、Realtime 各 target owner，以及两个 subsystem 的 new/resize/destroy 调用链。
这是 target 生命周期审阅，不代表已完成全部 pass 的资源访问声明或 GPU 验收。

## 修复前发现与处置

- **同一规则重复实现，本批修复**：GBuffer 三通道另写了与 PerFrameImageSet 相同的
  image 创建、GENERAL 初始转换、注册 view 和释放路径。格式、usage、名称和 extent
  属于 GBuffer；生命周期机制应复用已有 PerFrameImageSet，不新增 trait 或通用资源框架。
- **释放失败链不闭合，本批修复**：registry 的 release_image_now 会移除 image/view
  索引并完成叶子释放，再返回首个诊断异常；上层 PerFrameImageSet 在 take 整个数组后
  遇到首个异常就退出，其余 image 失去 target handle。SingleImageTarget 和固定 exposure
  则在该异常后保留过期 handle。多个子 target、SHARC buffer 的顺序 destroy 同样会跳过
  后续成员。只在调用方已提供 GPU safe point 时完成本组释放，再传播首个异常。
- **创建/resize 部分失败，继续定向检查**：shared/GBuffer 先创建 raw image，再做
  immediate transition，最后注册 image/view；中途失败没有完整的局部构造 owner。
  Offline、ReSTIR、DLSS 等组合 new 也没有部分构造回收；rebuild 先 destroy 后 new，
  不能宣称失败后保留旧 target。普通 Drop 仅断言，不释放；debug unwind 可能二次 panic。
- **未知 GPU 状态不能套用释放补丁**：GfxImmediateCtx::one_time_exec 把提交前、submit
  和 wait 失败都向外传播 panic；crate 内 try_one_time_exec 才区分提交前 Err。
  Renderer 不能捕获所有构造异常后立即释放 image。此边界和 subsystem 顶层 pass/target
  的部分初始化、shutdown 短路，续接 B15-a4；跨层错误模型统一留 B27 方案，不实施。

## 设计边界

保留显式 destroy 和 typed Ctx，不在 Drop 释放 Vulkan。registry 是 image/view 实体
owner，target 持有 handle；view-before-image 顺序仍由 registry 保证。多 target 清理
只延后已进入安全释放路径的诊断，不推断未知 submit/wait 结果，不提供渲染恢复机制。
GBuffer 仍保留 A/B/C 格式、STORAGE|SAMPLED usage、frame label 和 render extent；
Realtime/Offline 的调用顺序与资源数量不变。

首组 `c5a8ab2a`：GBuffer 复用 PerFrameImageSet，删除重复构造与 Drop 断言。
`.temp/code-design/B15-a3/run-gbuffer.py` 编译修复前后实际 GBuffer/shared 源码，
仅替换底层 Vulkan/registry 为 CPU 记录器。两种 debug 配置共 4 次执行通过；
创建、所有 FIF 的三通道访问器、不同 extent 的 rebuild、destroy、重复 destroy 的
事件序列完全相同，包含格式、usage、资源名称、初始转换批次与释放顺序。
App `cargo check --offline --locked -p truvis-app` 通过。未运行 GPU。

第二组为本报告所在提交：PerFrameImageSet::destroy_all 收敛同类 target 集合的释放；
Offline 的混合 target、MainView 的 color/depth 和 SHARC buffer 保留各自 owner 的顺序。
SingleImageTarget 与固定 exposure 在调用 registry 前撤销快照，异常后不留下过期 handle。

`run-release.py` 提取实际 destroy、字段和 Drop 代码，对照 `c5a8ab2a`，以遵循
“撤销索引/释放后抛诊断”契约的 CPU registry/buffer 替身注入错误。12 类 owner
（shared 两类、GBuffer、Offline、RT working、ReSTIR、SHARC、SR inputs/exposure、
RR inputs、DLSS output、MainView）× 正常/首个/中间/最后/多个错误 × 前后版本 ×
debug 开关，**240 次通过**。包括 MainView 实际拥有的 depth，不以空 handle 代替。
检查旧版短路与残留状态、新版完整释放/空 handle/首错身份，以及清理后的重复 destroy
和真实 Drop 断言。SHARC 替身验证三 buffer 调用，不证明 VMA/native 异常后可恢复。

修复后重跑 GBuffer 正常生命周期对照，事件序列仍相同；App 编译与空白检查通过。
临时夹具均在 `.temp/code-design/B15-a3/`，未新增源码单元测试。没有 shader/ABI 改动，
未执行窗口/GPU 验收；fixture 不证明 GPU 完成、驱动异常安全或全局 shutdown 完整性。
