## 发现与本批边界

1. **P1，队列筛选错误，已复现并修复。** 原筛选只要求任意 include bit 相交：transfer-only 可成为 graphics 家族或 compute-only 家族；还会先选一个 queue 的家族，再由 GfxCore panic，漏掉后面的可用家族。改为完整能力匹配和最低数量过滤。主家族要求 graphics+compute、至少两个 queue；专用 compute 排除 graphics，专用 transfer 排除 graphics/compute。依据 [VkQueueFlagBits](https://docs.vulkan.org/refpages/latest/refpages/source/VkQueueFlagBits.html)，graphics/compute 隐含 transfer，不能误要求显式 TRANSFER bit。未改变设备扩展与 feature 集合。
2. **P1，debug 诊断共享可变状态与回调 panic，已修复。** 修复前固定 flags 用未同步的 `static mut` 懒初始化；public safe 配置函数可被多线程调用。Vulkan callback 直接进入 JSON 格式化和 log backend，logger panic 没有隔离，将在 extern system 边界终止进程。改为固定值计算并隔离可捕获的 Rust unwind，不新增日志队列/锁/全局 owner。
3. **P1，root 创建失败未完整回收，留 B05-a2 实施。** Instance 创建后，物理设备枚举/队列要求失败没有 destroy_instance；Device 创建后 debug messenger 或 debug name 失败会留下 device，GfxDevice/DebugMsger Drop 的诊断可能在 unwind 再 panic。GfxCore 交付后若 command pool/VMA 失败，已有 pool/core 同样未显式回收。这里需要逐阶段交付/回滚，而不是给 Drop 加 Vulkan release 或用 catch 忽略错误。
4. **P1，safe API 不等同于 owner 安全，已确认接口缺口，跨对象约束继续审阅。** `GfxDevice::destroy(&self)` 可通过借用调用、可重复调用，Rc 仅保存 wrapper；CommandBuffer 等 Rc 不会阻止 root 显式销毁。多个 foundation constructor 接收 ash wrapper/raw handle 却为 safe。typed Ctx 缩窄依赖，但不证明 handle 同 device、GPU 已完成或所有 child 已销毁。不能只补一个 destroyed flag 就宣称整个 RHI sound；B05-b/c 联合核对，owner 层级重设只进入全局建议。
5. **P1，VMA 的隐式 Drop 仍会释放 native，已由依赖源码确认。** `VMemAllocator::drop` 只有诊断，但其 `Option<vk_mem::Allocator>` 随后仍自动 drop；当前锁定 vk-mem 0.4.0 的 Allocator::drop 调用 vmaDestroyAllocator。非显式 Gfx drop 的字段顺序也不保证 loader 最后释放。显式正常 destroy 路径有正确顺序；误用/失败路径的实际后果尚未 GPU 复现，B05-a2 必须处理，不能把设计约束当成实现保证。

## 设计与当前实现

设计上 Gfx 是唯一 Vulkan root owner，Ctx 是短期能力借用，叶子对象在 owner 阶段显式销毁。当前代码符合依赖方向，未引入 Renderer→Engine 反向业务依赖；但公开底层 destroy、可逃逸 Rc/raw handle 与缺少失败事务，使类型约束弱于设计意图。

正常 `Gfx::destroy` 是 pool→allocator→Streamline→GfxCore(debug/device/instance)，调用者应已释放外部 child 并完成 GPU 工作；Gfx 不自己证明这些前置。正常显式销毁期间 Entry 仍存活。GfxCore 注释把“首个字段”误写成“最后 drop”、把 Rc 误写成 native device 的生存保证，需要更正，不能据错误注释断言正常路径已经 UAF。VMemAllocator 的 Pin 说法也不符合当前传值构造：需要保证 native root 的生存期，不是移动 Rust wrapper 就失效。

扩展/feature 仍由 GfxDevice 硬性请求；GfxPhysicalDevice 只按 discrete 偏好，不按完整可用性评分，且逐候选构造中任一 panic 会中断后续枚举。不要把现有行为描述成完整能力协商或多 GPU fallback。专用 compute/transfer 家族为 Option，但公开 getter 直接 unwrap；生产 queue 实际来自主家族。是否保留这些未用能力需与命令子批及架构需求一起决定。

冗余评估：Gfx 与 Ctx 的访问器存在重复，Ctx 的价值在于限制调用依赖，不能仅以方法重复删除。两类设备队列共享主家族是明确策略；本批保留两个 queue 需求，不增加自动退回单 queue。现有无状态 flags 的全局可变存储则没有必要。

## 验证与提交

第一提交 `1870b85c`：队列能力与数量筛选。

- `.temp/code-design/B05-a/queues.rs` 包含实际 physical_device.rs，通过 ash 查询函数桩提供四组设备信息，模拟句柄不进入 driver。修复前四组均选 family 0：覆盖 transfer-only、graphics-only、首个家族只有一个 queue、没有合格家族。修复后前三组分别选 2/2/1，最后一组明确失败；也核对了 compute-only/transfer-only 选择，以及未显式报告 TRANSFER bit 的合法 graphics+compute 家族。
- `cargo check --offline --locked -p truvis-gfx` 通过；没有实际 GPU 启动或队列提交验证。

第二提交为本报告所在提交：debug 诊断边界。复用现有 GfxDebugMsger 与 callback，不改变日志线程、资源 owner 或 GPU 顺序。固定 flags 无共享写入，回调捕获 Rust unwind 后返回 FALSE；故意不析构 panic payload，避免用户 payload 的 Drop 再次 panic。正常 callback 不增加该保留成本。

- `debug.rs` 直接包含实际模块，通过 `debug_utils_messenger_ci().pfn_user_callback` 调用真实 extern system 回调，装入可控 logger。修复前正常 JSON/severity/null message 通过，logger panic 子进程退出码 -1073740791，输出 `thread caused non-unwinding panic. aborting.`；修复后相同 logger panic 返回 FALSE，panic payload 析构会 panic 的场景也正常返回。
- 正常 JSON MainMessage、ERROR/WARNING/INFO、空 message 及 null data 行为核对通过；8 个线程各构造配置 1000 次，flags 一致。并发夹具是功能检查，消除数据竞争的证据是已移除 static mut，不声称运行了 TSan。
- `cargo check --offline --locked -p truvis-gfx -p truvis-renderer` 和修改文件 rustfmt 检查通过。未运行真实 driver callback、GPU 队列或 Release/abort profile。panic hook/OOM 导致的 abort 不能被 catch_unwind 恢复。
- [Vulkan callback 契约](https://docs.vulkan.org/refpages/latest/refpages/source/PFN_vkDebugUtilsMessengerCallbackEXT.html) 要求返回 FALSE，且不得调用 Vulkan；同步 logger/panic hook 也必须遵守不重入约束。本批未引入异步日志桥。
