## P1：evaluate 失败仍消费 output 并提交

`DlssSrRgPass::execute` / `DlssRrRgPass::execute` 原先只写入 Cell<Failed> 后正常返回。
Realtime 建图时已把 DLSS output 作为 SDR source，后续不会因 Cell 失败而改变；因此曝光/SDR
仍读取未确认的输出，Renderer 仍提交整批命令。B15-a5 对 debug preview 的筛选不能保护主显示。
native wrapper 的失败可能发生在 token/constants/tag/evaluate 各阶段，C++ 异常转换也不保证回滚。

最小修复：两个 adapter 只允许 Succeeded 继续；Failed 和不符合调度条件的 NotRun 都中止 graph。
复用 CompiledGraph::execute 的既有 panic 契约：放弃该录制结果，不追加 SDR、不 submit。
原始 SDK 错误仍在 evaluate 日志中，断言保留 SR/RR 阶段。无动态 fallback、SDK 自动重试或
RenderGraph 通用错误框架；成功路径及预算警告转成功的 native 策略不变。

登记的 SDK feature 仍由 B16-a 状态持有；主视图、SDR、DLSS 和 Runtime instance 历史均不会
由这次失败 render 确认。此处中止当前渲染路径，不声称可以在下一帧自动恢复，也不证明 SDK
内部没有副作用或完整退出安全。后续生命周期收尾仍属于 B16。

第一组验证：`cargo check --offline --locked -p truvis-app` 与 `git diff --check` 通过。
`.temp/code-design/B16-b/check-graph.py` 抽取真实 SR/RR execute、真实 CompiledGraph::execute，
mock 资源、SDK 和后续 SDR/提交/历史事件。SR/RR × NotRun/Succeeded/Failed/panic × 有无部分录制
共 16 种情形，在修改前后、debug assertions 开/关共 64 组通过。修改后只有成功路径进入 SDR，
失败保留模拟的部分录制事实，但不触发后续模拟提交/确认。真实 Renderer 中 submit 位于 compute
execute 后且没有捕获后继续的分支，仍由静态调用链和应用编译核对；夹具不运行 Vulkan。

## P2：组合矩阵再次求逆的精度损失

`DlssCommonConstantsBuilder::build` 原先先求 current→previous，再对该组合矩阵求逆。
探针在 near=0.03、相机从原点移至 (2,3,4) 并朝原点观察的样例中，测得 clip-space 正反串联
误差约 0.0302。进一步以同一世界点分别直接投影为独立参照，previous→current 的误差为
0.00301075，超过探针 0.001 的阈值。这是 CPU 数值证据，不是已观察到的 DLSS 画面故障。

第二组复用 RenderView 已保存的 inv_view/inv_projection，分别组合两个方向；不新增类型、
fallback 或矩阵缓存，不改变 row-major ABI、坐标约定、jitter 和 previous-view owner。
同一样例修复后 forward 误差约 0.0000927，reverse 约 0.0000410。正反串联仍约 0.0166：
投影与浮点舍入的条件数问题没有消失，因此最终检查使用两个方向各自的独立投影参照，
不以此宣称所有近远面/相机范围均满足固定误差，亦不把矩阵乘积严格等于单位阵作为前提。

`check-temporal.py` include 真实 DlssSrState、DlssOptions、RenderView、FrameRenderState，
复用现有 glam/ash；仅 SDK enum/ABI 常量使用 CPU stub。debug assertions 开/关均验证：

- 三种 render extent（1×1、1279×719、1920×1080）下空场景不推进 previous/jitter，成功提交推进；
  native 不消耗 jitter，reconfigure 重启序列但保留上一已提交相机。
- reset 在 prepare 后只改变 reset 标记，不重写本帧 jitter/矩阵；重复 prepare 和 prepare 后
  reconfigure 被拒绝；Halton u32 回绕到合法非零起点。
- 矩阵行列投影、采样 jitter 与 SDK jitter 反号、MV scale、near/FOV 与上述数值误差。
  同样探针编译基准源码，两个配置均复现 reverse 独立投影阈值失败。

`cargo check --offline --locked -p truvis-app`、修改文件 rustfmt 与空白检查通过。

## 输入与历史契约复核

| 链路 | 当前事实与保留边界 |
|---|---|
| graph→native tags | SR 5 项、RR 8 项，输入 layout 与 SL_INPUT_READ 的只读状态一致，output 为 GENERAL；opaque 读写覆盖 ALL_COMMANDS。native 在同一 token/viewport/command buffer 上提交 constants、tags、evaluate。 |
| extent/target | color/depth/MV/RR guide 用 render extent，DLSS output 用 output extent；SR exposure 是固定 1×1 R32F 的 1.0，输出按 FIF 持有。实际 SDK 对任意设备尺寸的接受性未由 CPU 检查证明。 |
| depth/MV/jitter | device depth 与 use_linear_depth=false 配套，天空写 1；MV 使用无 jitter 前后投影、previous-current 像素位移，包含模型与相机运动，scale 为 render extent 倒数。native 设置 motionVectorsJittered=false，不二次翻转 jitter。 |
| previous/reset | prepare 产生候选，Renderer queue submit 后才确认；after_prepare reset 不覆盖已上传输入。实际失败 graph 已中止，不调用 finish；保留状态 helper 的 Failed 分支不代表生产路径可以提交失败结果。 |
| RR packed guide | GBufferA 的 shading normal.xyz/roughness 与 packed option 配套；albedo、depth、MV、反射距离对应 primary surface。确定性反射距离不是粗糙反射/折射的完整运动表达，F0 guide 也不等同于参考文档的视角相关积分反射率。材质模型一致性继续交 B17，不能凭格式正确宣称重建质量正确。 |

参考仍为资源配置 Streamline v2.14.1、源码 commit `2122257e0fce486f91b385aa63b9a09b0a34b363`。
本批重新取得官方 [sl_consts.h](https://github.com/NVIDIA-RTX/Streamline/blob/2122257e0fce486f91b385aa63b9a09b0a34b363/include/sl_consts.h)
