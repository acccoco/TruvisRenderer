## 确认问题

**P1：sample 的多余 layout Rc 阻断构造失败回收。** 基准 TrianglePass:44、61–73，
ShaderToyPass:68、85–106 各保存 layout 并 clone 给 GfxGraphicsPipeline；字段只在 destroy 使用，
ShaderToy draw 已通过 `self.pipeline.layout()` 取得布局。底层 `GfxGraphicsPipeline::new` 失败时
调用 destroy，但只有最后一个 Rc 才释放 layout（graphics_pipeline.rs:200–210）。
shader 读取/创建或 pipeline 创建/naming 失败后，外层 Rc 在 unwind 中 Drop，未调用 destroy；
debug layout Drop 断言可能造成二次 panic，关闭断言也会漏掉 native layout 释放。

正常路径两步释放看似完整，是保留现状的理由；但两种 pass 都不共享 layout 给第二条 pipeline，
这份 Rc 没有独立使用者。最小修复：直接 move layout 给 pipeline，删除 pass 字段及额外 destroy，
复用 B05-c2 已实现的最后 owner 回收。公共接口、shader ABI、GPU 安全点和 resize replacement 顺序不变。
处置：已修复并通过下述验证，修复基准为本报告所在提交。

## 已核对的职责与保留项

- Tauri main thread 持有 Desktop/IPC/window host，Client 在 RenderThread 借用 World。
  App/Cornell 共用 TruvisRenderer 和 SceneInitializer；相似入口仅提供窗口/图标/预设，不复制渲染业务。
- StartupOptions 统一默认 Manual 和参数解析，help/非法参数在建窗前结束；重复 --scene 以最后值为准，
  `--help` 与非法参数组合仍报错。当前没有相反需求，不擅自改 CLI 策略。
- SceneInitializer 在 Ready/Failed/stale 终态先清 pending，再实例化或记录日志，B21-c 修复仍存在。
  实例化逐项失败保留成功前缀且不重试，这是当前明确策略；没有事务要求，不新建回滚框架。
- Manual/Sponza 复用 MaterialSamples 和 procedural mesh；Cornell preset 与手工箱子是不同展示场景，
  不因为名称相似合并。场景只注册 CPU handles，上传和销毁仍归 World/Runtime。
- samples 共用 ImGui/RenderLoop，固定 sample pass → GUI 顺序，提交后返回 false，
  不把 sample 绘制误认成 Runtime scene 的主视图提交。命令 buffer 归 Runtime allocator，sample 只持 alias。
- ShaderToy GLSL package 独立，48 字节 push constants 保留 B03 的显式宿主投影；iMouse 当前固定为
  20% 视口位置而非真实输入，iFrame 由 u64 转 i32，长期计数可能回绕。这是现有 sample 支持域，
  非本批自动扩展完整 ShaderToy API 的理由。作品源码与 ABI 不改。

## 未决与后续

App/Renderer init 中途 panic、shutdown 中某个子系统失败跳过后续释放，以及 unknown GPU submission
仍属于 B27 的全局退场方案；本次只修复已知未提交的两条 sample pipeline 构造链。
不能因正常 shutdown 或字段 Drop 顺序正确而声称失败退场完整。

ImGui 键盘/文本能力也有限：InputEvent 只建模少量物理导航键，ImGui 的 KeyboardInput 分支
只返回 want_capture_keyboard，没有注入 key/text。现有鼠标控件可以使用，不能把这些路径称为完整
键盘编辑支持。扩展文本、修饰键与 IME 涉及平台/Renderer 契约，列入 B26/B27 的能力与验收方案。
