## P1：插入失败误用有效槽 0（已修复）

HashMapInsert 的 16 槽探测全部失败后返回 false，却将 out cacheIndex 设为 0。
HashMapInsertEntry 忽略 bool 并直接返回索引；SharcUpdateHit 因而读取槽 0 的 unrelated
resolved 数据，或向其 accumulation 写入当前顶点，还会把错误索引放入后续传播状态。
固定上游版本同样包含此实现；本地修正是有证据的偏离，不更新 external 资源。

架构预检：修复归属已有 hash-grid 插入函数，失败输出改用既有
HASH_GRID_INVALID_CACHE_INDEX。下游 GetVoxelData/AddVoxelData 已有无效索引守卫，
继续传播此前有效顶点；无新 helper、ABI、资源、线程或 pass 改动。成功插入与命中路径不变。
代码及文档与本报告所在提交一致。

`.temp/code-design/B20-b1/check-insert.py` 抽取实际 Insert/Find/Entry 和 UpdateHit，
mock hash→base 映射、原子 CAS 和缓存资源。8 种容量、全部 base、空槽/同 key 位置与
wraparound 共 77,494 组，其中 17,283 个探测失败；raw/Entry 错误索引 34,566 → 0。
成功后的 key 表与独立的首个可用槽 oracle 一致，Find 的已有 key 查找保持成立。

另有 32 个 cold/warm × 历史深度 × resampling 随机值的 UpdateHit 用例：旧版均读写
错误槽或发生错误终止，新版均继续且不访问槽 0，同时把当前直接光按原权重传播给此前
有效顶点。实际 GetVoxelData 的无效索引分支保留；AddVoxelData 用有相同守卫的 recorder，
不验证原子辐射累积数值或真实 GPU 竞争。O0/O2 均通过。

`just shader` 24 编译、7 复用，两个 binding crate 构建通过；Realtime/Offline raygen
SPIR-V 校验通过，既有条件 candidate 初始化告警保留。没有 Rust/ABI 改动，不重复

## Update 与 Resolve 已核对部分

- 稀疏 Update 采用完整 5×5 block 每帧随机选择一个位置；边缘不足整块时所选位置可能
  越过 extent，因此不是每个边缘 block 都有一条更新路径。未据此判作能量错误。
- 每段 NEE 的 throughput 为 1；SharcSetThroughput 乘入当前及此前登记顶点的权重，
  UpdateMiss 把 sky/emission 传播给既有状态。非纯发光材质本地 emission 不进入当前
  反射 cache；纯 EMISSIVE 在登记前结束。MIS 使用统一 sky/emissive PDF 与原始上一位置。
- 硬限 8 次 trace；末顶点仍 UpdateHit，之后不采样 BSDF。cache resampling 取旧反射量
  替换 directLighting 后传播并停止，和硬限缺失互补样本不同。沿用 B18-c2 的已修复边界。
- 当前 propagation depth=4、最多保留 3 个先前登记项；anti-firefly 开启，radianceScale=1000，
  u32 原子累积后还原为平均值并存 fp16。量化、溢出、过滤偏差和方向相关材质近似仍须
  与 Query/支持域联合审阅；未在本批擅自 clamp、改阈值或宣称无偏。
- Resolve 采用 32 帧 accumulation 上限、64 次无样本维护后淘汰；Off 不执行 Resolve，
  stale 计数不是 wall-clock 帧数。当前 previous camera=current，adjacent-level blend
  实际未进入。配置/场景失效仍交 B20 后续。

`check-resolve.py` 抽取实际 ResolveEntry，在当前不使用 adjacent/fade 分支的条件下，
检查 960 组新旧样本数、累计帧、stale 和窗口 clamp，均符合独立平均/淘汰 oracle，
O0/O2 一致。资源/pack 为 CPU mock，保留 float32，不验证 fp16 量化、原子竞争或 GPU 调度。

## P1：Resolve 跨槽历史读取与淘汰竞争（开放，下一批先修）

旧槽前出现空洞时，Insert 可在靠前空槽建立相同 key。新槽的 Resolve 在 sampleNumPrev=0
时向后寻找旧同 key，直接读其 hash/resolved；另一个 invocation 同时可能清空旧槽，
或更新其 resolved。阶段间 barrier 无法把同一次 Resolve dispatch 内的这些读写分开。

实际 ResolveEntry 的受控串行排程反例：新槽当前样本辐射 2、数量 1；后方旧同 key 槽
辐射 10、数量 4、stale=63。新槽先执行得到 8.4，旧槽先淘汰则得到 2。两种次序都完成
相同 entry 集合；O0/O2 均复现。该反例没有模拟 fp16 舍入或 GPU 撕裂，足以证明当前
跨槽读取不具有稳定历史来源；固定上游同样有此路径，不能用来源一致解释为安全。

**B20-b2 必须先修复稳定读取契约**：在 SHARC owner 内提供 Resolve 所需的稳定 hash/
resolved 来源，连同复制或轮换、descriptor、同步和销毁一起验证；不能只给现有 dispatch
前后补 barrier，也不能删除碰撞历史继承来绕过问题。它是明确局部修复，不转交 B27。
完成后再继续 Query、失效、数值支持域与 debug。B20 尚未整体完成。

后续 [B20-b2](B20-b2.md) 已通过独立 Snapshot 阶段与两个 owner-owned buffer 修复该 P1；
反例两种次序都保留历史并得到 8.4，绑定、生命周期与阶段同步验证边界见续接报告。
