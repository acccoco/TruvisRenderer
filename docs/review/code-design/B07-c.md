## 审阅结论与局部方案

- **P1，同一 semaphore 被重复投影。** compile 将每个 import wait、export signal 和额外
  signal 直接拼接。多个 image 共用一个完成事件时，binary 被重复等待，timeline 可在同一
  batch 被重复 signal。按 handle 聚合，stage 取并集；timeline wait 取最大值（满足全部
  下限），同值 signal 合并，不同 signal 值拒绝，不替调用方选择最终里程碑。
- **P1，声明冲突未拒绝。** 同一 handle 可同时被声明 binary/timeline；timeline signal
  可以是 0，或不大于本 batch wait。compile 统一拒绝 null、类型冲突、同 handle 多个
  signal 值和 signal <= wait。raw handle 的真实 native 类型、当前计数、设备 limit 和
  queue stage 支持仍由 semaphore/queue owner 保证；不查询或改变设备状态。
- **P2，可预测的 label 错误发生在录制中。** add_pass 接受包含 NUL 的名称，execute 到
  begin_label 才 CString::new panic，之前的 barrier/pass 可能已录制。add_pass 在 setup
  之前拒绝 NUL；名称为空仍合法。不在失败后试图补 end_label 或继续提交部分 command。
- **P2，重复执行说明缺少前置。** CompiledGraph 缓存了 import 的初始 state 和 raw semaphore
  值；execute 不回写长期 image 状态，也不重置/推进 semaphore。明确只有重新满足初始
  layout/access 和同步前置时才能再次录制；当前 Renderer 每帧新建 graph，未复用旧计划。

规范依据：[VkSubmitInfo2](https://docs.vulkan.org/refpages/latest/refpages/source/VkSubmitInfo2.html)
规定同一 timeline 的 signal 必须大于 wait；[同步规范](https://docs.vulkan.org/spec/latest/chapters/synchronization.html)
说明同 batch signals 彼此无序，不能对同一 timeline signal 两次。

## 架构预检与不变量

聚合和校验留在 RenderGraphBuilder/RgSemaphoreInfo，复用现有 raw submit 投影；不修改
RHI submit API、native owner、线程、queue 或 pass 顺序。Graph 仍描述一次 batch，不能
通过不同 signal 值表达内部阶段；需要多个里程碑应由调用方分 batch。binary 在同 batch
wait 后 signal 不额外禁止，其先前 signal 与消费顺序是调用方契约。

stage 按位合并，不禁止合法的 NONE 或擅自扩大为 ALL_COMMANDS；其覆盖资源首末访问的
正确性由调用方负责。未使用 import 的 wait 仍保留，因为 graph 可以有 export transition；
不在本批添加资源裁剪或重新定义外部完成事件。

## 实际执行链与失败边界

TruvisRenderer 分别构建/录制 compute 和 present graph，cmd.end 成功后各生成 SubmitInfo，
最后按 compute→present 组成同一次 gfx_queue.submit。compute 输出显式 export 为后续
fragment read，present 再以对应 state import；buffer/TLAS 来自 Runtime prepare，未进入
image tracker。Presenter 固定 acquire wait 为 COLOR_ATTACHMENT_OUTPUT，present 完成
signal 和 FIF timeline signal 使用 BOTTOM_OF_PIPE；signal 的第一作用域覆盖前序 batch，
具体 GPU/WSI 完成边界仍需 B12。Triangle/ShaderToy 使用单 graph 的同样顺序。

command begin/end、pass execute 或 debug dump panic 均中断正常调用，现有调用方不会
执行后续 submit。Graph 不捕获回调错误：部分 command 可能已录制，必须由 owner 在安全
条件下 reset/discard，不能把 catch_unwind 当作恢复完成。build_submit_info 不持有 native
owner，也不证明传入 commands 已执行完整 graph；合法空 batch 仍由调用方明确组织。

跨 graph 的 CPU 引用在录制后结束，但 subsystem native owner 必须持续到 GPU 完成；
TruvisRenderer 提交成功后才 finish_rendered_frame。其它 prepare/累积状态可能在录制前
推进，panic 后 Runtime/RenderThread 的整体销毁与重试不在此图局部保证内，交 B12/B13/B15。
queue_submit2 的错误是 panic，未区分可重试 OOM 和 device lost；本批不统一全局错误模型。
