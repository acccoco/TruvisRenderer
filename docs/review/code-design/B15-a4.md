## 修复前发现与处置

- **冗余分配，本批删除**：MainViewTargets.depth 仅参与 new/destroy/Drop，没有访问器，
  不进入任何 graph 或 pass。实际 DLSS depth 来自 DlssSrInputTargets，不是该图像。
  MainView color 与 Offline render_target 都由 SDR/Clear 作为 storage 写入，由 Resolve
  作为 sampled image 读取；COLOR_ATTACHMENT 属于 Resolve 的 swapchain 输出。
  移除未使用的 depth 分配及两处预留 attachment usage，不影响需要的 storage/sampled 能力。
- **顶层释放短路，本批修复**：两个 RenderResources::destroy 顺序调用 pass 与 target。
  RT pass 已在 SBT destroy 前释放 pipeline/descriptor；SBT 或 target 的释放日志抛异常，
  仍会跳过后续 owner，甚至在 unwind 中触发 live-resource Drop 断言。
  已知 GPU safe point 下完成本资源集合，再传播首个异常；不引入 cleanup 框架。
- **构造失败边界，继续定向处理**：shared target 的 raw image 分配与 view 创建本可在
  未提交阶段局部回收，但目前跨越 initial transition；提交前错误与未知 submit/wait
  对外均为 panic。下一步先把可回收阶段与 immediate 提交隔开，再处理组合 owner，
  不捕获未知提交后直接释放。此问题没有被释放链修复覆盖。

## 约束与证据

资源与状态仍归原 struct；Renderer 依赖方向、线程、FIF 规则、pass 顺序不变。
RenderLoop::shutdown 在 Renderer shutdown 前 wait_idle；resize 经 Presenter 的 device
idle 后再调用 Renderer。这里仅使用 GPU command 安全点，不推断 WSI presentation 完成。
destroy 不变成异常后继续渲染的恢复接口；构造/resize 半成品仍需单独处理。

源码入口：renderer-rendering 的 realtime/offline/mod.rs、resources.rs，render-passes
的 ray_tracing/{realtime,offline,pipeline}.rs、compute_pass.rs 和 post_process
的 accum/image_clear/resolve/sdr。Native pipeline/layout destroy 不调用 logger，
RT SBT 和 target 叶子在 native release 后记录诊断；这不证明任意 native 故障可恢复。

首组 `ff73f629`。删除 MainView 的 depth 字段、构造 helper、释放和断言，以及
Realtime/Offline 中间输出的 COLOR_ATTACHMENT。所有读取 MainViewTargets 的路径仅
调用 color；ResolveRgPass::setup/execute 把中间输出作为输入，把 swapchain 作为唯一
attachment。Clear 与 SDR 声明 storage write。源码扫描确认旧 depth 名称/helper 无残留，
`cargo check --offline --locked -p truvis-app` 和空白检查通过。未做 GPU 验收；此处不
声称测得显存或性能收益，不为删除不可达资源新增单元测试。

第二组为本报告所在提交。Realtime/Offline RenderResources 对各成员显式清理、
收集首错，在所有成员处理后 resume_unwind；不重排释放顺序，不吞掉异常。
`SubsystemLifecycle::shutdown` 原有 resources.take 仍保证资源集合只交付清理一次。

`.temp/code-design/B15-a4/run-shutdown.py` 提取两版实际资源字段与 destroy 函数，
以完成自身释放后可抛诊断的 pass/target 替身记录调用。Realtime 14 个成员、Offline
5 个成员逐点注入失败，加正常与多点失败，共 23 类 × 前后版本 × debug 开关，
**92 次通过**。确认旧版在首错处截断，新版顺序完整且保留原错误身份。
这不模拟 native 失败、真实 GPU 完成或组合构造；下层 target 的组内清理证据见 B15-a3。
App 编译、空白检查通过；未改 shader/ABI，未新增源码单元测试，未做 GPU 验收。

## Pass 边界与未闭合范围

| 已核对入口 | 当前资源契约 | 进一步验证归属 |
|---|---|---|
| Offline RT → Accum → SDR | RT 写 single-frame；Accum 读单帧、读写共享累计；SDR 读累计、写输出 | running average 与采样算法 B18，曝光/显示 B15-b |
| Realtime RT | 单帧/GBuffer/mvec/ReSTIR 由 RT storage 访问；depth、RR guides 写入 | 多 phase 内部 barrier、历史有效性与 shader 读写 B19/B20 |
| SR/RR → SDR | adapter 读取声明的 color/depth/mvec/guides，写 DLSS output；SDR 读有效 source | Streamline tag/layout/feature 行为 B16 |
| Clear → Resolve / Debug | Clear 写 storage；Resolve 采样主输出/debug image，写 swapchain attachment | 无 TLAS 或未执行 DLSS 时 debug target 内容有效性续接 B15-a5/B24 |

以上是 setup/execute 与 owner 的静态调用对照，不宣称图间 barrier、所有 shader 分支
或未初始化内容已通过 GPU 验证。ReSTIR 与 SHARC 仍有真实消费者，不能因某模式关闭
就把其常驻分配直接判为冗余；是否按需分配需结合切换成本另评估。

构造缺口保持明确：raw image 数组中途失败、transition 完成后 view 创建失败、SR
exposure 的 stage-buffer 释放诊断、RR/SHARC 初始化提交，以及组合 new 的半成品。
其中分配/view 发布前后可证明没有在飞引用的阶段，可先局部修复；unknown submit/wait
不能依据一个 panic 就释放。下一批 **B15-a5** 先收敛 shared target 的可回收构造阶段，
并核对 debug source 的内容有效性；不把两项问题藏入最终全局重构。

`TruvisRenderer::shutdown` 外层仍依次调用 Client、DLSS、ImGui、overlay、selection、
SDR、Offline、Realtime。任一 hook 的异常仍会中断外层链；需要结合 B15-b/B16/B24
的各 owner 契约定向设计。全局生命周期/错误模型统一仅进入 B27 方案，不在本批实施。
父批 B15 保持部分完成。B26/B27 最终全局修改只输出方案。

后续 [B15-a5](B15-a5.md) 已完成 shared target 已知安全阶段的构造回收与 debug source
有效性筛选；未知提交、组合 owner 和外层 hook 的剩余边界见该报告，不视为已修复。
