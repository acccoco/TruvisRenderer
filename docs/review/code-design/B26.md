## 可删除或局部收敛的候选

### 路径兼容入口与闲置工具：删除，P3

[`TruvisPath`](../../../engine/e00-utils/truvis-path/src/lib.rs) 仍显式保留七个旧名称。
当前 `workspace_path/target_path/assets_path/resources_path/resources_path_str` 分别有
4/1/2/4/1 处限定名调用；`engine_path/assets_path_str` 为零。它们没有独立路径策略，
只是转发或转换，属于确认的 API 冗余。

最小方案：一次迁移这些调用点到现有 `workspace/target/assets/resources`，删除旧别名；
ImGui 读字体直接传 PathBuf，避免先转 UTF-8 字符串。保留 `target()` 的当前名称和语义，
不为清理别名另起一轮命名迁移。会失去旧源码调用名；纯本地项目不再保留兼容包装。
验证覆盖 fetch-res、CXX 工具、类型导出、Runtime、Truvis/Cornell/Triangle/ShaderToy 的编译，
并复查非 Unicode 路径与返回类型差异，不能只编译路径 crate。

另有仅发现定义/内部调用的候选：[`ResourceConfig::save_to_file`](../../../engine/e00-utils/truvis-fetch-res/src/fetch_resources/resource_item.rs)、
native [`PathUtils`](../../../cxx/modules/truvixx-utils/include/TruvixxUtils/path.hpp) 及其
[`实现`](../../../cxx/modules/truvixx-utils/src/path.cpp)、
[`StringUtils::utf16_ptr_or_default`](../../../cxx/modules/truvixx-utils/src/string.cpp)。
建议删除对应声明/实现，保留实际使用的 StringUtils 编码转换；Rust PathUtils 有 Streamline
生产调用，不能因同名一并删除。native 最小验证是重建 utils 及其 Assimp/Streamline 消费者，
检查 public header/链接符号；不把“本仓未用”直接解释为性能缺陷。

### MCP 材质参数双份声明：局部收敛，P2 维护风险

[`mcp_server.rs`](../../../app/truvis-app/src/mcp_server.rs) 的 MaterialPatchArgs、MaterialClassArg、
CoverageArg、TextureMappingPatchArg、TextureMappingArg 与
[`bridge material`](../../../renderer/editor/truvis-editor-bridge/src/protocol/material.rs) 重复字段和 tag；
update_material 经 serde_json 序列化再反序列化为 MaterialPatch。当前没有新证据证明字段丢失，
但两份声明独立演进会把编译期形状检查降为运行时转录风险，B22-b 的代表性往返不能证明全部组合。

首选方案：由 bridge 现有 DTO 持有结构，增加所需 JsonSchema 派生，MCP 外层参数保留自身的
工具描述、ID 和版本边界，直接使用 MaterialPatch。bridge 只增加 schema 描述依赖，
不依赖 RMCP、HTTP、App 或 World。先验证 schemars 对 enum tag、Option 缺省和数组的输出；
若派生无法表达既有 schema，应明确字段转换与差异，不能留下 JSON 转录作为隐藏兼容层。

会失去 MCP 私有参数类型独立演进的自由，新增 bridge 编译依赖；收益是只有一份材质 patch
结构。必须比较 tools/list schema、完整参数/省略字段/错误类型的 HTTP 行为和 TS 生成结果，
并覆盖 Editor 与 MCP 的 World mutation 入口。不要把整个 World MaterialData 暴露为 wire DTO。

同文件 `version` 只返回 `Ok(value.map(SceneVersion))`，没有失败分支；可删除多余 Result/`?`。
这是独立 P3 清理，真正的 u64 格式与冲突检查仍在 RenderThread controller，不能随之删除。

### Automation 空通知能力：删除，P3

[`create_automation_bridge`](../../../renderer/editor/truvis-editor-bridge/src/lib.rs) 总是分配通知队列；
[`AutomationNotification`](../../../renderer/editor/truvis-editor-bridge/src/protocol/automation.rs) 只有
SceneVersionChanged。当前 controller 没有发送调用，MCP `run` 将 receiver 绑定到 `_notifications`
而不读取。确认是没有实际生产/消费的能力，不是已发生队列堵塞。

最小方案：让 Automation 只携带现有 RequestEnvelope/oneshot 请求链，删除其通知枚举、
sender/receiver 和通知容量配置；Editor 的通知、重查与独立请求预算保持。可以复用现有
request 部分，但不要为可选通知增加模式 trait、注册器或泛型能力组合。会失去预留的主动推送
扩展点，当前 HTTP query/reply 不受影响。验证容量满、关闭排空、放弃 reply 后 mutation
仍可能执行，以及 Editor 通知恢复。不能把两条请求队列合成一条而改变饥饿/预算边界。

### native 提交投影缓存：局部收敛，P3

[`GfxSubmitInfo`](../../../engine/e10-gfx/truvis-gfx/src/commands/submit_info.rs) 同时保存
`inner: SubmitInfo2<'static>` 和三个 owned Vec，`submit_info()` 又用 Vec 重建全部指针/count。
当前没有发现 inner 承载其他可变策略，建议现场构造 SubmitInfo2，仅保存真实输入。
会失去缓存原生投影的扩展点；Vec 的堆地址在 wrapper 移动时不变，不能把这项清理说成
已证实的悬垂修复。验证 empty/multiple command、wait/signal 的 flags/count/pointer/value
投影一致；raw semaphore 的存活和提交完成仍由调用 owner 保证。

## 提案顺序、验证与交接

后续若选择实施，建议按语义独立推进：路径别名迁移、native 闲置工具删除、Automation
通知移除、MCP schema 单源、submit 投影清理各自独立可回滚；不要打包成“全仓清理”。
材质诊断、Ctx 权限和资源失败协议分别另设设计/验证批次，不能混入机械删除。
先解决 B27 的高风险生命周期方案，再根据成本安排 P2/P3；本次不执行上述任何源码改动。

本批验证限 manifest 依赖检查、源码使用关系与文档链接/空白检查。未修改源码、配置、
锁文件或生成物，不重跑构建、shader、GPU 或 HTTP 夹具；历史结果仅引用对应报告。
这不包含实机 DPI/输入、未知提交/设备丢失、完整图像/性能或所有动态依赖的验收。

B26 约定范围已扫描，**下一批 B27：全局严密性与验收计划**。沿主清单八条端到端链

版本耗尽和材质数值/能力边界。输出整改顺序、最小回滚范围、证据等级及未覆盖项；
