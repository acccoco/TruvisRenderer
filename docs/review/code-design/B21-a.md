# B21-a：Editor transport 与 RenderThread 生命周期

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准 `a7bd7703`，`refactor`，起始工作区干净。本子批核对 Editor request inbox、
oneshot reply、notification outbox、每帧预算、timeout 和 shutdown；当前链路没有需要
局部改写的传输缺陷，补充了可验证的语义边界。

## 已核对的不变量

- `FrontendEndpoint` 只拆出 request sender 与 notification receiver；`RendererEndpoint`
  只在 RenderThread update 阶段 `try_recv`，不跨 await、不等待 Tauri/WebView。
- 每条 request 携带独立 oneshot reply。queue full 在 `try_send` 处立即返回 `Busy`；
  receiver closed 返回 `Internal`；RenderThread 关闭 receiver 并清空尚未处理 envelope，
  已等待调用方看到 reply sender drop。
- Editor controller 按消息数和 wall-clock 双预算消费；预算在请求之间检查，本帧停止后
  inbox 留给后续 frame。队列读取非阻塞，但单个慢请求不可抢占，500μs 不是硬耗时保证。
- timeout 只结束当前 Tauri invoke 的等待，不撤销已入队请求。若命令尚未执行，后续
  RenderThread 仍可能完成 CPU mutation；reply receiver 已丢弃，结果由 scene version
  notification 或后续 query 恢复。已经开始执行的 mutation 更不能回滚。
- notification 是 best-effort。outbox 满只丢通知，不影响该 request 的独立 response；
  WebView 必须通过 scene version/query 重建投影。正常 shutdown 先禁止新 invoke，并由
  RenderThread Client 清空 request inbox，再停止 notification task；异常退场另行审阅。

## 实现判断

当前 timeout 后继续执行是设计选择，不是隐藏的取消保证：`RequestEnvelope` 没有 cancellation
token，controller 在同一 update 阶段直接调用 World adapter。添加“超时即取消”需要定义
命令原子领取、World mutation 前的取消竞态、Automation 对应语义和前端显示，不能作为
transport 局部修补混入本批。

本批未发现队列重复实现：Editor/Automation 各自拥有 lane 和领域协议，共用 endpoint
结构与 shutdown 机制；Desktop command 另用容量为一的特权队列，避免把 PathBuf 提升为
通用 DTO。没有把 `accepted`、CPU mutation 或 GPU 完成混成一个 response。

这里仅验证 App 侧恢复机制可用，不证明 Web 会在每一种错误后自动刷新或避免旧草稿
覆盖新数据；前端恢复策略留给 B23。Desktop dialog 等待不使用 Editor 两秒 timeout，
其等待/关闭及特权命令生命周期由 B21-c 继续核对；MCP 的完整行为留给 B22。
