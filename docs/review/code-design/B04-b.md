# B04-b：Vulkan native 命令桥接

> 历史说明：本文项目 hash、提交次数及“本报告所在提交”均按压缩前历史解释，实验引用保留为“压缩前证据基准”；第三方版本不变。当前分组见[提交压缩映射](commit-squash.md)。


基准：`refactor` 的 `7df81047`，工作区干净。范围包括 truvixx-vk 的全部 header/实现/CMake、truvis-vk-binding 全部源码/构建配置、生成绑定，以及 GfxDevice 构造失败清理、GfxCore 显式销毁和 push descriptor 的直接调用链。Gfx 全量生命周期、能力协商与录制状态审阅归 B05。

## Owner、冗余与抽象

桥接不创建 Vulkan 对象、不加载第二个 loader、不分配 native heap；函数表按值保存设备和一个命令地址，Rust 不公开可修改表。ash Entry→Instance 的原生查询函数进入 native，命令指针按设备缓存，调用同步返回。GfxDevice 持有 wrapper，初始化失败会先 destroy_device 再 panic；上层 Instance/Entry 的整体失败回收仍需 B05。

Rust namespace import 复用 ash 0.38.0+1.3.281 的 handle、enum、PFN 和 WriteDescriptorSet，未发现重复 DTO。native 仅链接 Vulkan::Headers，VK_NO_PROTOTYPES 排除意外 loader 依赖。C++ extern C 导出与 Vulkan PFN system 调用约定分开，目标被固定到 Windows x64 MSVC。

此桥接目前只转发一个命令，确实比直接调用 ash 多一层；但符合项目已确认的 CXX integration 边界，不能仅凭薄包装删除。函数表中的 device 没有参与每次转发，也无法据此核验 command buffer 的真实 parent；保留其设备身份说明，不新增全局句柄注册表或伪安全检查。

## 修复前发现

1. **P2，构造安全性契约未体现在 Rust API，已确认，已修复。** `src/device.rs::Device::new` 是 safe，却直接调用要求有效 native device 与 loader 的查询入口。`&ash::Device` / `&ash::Instance` 不拥有 Vulkan 对象，引用不能证明句柄尚存活或来自同一链路。当前唯一生产调用位于同一 Instance 创建 Device 后，符合前置；未观察到生产故障。改为 unsafe constructor 并写 Safety，调用方在已有创建位置承担证明，不新增引用型 owner。
2. **P2，空 push 列表未拒绝，已确认，已修复。** `GfxCommandBuffer::push_descriptor_set` 的 safe 入口可接收空列表；with_writes 对空列表照常回调，binding 将 count=0 透传。现有生产调用列表非空，不代表接口覆盖。Vulkan 要求 descriptorWriteCount 大于 0；在 binding 的命令方法进入 native 前用非 debug assertion 拒绝，既不改通用 with_writes（普通 update_descriptor_sets 的零写入语义不同），也不静默跳过错误。
3. **B05 交接，已确认注释偏差、完整风险待复核。** GfxCore 的 vk_entry 注释误称首个字段最后 drop；gfx_device 注释误称 Rc 保证 native device 不被提前销毁。实际 destroy 显式释放 native 对象，Rc 只延长 Rust wrapper，Drop 不做 Vulkan release。正常 destroy 内 Entry 仍存活；不能仅因字段顺序推断当前正常路径发生 use-after-free。B05 应一起复核 safe Gfx 入口、外部 Rc、失败 unwind 和销毁后继续调用，而非在此改变全局 owner。

规范核对：[vkGetDeviceProcAddr](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetDeviceProcAddr.html) 的有效 device 与设备子对象限制；[vkCmdPushDescriptorSet / KHR](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdPushDescriptorSet.html) 的非零 count、同设备、录制与外部同步要求。核对日期 2026-10-28；不据最新版页面增加当前项目未启用的新 feature。

## 架构预检与局部方案

修改归属现有 binding Device impl；唯一构造调用在 GfxDevice 同步调整。native ABI、对象 owner、线程、DLL 来源和 GPU 资源存活期不变。依赖仍为 Gfx→binding→C ABI；用现有 Rust unsafe/断言表达约束，不新增 wrapper 或兼容层。同步 binding README 与 Gfx 的直接说明，相关报告随行为提交，最多两次。
