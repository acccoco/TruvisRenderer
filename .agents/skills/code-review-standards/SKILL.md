# 代码审查标准

## 审查顺序

1. 先报告会造成错误行为、安全问题、资源泄漏、数据损坏或契约破坏的真实缺陷。
2. 再报告有具体证据的维护性问题，例如职责分散、重复实现、所有权不清或未表达的顺序依赖。
3. 最后列出开放问题、假设和必要的验证缺口。

除非用户明确要求修复代码，否则只做审查，不直接改代码。审查输出默认使用中文；代码标识符、API 名称、领域术语可以保留英文。

## 重点检查

- 结合 diff、相邻模块、调用方和项目文档判断改动，不脱离现有职责边界评价局部代码。
- 对每个新增 helper、局部工具类型或通用转换逻辑，搜索标准库、现有依赖和仓库内相似实现；发现重复时指出已有 API 或模块以及建议归属。
- 当多个函数共享同一组依赖、调用顺序、资源生命周期、跨帧状态或领域不变量时，检查它们是否缺少明确的 owner。
- 无状态、真正局部、逻辑简单或由语言与框架要求的 free function 可以保留，不为形式强行引入 `struct`。
- 检查新增的全局可变状态、隐式依赖、职责不清的 manager，以及为了单一分支产生的过度抽象。
- 按 `AGENTS.md` 和当前规则检查中文注释与文档；重点关注所有权、生命周期、线程与同步、资源释放、FFI、RenderGraph、shader/resource 和坐标系契约，不要求复述代码行为的注释。

维护性问题必须说明缺失的内聚点、可能造成的实际成本和可执行的收敛方向；不要只给出个人风格偏好。

## 输出格式

每个问题包含：

- 严重级别。
- 文件与行号。
- 触发条件和具体风险。
- 建议方向；涉及重复实现时必须指出已有归属 API 或模块。

问题列表放在最前；没有问题时明确说明。随后给出开放问题或假设、简短总结，以及必要的测试或验证缺口。
